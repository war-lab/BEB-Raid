# 32. 改修計画_敵対的検証

## 1. 結論と進め方

[31_敵対的検証棚卸し](31_敵対的検証棚卸し.md) の所見99件（K-1〜K-99）のうち98件を92タスク（T-274〜T-365）へ割り当て、10のウェーブに分けた。K-9（ブランチ保護）はJ-116によりタスク化せず、人間タスクH-18として10節に置く。

ウェーブ0は契約変更を含むため単独PRとし、他のウェーブより先に完了させる。ウェーブ1は本番で機能が損なわれている疑いのあるもので、次に着手する。以降は依存が薄いため並行してよい。

判断J-115〜J-126は自走を止めないため3節で正文を確定させた。発起人はこれを覆してよい。

規模が大きいため、1セッションで全ウェーブを完了できない場合は**ウェーブ単位で区切って中断する**。中断時はSTATUS.mdの1.4節に到達ウェーブを記録する。着手済みで未完のタスクを残したまま次のウェーブへ進んではならない。

## 2. 位置づけ

正本は01〜07およびADR群で、本書はそれらに従属する。所見の詳細・機構・根拠は31を正とし、本書には再掲しない。

タスクIDはグローバル連番を継続しT-274から振った。判断IDはJ-115〜J-126である。

31との対応は6節のタスク表の「所見」列（タスク→所見）と、6節末尾の対応表（所見→タスク）で引く。1つのタスクが複数の所見を解消する場合と、1つの所見が複数のタスクに分かれる場合の両方がある。

## 3. 事前決定事項（J-115〜J-126の正文）

### J-115 ダメージの丸めと滞留端末の復旧

丸めは `services/answerPipeline.ts` の送信ペイロード組み立て直前で行う。`Math.round` を使い、切り捨てにはしない（0.5係数で常に不利にならないようにする）。

`engine/damage.ts` の `computeDamage` は変更しない。表示用の実ダメージと送信値を分離し、契約が整数であることは送信側の責務とする。

滞留端末の復旧経路を設ける。`syncRaidDamage` が400（`invalid_body`）を受けた場合、当該バッチのペイロードを1件ずつ検証し、非整数の `damage` を持つレコードは `Math.round` して書き戻す。書き戻しても不正な場合は警告して削除する。削除は `pendingSync` のみを対象とし、`attempts` には一切触れない。

### J-116 CIゲートの強制範囲

`deploy.yml` のみ修正する。`build` ジョブに `npm run lint` と `npm test` のステップを追加し、いずれかが失敗した場合はPagesへの配信に進まないようにする。

**リポジトリ設定（ブランチ保護・required_status_checks・enforce_admins）は変更しない。** `gh api` によるリポジトリ設定の変更をタスクに含めてはならない。K-9は記録に留める。

### J-117 deviceTokenの扱い

エクスポート時に `deviceToken` を伏せ、インポート時は復元先の既存トークンを優先する。既存トークンが無い端末では再登録の導線を出す。

エクスポートUIに「このファイルは学習データを含む。共有APIの認証情報は含まれない」旨を表示する。

`packages/api` と `shared-schema` の契約は変更しない。サーバー発行シークレットへの分離は採らない。

### J-118 Service Workerの更新方針

`registerSW` に `onNeedRefresh` を渡してリロードを奪う。更新の適用はユーザー操作か、セッション非進行中のホーム表示時に限定する。

[18_改修計画_表示更新とUX残課題](18_改修計画_表示更新とUX残課題.md) の記述（次回起動時反映）を実装が満たす形にする。文書側は変更しない。

### J-119 人手レビューの必須範囲

**全パックをAIクロスレビューで可とする。ただし敵対的検証を工程に含めることを条件とする。**

読解（ADR 0006判断5）の人手レビュー必須は維持する。他パートは「LLM生成＋AIクロスレビュー＋敵対的検証＋TTS」を正規の工程とし、CLAUDE.mdとdocs/04の不変条件の文言をこれに合わせて改訂する。

敵対的検証の工程定義は8節に置く。既存の全パックに対して遡って適用する（T-355）。

配信は止めない。未レビューと記載のある3パックも、敵対的検証を通した時点で `origin` の記載を更新する。

### J-120 シャドーイングの算入先

ストリークに算入する（docs/03 8節の記述どおりにする）。`countSrsAnswersOn` を `mode === 'srs'` または `questionId` が `shadow:` で始まるものへ広げる。

成長ランクの学習日数からは除外しない。ただし「1日あたり最小1問の正誤判定を伴う解答がある日」を学習日の条件に加え、再生のみの日は数えない。

### J-121 レイド帰属窓とHP日数

実装を変えず、docs/17にJST併記と「土曜0:00から月曜9:00は非加算」を明記する。`RAID_DAYS` は5のまま据え置く。

窓の変更はレイドのバランスに直接影響し、本番稼働中の週をまたぐため、本改修では扱わない。

### J-122 ボスHPの母数

docs/02 5.2節とdocs/03 6.2節を実装に合わせ、母数を「登録メンバー全員」と改める。docs/17の記述が正しい。

opt-inによる絞り込みはサーバーにjoin APIを作らない方針（docs/17）と衝突するため採らない。

### J-123 サンドバッグ対策

対策を実装しない。docs/03 5.6節に「M4到達後に再評価し、仲間内運用のため引き続き対策しない」と決定を追記し、ADRには起こさない。

### J-124 端末時計の変更への防御

値の破損を防ぐクランプのみ実装する。時刻そのものの正当性検証（サーバー時刻との突き合わせ等）は行わない。

対象はSRSの `dueAt` の上限クランプ、ストリークの未来値巻き戻し、`rankPoints` の単調化の3点に限る。

### J-125 アクセントの縮退

docs/04 5節とdocs/08を「米/英の2アクセント（Piperの対応状況による縮退。スキーマの `AU`・`CA` は有効値のまま）」へ改訂する。別プロバイダの検討は行わない。

### J-126 カバレッジの運用

`@vitest/coverage-v8` を導入し、レポーターは `text` と `json-summary` とする。閾値は導入時点の実測値をそのまま下限として固定し、以後下げない。CIはサマリを出力するのみで、閾値未達時は失敗させる。

## 4. 変更禁止・注意領域

以下は本改修の対象外である。触れてはならない。

- **リポジトリ設定**（ブランチ保護・ルールセット・Actionsの権限）。J-116による。
- **SRS間隔テーブル**（`engine/srs.ts` の間隔値）。docs/03が正本で、本改修では値を変えない。
- **レイドの週境界とRAID_DAYS**（`raidWeek.ts`・`raidConfig.ts` の期間定義）。J-121による。
- **`attempts` の削除・更新経路**。追記のみの不変条件を崩す変更を一切行わない。
- **`packages/api` の認証契約**（`/register` の応答形式・Bearerの意味）。J-117による。
- **main への push・マージ**。devへのPRまでとする。本番APIの自動デプロイを伴うため。

次は注意して扱う領域である。

- **`content/packs/*.json` の直接編集は禁止**。`verify-content` の drafts乖離チェックで検出される。コンテンツの修正は必ず `packages/cli/src/data/*.ts` を編集し、`beb generate` → `beb build` で再生成する。
- **`shared-schema` を変更したら必ず `npm run build -w @beb-raid/shared-schema` を実行してから他パッケージのテストを走らせる**。消費側は `dist` を見るため、ビルドしないと古いコードをテストする（K-14。T-287で恒久対策する）。
- **`beb tts` は外部バイナリに依存する**。`piper`・`ffmpeg`・`ffprobe` と `.piper-voices/` の4モデルが必要である。実行前に存在を確認する。

## 8. AIクロスレビュー＋敵対的検証の工程

J-119により、読解以外のパックはこの工程を人手レビューの代替とする。工程を経ていないコンテンツは配信しない。

### 8.1 手順

生成物（`content/drafts/*.jsonl`）に対して2段階を実施する。

第1段はクロスレビューである。生成に使ったのとは別のモデルで全問を読み、正答の一意性・英文の自然さ・解説の妥当性・スキーマ準拠を判定する。

第2段は敵対的検証である。以下の観点を明示して、問題を壊す側から読む。観点ごとに独立して実施し、結果を統合する。

| 観点 | 問い |
|---|---|
| 二重正答 | 正答以外に成立する選択肢は無いか。語法・文脈の両面から反例を挙げよ |
| 不当な易しさ | 音声を聞かずに、または本文を読まずに解ける経路は無いか。消去法・語形・パターンで解けないか |
| 話者と設問の整合 | スクリプトの話者ラベルと設問・解説の指示（man／woman）が一致するか |
| 題材の適格性 | 本試験が扱わない題材（訴訟・破綻・人員整理・個人の不利益）を含まないか |
| 実在情報の混入 | 実在の企業名・人名・メールアドレス・URL・電話番号を含まないか |
| 統計的偏り | 正答位置・選択肢セット・設問タイプ・難易度の分布に偏りが無いか |

### 8.2 記録

判定結果を `content/drafts/<name>.adversarial.tsv` に記録する。列は `id`・`verdict`（accept／revise／reject）・`observation`・`reviewer`（モデル名）・`reviewedAt` とする。

`pack.origin` に工程名と日付を記録する。書式は「<生成手段>＋AIクロスレビュー（<モデル名>）＋敵対的検証（<観点数>観点・<日付>）＋TTS」とする。<生成手段>はパックごとに異なるため（「エージェント直接執筆」「既存スクリプトの流用」等）、PackDefinition側に持たせ、レビュー工程以降は `loadPackSources` が付ける。音声を1件も持たないパックには「＋TTS」を付けない。

`validatePack` に `reviewedBy`・`reviewedAt`・`reviewMethod` を任意フィールドとして追加し、記録が機械可読になるようにする。必須化はしない（既存パックの移行を止めないため）。

### 8.3 適用範囲

T-355で既存20パック全てに遡って適用する（**2026-08-13**: 適用は完了した。`pack-p2-s-003` を含む配信中の21パック全てに工程記録があり、`beb verify-content` の検査6が記録の欠落・accept以外の残存を検出する）。`verdict` が `revise` または `reject` になった問題は、ウェーブ7・8の該当タスクで修正する。

読解2パック（`pack-reading-p6-s-001`・`pack-reading-p7single-s-001`）は人手レビュー済みだが、敵対的検証は同様に実施する。人手レビューの記録は上書きしない。
