## 1. 位置づけと使い方

- [08_M1タスク分解](08_M1タスク分解.md) の残タスク（F4: T-15〜T-23、F5: T-25〜T-34、F6: T-35〜T-38）を、**AIコーディングエージェント（Sonnetクラス）が1タスク=1セッションで完遂できる粒度**に落とした作業指示書。タスクの目的・依存・完了条件の正本は 08 であり、本書は 08 に従属する（矛盾したら 08 が優先し本書を直す）。

  ```

  着手前に同書の2節（共通ルール）・3節（事前決定事項）と、シートに記載の正本参照節を必ず読むこと。
  完了時は2節の完了手順（検証・STATUS.md更新・PR作成）まで実施してください。
  ```

## 2. 全タスク共通ルール（ガードレール）

### 2.1 着手手順

1. `git fetch` し、`dev` を最新化してから `task/T-xx-説明` ブランチを切る（`feature/` は使わない）。
2. シート記載の「正本参照」の docs 節と、変更対象ファイルの現状を読む。
3. `docs/STATUS.md` のタスク別状態に着手を反映する（完了時と同じPRでよい）。

### 2.2 変更禁止の共有面（契約）— 停止条件

以下は確定済み契約（[09](09_開発体制.md) 2節）。**変更が必要だと判断した時点で作業を停止し、人間に確認する**（変更する場合は契約変更のみの単独PR）:

- `packages/shared-schema/src/` 全体（C-1）
- `packages/app/src/db/schema.ts`・`database.ts` のストア定義・フック（C-2）
- `packages/app/src/platform/` のインターフェース定義（C-3）。**実装ファイル（WebAudioPlayer.ts 等）の中身の実装はT-15等の対象で変更可**
- `packages/app/src/engine/types.ts`（C-4）

また、以下も停止条件とする:

- シートに列挙されていない**新規npm依存の追加**が必要になった場合（許可済み依存は3.6節）
- M2以降の機能（下記2.3）を実装しないと完了条件を満たせないと感じた場合（ほぼ確実に解釈誤り。シートと08を読み直し、それでも矛盾するなら停止）
- テスト・スコープを縮退しないと完了できないと判断した場合（勝手に縮退せず必ず人間に確認）

### 2.4 実装規約

- 色は必ず `tokens.css` のトークン経由（hex直書き禁止）。タップ目標48px以上・解答ボタン56px。演出は07の9節（学習中は最小、`prefers-reduced-motion` 対応）。
- UI・エンジンから `Audio` / `AudioContext` / `caches` を直接呼ばない（ESLintで遮断済み。必ず `platform/index.ts` の factory 経由）。

### 2.5 完了手順

1. ルートで `npm run build` / `npm test` / `npm run lint` が全て通ることを確認する。
2. シートの完了条件チェックリストを1項目ずつ検証する（テストで担保できない項目は `npm run dev` を起動して実際に操作して確認。Playwright等のブラウザ操作手段があれば使う）。
3. 「本来やるべきだったが省略した項目」がないか再点検する。あれば正直に報告する。

5. dev への PR をドラフトで作成する（タイトル: `Feat: <タスク名> (T-xx)`）。人間チェックポイント🟡がある場合は PR 本文に「未検証項目」として明記する。

## 3. 事前決定事項（実装方式）

Sonnetクラスが迷わないよう、docs に書かれていない実装方式をここで確定する。根拠の詳細は [ADR 0003](adr/0003-F4のUI実装方式.md)。

### 3.1 画面遷移: ルーターレス

- react-router 等は導入しない。Zustand ストアの `screen` 状態（`'home' | 'drill' | 'vocab' | 'dashboard' | 'settings' | 'diagnostic' | 'result'` 程度の判別union）で `App.tsx` が画面を切り替える。
- 理由: M1は6画面・deep-link不要・オフラインPWA。ブラウザ履歴連携（戻るボタン）はM2で必要になってから検討する。
- 画面コンポーネントは `packages/app/src/screens/` に置く（例: `HomeScreen.tsx`, `DrillScreen.tsx`）。

### 3.2 状態管理: Zustand

- `zustand` を導入する（[05](05_アーキテクチャ設計.md) の技術スタックに記載済み）。ストアは `packages/app/src/store/` に置く。
- 正本データは常に IndexedDB。Zustand は「画面状態＋DBから読んだ表示用キャッシュ」のみを持ち、解答等の書き込みは必ずサービス層（`services/`）経由で行ってからストアを更新する。

### 3.3 セッションの per-item mode 拡張（STATUS の F4引き継ぎ事項の解決）

- `SessionSnapshot.questionIds: string[]` を `items: SessionItem[]` に置き換える。`SessionItem = { questionId: string; mode: AttemptMode; srsCardId?: string; reason?: QuickPackReason }`（`QuickPackItem` から質問実体のあるものを写像）。
- `answerCurrentQuestion` は現在 item の `mode` で attempt を記録する。SRS由来 item（`srsCardId` あり）の解答時は UI 側で `reviewSrsCard` も呼ぶ。
- SessionSnapshot は進行中セッションの一時データであり、マイグレーション不要（形式が変わったら旧スナップショットは破棄してよい。`resumeSession` に形状チェックを入れ、不正・旧形式なら null を返す）。
- この変更は T-16 の最初のコミットとして `services/session.ts` とテストをまとめて行う。

### 3.4 QuickPackItem と画面の対応

- `kind: 'srsVocab'` → 語彙カードUI（S3と同型のカード）で表示。`questionId` が null のカードは refId（単語）のみで表示し、attempts には `questionId: 'vocab:<refId>'` として mode='srs' で記録する（問題別統計から `vocab:` プレフィックスで除外可能にするための規約）。
- `kind: 'srsQuestion' | 'drill'` → S2ドリルUIで表示。`reason` があれば出題理由ラベル（`engine/reason.ts` の文言）をステータス帯に出す。
- 15分パックの Part3/4 増量は J-2 で M1 対象外。quickPackConfig の現行配分のまま増量される挙動を正とする。

### 3.5 チャート: ライブラリ不使用（SVG自作）

- S6 の3チャート（折れ線1系列・横棒・ヒートマップ）は素のSVGコンポーネントとして自作する。07の8節の規定が細かく、ライブラリのデフォルト挙動を殺す工数の方が高いため。
- 系列色は `--chart-*` トークンのみ。ツールチップはタップで値表示（ホバー前提にしない）。数表ビュー（`<table>` を視覚非表示で併設 or 切替）を必ず付ける。

### 3.6 許可済み新規依存

| パッケージ | 対象 | 用途 |
|-----------|------|------|
| `zustand` | app | 状態管理（3.2） |
| `@anthropic-ai/sdk` | cli | T-26〜T-29 の問題生成（LLM呼び出し） |

これ以外が必要になったら停止して人間に確認（2.2節）。Azure TTS は SDK を使わず REST（fetch）で叩く（依存を増やさない）。

### 3.7 ダミーコンテンツ

- S-A1〜S-A4 で使う開発用ダミーパックは `packages/app/public/packs/dev/`（`pack-dev-p2-001.json` 等）に置き、**必ず C-1 スキーマに準拠**させる（`license: "internal-original"`, `origin: "開発用ダミー"` でよい）。音声はTTS前なので数百msの無音mp3をスクリプト生成して置く（`scripts/` に生成スクリプトを残す）。
- ダミーパックは T-37 の本番コンテンツ差し替え時に削除する。

### 3.8 レビューフォローアップの割当

STATUS.md のレビューフォローアップは以下のタスクに内包する: quickPackConfig 検証→T-16、ストリーク途切れ表示→T-21、CLI maskApiKey/stderr→T-26、backup dbVersion 検査→T-23（インポートUIを作るついでに実装）。

### T-15 音声再生基盤 🟡

- **正本**: 08のT-15行、05の8節、02の3.4（M1範囲）、07の6節（音声プレイヤー）
- **依存**: T-04（済）
- **変更**: `platform/audio/WebAudioPlayer.ts`（骨格→本実装）、`platform/index.ts`（PackCache注入の配線）、同テスト
- **実装指示**:
  1. `WebAudioPlayer` を Web Audio API ベースに書き換える。`unlock()` はユーザータップのハンドラ内で呼ばれる前提で、`AudioContext` の生成/`resume()` ＋無音バッファ1発再生を行う（iOS Safariの自動再生制限解除）。
  2. 音源取得はキャッシュファースト: コンストラクタに `PackCache` を注入し、`play(src)` は `packCache.get(src)` → Blob → `decodeAudioData`。キャッシュmissは `fetch(src)` にフォールバックし、取得後 `addAll` はしない（ピン留めはT-35の責務）。デコード済み `AudioBuffer` はセッション中メモリキャッシュ（Map、上限あり）。
  3. `playSequence` は `AudioBufferSourceNode` を連結スケジュール。`PlayOptions.startMs/durationMs` で部分再生（T-17の冒頭再生用）。`rate` は無視（予約のみ=J-6）。`replay()` は直近の play を再実行、`stop()` は現行ソースを停止。
  4. テスト: `AudioContext` をフェイク注入できる構造にし（既存の `AudioElementFactory` 注入パターンを踏襲）、unlock前play拒否・部分再生のオフセット計算・シーケンス順序・replay をユニットテストで検証。
- **完了条件**:
  - [ ] 上記テストが緑。build/lint通過（platform配下はESLint制限の対象外であること確認）
  - [ ] `npm run dev` でダミーmp3の再生・部分再生・連続再生がPC Chromeで動く
  - [ ] 🟡 **人間**: iOS Safari 実機で「セッション開始タップ後、連続出題中に毎問の再生タップを要求されない」（PR本文に未検証と明記し、T-36で最終確認）
- **停止条件**: `AudioPlayer` インターフェース自体の変更が必要になった場合（C-3契約）
