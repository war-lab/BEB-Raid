# 11. レビュー運用手順

コンテンツ生成パイプライン（正本: [04_データ設計](04_データ設計.md) 5節）のうち、「生成 → 人手レビュー → 取込」の1サイクルの操作手順。実装は T-30（`packages/cli/src/review.ts`・`commands.ts`）。

## 前提: ドラフトJSONLの形式

生成コマンド（`generate`。T-26〜T-29で実装）は、1行1件の「ドラフトJSONL」を出力する想定。各行は次の形（`GeneratedItemDraft`）:

```json
{"id": "v-001", "kind": "vocab_card", "preview": "submit / 提出する", "payload": { ... 実際のQuestion等 ... }}
```

- `id`: ドラフトの一意ID（採用後の `Question.id` と同じである必要はない）
- `kind`: 種別（`Question.format` 相当）
- `preview`: レビューア向けの1行要約（英文・和訳の要点など。生成コマンド側が組み立てる）
- `payload`: 実際の生成物一式（採用時はそのまま、修正時はパッチをマージして出力に含める）

## 1サイクルの手順

### ① 生成

```
beb generate ... > drafts.jsonl
```

（`generate` の実引数はT-26〜T-29で確定。ここでは「ドラフトJSONLを吐く」という出力契約のみが前提）

### ② レビュー用TSVへ書き出し

```
beb review-export drafts.jsonl review.tsv
```

`review.tsv` は次の列を持つ（スプレッドシートにそのまま貼り付けられるタブ区切り）:

| 列 | 内容 |
|---|---|
| id | ドラフトのID（書き換えない） |
| 種別 | kind（書き換えない） |
| 本文プレビュー | 1行要約（書き換えない。判断材料） |
| status(採用・修正・破棄) | レビューアが記入。**「採用」「修正」「破棄」のいずれか** |
| 修正内容 | status=修正 のときのみ、`payload` に浅くマージするJSONオブジェクトを1行で記入（例: `{"question":"直した本文"}`）。空欄なら実質「採用」と同じ扱い |
| 破棄理由 | status=破棄 のときに記入。空欄でも取込は通るが `(理由未記入)` として記録される（**理由は書く運用にする**） |

### ③ スプレッドシートで目視レビュー

- 正答の妥当性・ひっかけの質・不自然な英文の除去（04の5節）
- 既存教材（金のフレーズ等）に酷似していないか（著作権リスク。CLAUDE.md不変条件）
- status列を必ず埋める（空欄の行は「レビュー未完了」として次回に持ち越されるだけで、取込に失敗するわけではない）

### ④ レビュー済みTSVの取込

```
beb review-import drafts.jsonl review.tsv accepted.jsonl rejected.jsonl
```

- `accepted.jsonl`: 採用・修正が反映されたpayload一覧。**この時点ではまだ `beb tts` / `beb build` に渡せない**（次項⑤を参照）
- `rejected.jsonl`: 破棄された項目一覧（`id` / `kind` / `reason`）
- status未記入・`drafts.jsonl` に対応するidが無い行はどちらにも入らず、コンソールに件数だけ表示される（次サイクルにそのまま持ち越してよい）

### ⑤ acceptedをdrafts.jsonlへ反映（手作業）

`accepted.jsonl` は行ごとに裸のQuestion（`payload` の中身だけ）を並べたJSONLである。

一方 `beb tts`（`ttsBatch.ts`）と `beb build`（`loadPackSources`）はどちらも `draft.payload` を読む前提で、`{id, kind, preview, payload}` の `GeneratedItemDraft` 形を要求する。

`accepted.jsonl` をそのまま `beb tts` や `beb build` に渡すと、`payload` が存在しないためTypeErrorになるか「問題がオブジェクトではない」で止まる。

`beb build` はさらに、コマンド引数に渡したパスではなく `content/drafts/<パック定義のdraftPath>`（`packages/cli/src/build.ts` の `PACK_DEFINITIONS`）を固定で読む。

そのためビルドに反映するには、`accepted.jsonl` の内容を**元の `drafts.jsonl`（＝該当パックの `draftPath` として登録済みのファイル）へ手作業で書き戻す**必要がある。手順は次のとおり。

1. `rejected.jsonl` に載っている `id` の行を `drafts.jsonl` から削除する
2. `accepted.jsonl` の各行（`payload.id` を持つ）について、`drafts.jsonl` 側で同じ `id` を持つ行を探し、その行の `payload` を `accepted.jsonl` の内容で置き換える（`id` / `kind` / `preview` はdrafts側の値をそのまま残す）
3. status未記入でスキップされた行は `drafts.jsonl` にそのまま残し、次回のレビューサイクルに持ち越す

この手順は、**生成コマンドが `draft.id` と `payload.id` を常に同じ値にする**運用（`packages/cli/src/vocabCard.ts` 等の既存の `buildXxxDrafts` 系関数が例外なくこの形で書かれている）に依存する。`id` が食い違う生成物を扱う場合は、`id` ではなく本文の内容で対応行を確認すること。

書き戻し後、`beb build` を実行してエラーが出ないことを確認する。`validatePack` の検証がここで書き戻しミス（`payload` の構造崩れ・JSON構文エラー等）の検知を兼ねる。

`content/drafts/text-passage-p6-s.accepted.jsonl` のように `content/drafts/` 直下にコミットされた `.accepted.jsonl` / `.rejected.jsonl` は、この書き戻し作業の記録として残っているものであり、それ自体が次工程の入力になるわけではない。

本手順を自動化してビルド入力へ直接接続する再設計は行っていない（`docs/30_改修計画_全量レビュー棚卸し.md` 15節でT-241として着手を保留している）。

### ⑥ 破棄理由をプロンプト改善へ反映

`rejected.jsonl` の `reason` を定期的に見直し、同じ理由（例:「既存教材に酷似」「ひっかけが不自然」）が繰り返し出る場合は、`generate` の生成プロンプト（T-26〜T-29でリポジトリにテンプレートとして保存される想定）を調整する。

### ⑥ ビルドとコンテンツ検証（T-234で追加。配信物のCIゲート）

`accepted.jsonl` の内容を `content/drafts/*.jsonl` へ反映したら、必ず `beb build` を実行して `content/packs/*.json`・`manifest.json` を再生成してからコミットする。**`content/packs/*.json` を手で直接編集してはならない**。CI（`ci.yml`）とデプロイ（`deploy.yml`）は `beb verify-content content` で配信物を独立に再検証しており、`content/drafts/` から再ビルドした内容とハッシュが一致しないパック（drafts を経由しない直接編集）はCIが赤くなって止まる（04の5節）。

```
beb build content
beb verify-content content
```

ローカルで `beb verify-content` を通してからコミットすれば、CIで初めて不整合に気づく手戻りを避けられる。

## 既知の制約（M1時点）

- 「修正内容」列はJSON文字列の手入力が前提のため、非エンジニアのレビューアには負荷が高い。M1では発起人自身がレビューする想定でこのまま運用し、レビューUIの改善は本タスクのスコープ外（docs/06のロードマップ参照）。
- TSVの「本文プレビュー」列はタブ・改行を空白に潰して1行に収める。複数行にまたがる本文そのものは `payload` 側にしか残らないため、詳細確認は必要に応じて `drafts.jsonl` を直接参照する。

## レビューUI（M2・T-57。上記の「既知の制約」の解消）

②③④（レビュー用TSV書き出し→目視レビュー→取込）をブラウザ上のフォームUIに置き換える手段。

種別ごとのフィールド単位編集に対応するのは `vocab_card` / `audio_qa` / `text_blank` / `key_vocab_similar` の4種別のみ（`packages/review-ui/src/components/DraftForm.tsx`）。

`dictation` / `shadowing` / `audio_set` / `text_passage` は専用フォームが無く、生JSONのテキストエリアへフォールバックする。この4種別ではJSON手入力は残る。

### 起動

```
npm run review-ui
```

ブラウザで表示されたURLを開く（開発者ローカル専用。ビルド・GitHub Pagesデプロイの対象外）。

### 手順

1. 画面上部のセレクトで `content/drafts/*.jsonl` から対象ファイルを選ぶ
2. 1件ずつ表示されるフォームでフィールドを直接編集する（正答の妥当性・ひっかけの質・不自然な英文・既存教材との類似は①③と同じ観点で見る）
3. フォーム下に shared-schema のバリデーション結果がインラインで出る（エラーがあっても採用自体は止めない。取込前の目安表示）
4. 音声が紐づく種別（vocab_card の phraseAudio、audio_qa の audio）は `<audio>` プレイヤーでその場再生できる。**audio_qa で `audioMeta.responseOffsetsMs` を持つ問題（音声のみモード対応。T-152）は応答ごとの区間プレビューも出る**ので、読み上げ順と選択肢 key の対応を聞いて検品できる
5. 「採用」（編集した内容がそのまま採用＝TSV運用の「修正」相当）または「破棄」（理由必須）を選ぶ。前へ/次へで他の項目に移動でき、確定済みの項目は「取り消す」でpendingへ戻して選び直せる。全件処理し終えると「書き出す」が押せるようになる
6. 編集状態はファイル選択ごとにブラウザのlocalStorageへ自動保存される。画面をリロードしても直前の状態から再開できる（書き出しに成功すると保存分は消える）
7. 「書き出す」で `content/drafts/reviewed/<元ファイル名>.accepted.jsonl` / `.rejected.jsonl` に書き出す。出力形式は `beb review-import` の出力と同じ裸のQuestion配列であり、`beb tts` / `beb build` への反映には⑤と同じ手作業の書き戻しが要る

CLIの `review-export`/`review-import`（①〜④のTSV往復）は引き続き使用可能。どちらか一方に統一する必要はなく、レビューア・案件ごとに選んでよい。

### 運用注意: Part2の選択肢を後から編集する場合（T-152）

音声のみモード用のPart2音声は「設問＋応答A＋応答B＋応答C」を1本に連結しており、**読み上げ順は選択肢の key 昇順で音声に焼き込まれている**。

そのため TTS 実行後に選択肢のテキストを編集すると、音声と key の対応が崩れて `answer` が実質誤りになる（音声ではBが正答なのに `answer` がAのまま）。画面上は正常に見えるので気づけない。

これを防ぐため `audioMeta.responsesTextDigest` に生成時の選択肢のダイジェストを持たせており、**編集後に `beb build` を実行すると digest 不一致でビルドが止まる**（警告ではなくエラー）。

対処は該当問題の**応答音声を再生成する**こと（`beb tts` を通し直す）。ビルドを通すために digest を手で書き換えてはならない。音声と選択肢の不一致がそのまま配信される。
