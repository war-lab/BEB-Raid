# 11. レビュー運用手順

コンテンツ生成パイプライン（正本: [04_データ設計](04_データ設計.md) 5節）のうち、「生成 → 人手レビュー → 取込」の1サイクルの操作手順。実装は T-30（`packages/cli/src/review.ts`・`commands.ts`）。

## 前提: ドラフトJSONLの形式

生成コマンド（`generate`。T-26〜T-29で実装）は、1行1件の「ドラフトJSONL」を出力する想定。各行は次の形（`GeneratedItemDraft`）:

```json
{"id": "v-001", "kind": "vocab_card", "preview": "submit / 提出する", "payload": { ... 実際のQuestion等 ... }}
```

- `id`: ドラフトの一意ID（採用後の `Question.id` と同じである必要はない）
- `kind`: 種別（`Question.format` 相当）
- `preview`: レビューア向けの1行要約（英文・和訳の要点など。生成コマンド側が組み立てる）
- `payload`: 実際の生成物一式（採用時はそのまま、修正時はパッチをマージして出力に含める）

## 1サイクルの手順

### ① 生成

```
beb generate ... > drafts.jsonl
```

（`generate` の実引数はT-26〜T-29で確定。ここでは「ドラフトJSONLを吐く」という出力契約のみが前提）

### ② レビュー用TSVへ書き出し

```
beb review-export drafts.jsonl review.tsv
```

`review.tsv` は次の列を持つ（スプレッドシートにそのまま貼り付けられるタブ区切り）:

| 列 | 内容 |
|---|---|
| id | ドラフトのID（書き換えない） |
| 種別 | kind（書き換えない） |
| 本文プレビュー | 1行要約（書き換えない。判断材料） |
| status(採用・修正・破棄) | レビューアが記入。**「採用」「修正」「破棄」のいずれか** |
| 修正内容 | status=修正 のときのみ、`payload` に浅くマージするJSONオブジェクトを1行で記入（例: `{"question":"直した本文"}`）。空欄なら実質「採用」と同じ扱い |
| 破棄理由 | status=破棄 のときに記入。空欄でも取込は通るが `(理由未記入)` として記録される（**理由は書く運用にする**） |

### ③ スプレッドシートで目視レビュー

- 正答の妥当性・ひっかけの質・不自然な英文の除去（04の5節）
- 既存教材（金のフレーズ等）に酷似していないか（著作権リスク。CLAUDE.md不変条件）
- status列を必ず埋める（空欄の行は「レビュー未完了」として次回に持ち越されるだけで、取込に失敗するわけではない）

### ④ レビュー済みTSVの取込

```
beb review-import drafts.jsonl review.tsv accepted.jsonl rejected.jsonl
```

- `accepted.jsonl`: 採用・修正が反映されたpayload一覧（次工程=TTS/パックビルドへ渡す）
- `rejected.jsonl`: 破棄された項目一覧（`id` / `kind` / `reason`）
- status未記入・`drafts.jsonl` に対応するidが無い行はどちらにも入らず、コンソールに件数だけ表示される（次サイクルにそのまま持ち越してよい）

### ⑤ 破棄理由をプロンプト改善へ反映

`rejected.jsonl` の `reason` を定期的に見直し、同じ理由（例:「既存教材に酷似」「ひっかけが不自然」）が繰り返し出る場合は、`generate` の生成プロンプト（T-26〜T-29でリポジトリにテンプレートとして保存される想定）を調整する。

## 既知の制約（M1時点）

- 「修正内容」列はJSON文字列の手入力が前提のため、非エンジニアのレビューアには負荷が高い。M1では発起人自身がレビューする想定でこのまま運用し、レビューUIの改善は本タスクのスコープ外（docs/06のロードマップ参照）。
- TSVの「本文プレビュー」列はタブ・改行を空白に潰して1行に収める。複数行にまたがる本文そのものは `payload` 側にしか残らないため、詳細確認は必要に応じて `drafts.jsonl` を直接参照する。
