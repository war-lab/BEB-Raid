### 週次ボス不発（問題①）に原因仮説が立った

**Cloudflare Workers のcron式は曜日を「1=日曜〜7=土曜」と解釈する**（公式ドキュメントに明記）。したがって `wrangler.toml:62` の `crons = ["0 0 * * 1"]` は月曜ではなく**日曜0:00 UTCに発火する**。`wrangler.toml:60` のコメント「"1" = 月曜（標準cron表記。日=0〜土=6）」はCloudflareに対しては誤りである。

日曜はISO週の最終日なので、`generateWeeklyBoss` の `isoWeekInfo(now)` は終わりかけの週を返す。その週のボスは既に存在するため `stub.init` の冪等ガードでスキップされ、翌週分は生成されない。この機構は2週連続の404という観測と整合する。

**未検証（仮説）である。** 確定手順は29の付録A-1に置いた。最短は `GET /raid/summary` の照会で、2026-07-30時点の空配列から変化していれば発火が起きたことになる。修正時は `index.ts:33` の `CRON_WEEKLY_BOSS` も同時に変更しなければならない（文字列が食い違うと `scheduled()` が `default` に落ちて無音になる）。

## 2026-08-03: 週次ボスの手動生成エンドポイントを追加（問題①の手当て）

発起人の「今週レイドが生成されていないのでは」という判断を受け、**cronの原因調査と切り離して今週のレイドを成立させる経路**を用意した。`POST /admin/raid/generate` を追加した（正本: [17](../17_M3実装計画.md) 3.10節の「運用エンドポイント」）。

### なぜエンドポイントを追加したか

Cloudflareにはデプロイ済みWorkerのcronを手動発火させる手段が無い。2026-07-22の `boss-2026-W30` は一時デバッグエンドポイントで手動生成したもので、その場しのぎのコードは残っていない。今後もcron不発のたびに同じ手を打つのは無駄なので、認可付きの経路として常設した。

### 安全側の設計（既存ボスがあれば生成しない）

`generateWeeklyBoss` は③ボスDO初期化は冪等だが、**①`emaDailyDamage` の更新は冪等でない**。同じ週の実績でEMAを二度平滑化すると、翌週以降のボスHP算出が前週値へ寄る（`index.ts` の `CRON_WEEKLY_BOSS` のコメントにある事故経路と同じもの）。そのためハンドラで先に当週ボスの存在を確認し、**あれば生成処理を呼ばずに現状を返す**（`{created:false, boss}`）。

この設計により、このエンドポイントは**存在確認としても使える**。ボスがあるかどうかを確かめるために別途 deviceToken を用意する必要がない。

なお当初「生成するとHPと貢献がリセットされる」と説明したが、これは誤りだった。ボスDOの初期化は既存状態を保つため、リセットは起きない。実際の非冪等性はEMA更新にある。

## 2026-08-03: イベントバトルの音声を自動再生しない（dev直コミット）

発起人の要望で、ホスト画面（S8）の音声問題を**「次の問題へ」を押した瞬間に再生しない**形へ変えた。押した瞬間に流れると、会場の注意がまだ前問の順位表に向いている状態で1問目の応答が過ぎてしまうため、ホストが会場を見て合図を出せる1拍を挟む。

### 第2ラウンド [P1] 保存再試行の連打で解答が二重に記録される

ADR 0010 の単一トランザクション化は「**失敗した1回の書き込み**が部分的に残らない」ことしか保証せず、**成功する保存を2回走らせる操作**は射程外だった。Reading経路はsnapshotを使わないため他に歯止めがなく、attempt・レートが二重に入る。

再試行導線を `hooks/useSaveGuard.ts`（当初 `useRetrySave`）へ切り出し、同期に読めるrefで再入を弾いたうえでボタンを `disabled` にした。stateだけでは再レンダーを待たない連打に間に合わない。この区別はADR 0010 の「本ADRが保証しないこと」節に追記した。

あわせて、再試行時の `responseMs` を**初回選択時の値**に固定した（再試行時刻から計算すると、エラー表示を見てから押すまでの時間が乗り、速答判定=isGuessまで壊れる）。「次へ」の終了判定は解答スロット数から `snapshot.items.length` へ直した（到達先は同じだが、範囲外indexへ進んだ次のレンダーのフォールバックに依存していた）。

**テストの作り方に注意点がある。** 連打の再現は2回のクリックを同じ `act` 内で dispatch する必要がある——`fireEvent` を2回呼ぶと間に再レンダーが挟まって `disabled` が効いてしまい、同期ガードを通らない。

### 第3ラウンド [P1] 保存の完了を待たずに進行できた

正誤表示は保存処理より先に出るため、**保存中・保存失敗の再試行待ちでも「次へ」が押せた**。Readingは最終サブ設問でattempt未保存のままリザルトへ進み、Drillは保存失敗時にDBのsnapshotが前問のままなので、次問を解答すると `answerCurrentQuestion` が前問のIDでattemptを記録しつつタグ・レートには次問の情報を使う不整合が起きうる。

`useSaveGuard` に保存の実行中フラグ（件数管理）を持たせ、`blocked = 保存中 || 再試行待ち` の間は進行導線を描画しない形にした。対象は「次へ」「次の設問へ」「ここで終了して結果を見る」・語彙カードの自己評価で、読解は別サブ設問の解答受付も止める（未保存の再試行を捨てて解答を失うため）。**「中断」は常時有効のまま残した**——保存が恒久的に失敗する端末で操作不能にしないため。

保存の各経路の開始時に `saveError` をクリアするようにもした（進行判定に含めたため、クリア漏れの経路では失敗後に成功してもバナーが残り進行を止めっぱなしになる）。

### 第4ラウンド [P1] 複合問題のサブ設問がスナップショットから脱落する

読解・audio_setのサブ設問は `recordAttempt` で直接保存しており、スナップショットに何も残らなかった。影響は2つ。**(1)** 途中で中断すると再開後に解答済みのサブ設問が再出題され、attempt・レート・タグ統計が重複する。**(2)** 完走してもリザルトの全体集計（T-109。`snapshot.attemptIds` 基準）から漏れ、読解のみのセッションが「正解 0/0」になる。

`answerCurrentSubQuestion` を追加し、attempt追記・`attemptIds` 追加・解答済みサブ設問（`subAnswers`）の記録を同一トランザクションで行う。判断はADR 0011に記録した。
