### 1.1 ネイティブ向けビルド成果物の分離（J-74）

`packages/app/vite.config.ts` は `process.env.GITHUB_PAGES === 'true'` のときだけ `base` を `/BEB-Raid/` に切り替え、それ以外は `/` を使う。

Capacitorが読み込むのは `capacitor://localhost` 配下のローカルアセットであり、`/BEB-Raid/` を前提としたパスでは解決できない。したがってネイティブ向けには `GITHUB_PAGES` を設定しない `base='/'` のビルドが必要である。

現行の `npm run build`（`packages/app`）は `GITHUB_PAGES` 未設定なので既に `base='/'` になるが、Pagesデプロイ用ビルドと取り違えないよう**ネイティブ向けビルドスクリプトを独立して追加する**（T-133の成果物）。

### 1.2 パックキャッシュの実態（J-75）

`packages/app/src/platform/cache/CacheStoragePackCache.ts` は既にService Workerに依存しない実装で、`caches.open('beb-pack-cache-v1')` を直接呼ぶ（Workboxのprecache名前空間とは別名）。「SW非依存の `PackCache` 実装を追加する」作業は存在しない。

`PackCache.get()` が null を返したときのフォールバックは実装済みである。

- `WebAudioPlayer.loadBlob()`・`loadBuffer()`: `await this.packCache.get(src)` が null なら `fetchAudio(src)`（内部で `fetch(src)`）を呼ぶ。
- `services/packSync.ts` の `loadPackQuestions()`: `packCache.get(packUrl)` が null なら `fetchImpl(packUrl)` を呼ぶ。

パック・音声をバンドル同梱にする決定（J-82）により、この `fetch` はローカルアセットへの取得になる。よって**ネイティブでは `get()` が常に null を返す `NullPackCache` で全機能が成立する**。

残る実作業は2つである。

1. `packages/app/src/main.tsx` の `registerSW({ immediate: true })` を無条件呼び出しから、ネイティブでは呼ばない形に変える。
2. 設定画面のキャッシュ使用量表示・手動削除の扱いを決める（常に0件・無効になるため、ネイティブでは非表示にするか「同梱済み」と表示する）。

なお、WKWebViewで `caches` API が使えるかどうかは未検証のまま残る。J-82の決定によりこれは機能の前提ではなくなったが、`CacheStoragePackCache` を代替案として残すため、T-146の検証項目には含める。

### 1.3 iOS実機への導入経路（J-72）

Apple Developer Programに登録しない前提でも、無料Apple IDによる実機sideloadは可能である。経路は次のとおり。

1. GitHub Actions の macOSランナーで、**署名なしの実機向けIPA**（arm64・`CODE_SIGNING_ALLOWED=NO` 相当）をビルドしartifactとして取得する。
2. Windows上の Sideloadly または AltStore が、無料Apple IDで署名しUSB経由で実機へインストールする。

この経路によりローカル通知は無料署名でも動作するため、**M5の最大の動機であるiOSのスケジュール通知を$99を払わずに実機検証できる**。iOSストレージ退避の解消も同様に実機で確認できる。

**以下の制約は無料署名に固有のもので、一般に知られている値である（本プロジェクトでは未検証）。**

| 制約 | 内容 |
|------|------|
| プロビジョニングプロファイルの失効 | 7日で失効し、アプリが起動しなくなる。毎週の再署名・再インストールが必要 |
| 同時sideload数 | 3アプリまで |
| App IDの発行数 | 7日あたり10個まで |
| 参加者への配布 | 不可（各自が7日ごとに再署名するのは非現実的） |

**失効後の再インストールでIndexedDBのデータが保持されるかは未検証である。** 同一bundle IDの上書きインストールなら通常は保持されるが、確証はない。データ消失の解消がネイティブ化の目的である一方、検証手段の側でデータを失う危険があるため、**実機導入前に `packages/app/src/services/backup.ts` の `exportAll()`（設定画面のエクスポート）でデータを退避することを必須の前提とする**（H-10）。データ保持の確認自体もT-146の検証項目に含める。

$99の支出判断は「発起人自身が実機で使えれば十分か、参加者にも配布するか」で決まる。

### 1.4 効果測定のベースライン（J-71）

起票時にベースライン指標として挙げた「参加者のストリーク維持率」は取得手段が存在しない。共有APIが個人に紐づけて保持しているのは「ダメージ換算値＋表示名」のみ（`packages/api/src/raidBossDo.ts` の `RaidContribution` は `displayName` と `damage` の2フィールド）で、これはプライバシー境界（CLAUDE.md・05の1節）に照らして正しい設計である。

そのため**一次指標は「自分の週次学習日数」に固定する**。`packages/app/src/engine/streak.ts` の `countSrsAnswersOn()` が `attempts` を `answeredAt` の範囲と `mode==='srs'` で数えるため、過去分を遡及算出できる。

参加者側の指標は補助扱いとする。匿名集計の `RaidSummary.participantCount` はT-131（2026-07-27）で追加されたばかりで、過去週のKVレコードが存在せず前方向にしか蓄積しない。

### 1.5 通知の要件（J-76・J-83）

`packages/app/src/platform/notifications/Notifier.ts` の `ScheduledNotification` は `{id,title,body,at}` の単発型で、`at` はエポックミリ秒である。実装・参照ともにゼロであるため、J-76の「毎日同時刻に1回」は現行インターフェースでは表現できない。方式はJ-83で決める。

**通知本文には問題文・スコア・レート実値等の学習内容を含めない。** ロック画面に表示されるため、肩越しの覗き見（02の心理的安全性方針）に対して露出が大きくなる。「今日の復習n件」のような件数のみは可とする。

### 1.6 音声再生の要件（J-77）

既存 `WebAudioPlayer` が満たしている要件を実コードから割り出した確定値として下表に示す。全経路をネイティブ実装へ置き換える場合、プラグインはこれらを満たす必要がある。

| 要件 | 確定値・根拠 |
|------|-------------|
| `onPosition` の通知間隔 | 100ms（`WebAudioPlayer` の `POSITION_NOTIFY_INTERVAL_MS`）。許容は150ms以下 |
| `onPosition` の位置精度 | 誤差±100ms未満。根拠は1.6.1 |
| `rate` の範囲とピッチ | 0.7〜1.3、ピッチ保持（J-27で決定。`WebAudioPlayer` は `HTMLAudioElement.playbackRate` ＋ `preservesPitch=true` で実現） |
| `startMs` のシーク精度 | ミリ秒精度（3秒戻し・区間リピート） |
| `durationMs` の打ち切り精度 | ミリ秒精度。`DrillScreen` は `audioMeta.questionEndMs` で質問部の終端を打ち切り、**正答読み上げのリークを防いでいる**。打ち切りが遅れると答えが漏れる（`BattleHostScreen` も同じ扱い） |
| 入力の形式 | `WebAudioPlayer` は `PackCache.get()` が返す `Blob` を受け取る構造である。ネイティブ音声プラグインは通常ファイルパスを要求するが、J-82の同梱によりパス指定が可能になる |

#### 1.6.1 位置精度の根拠

シャドーイングのカラオケ式ハイライトは、パックの `timing`（単語開始位置のミリ秒配列）に対して現在位置を突き合わせる。

`content/packs/pack-shadow-s-001.json` の全30問・708区間で、隣接する単語開始位置の差を実測すると、最小192ms・中位値255ms・48.6%が250ms未満だった（最大1130ms）。

位置通知が500ms〜1秒粒度のプラグインでは、1回の通知で複数語をまたぐためハイライトが機能しない。

#### 1.6.2 聞き流し限定にできる理由

バックグラウンド再生が必要なのは、金フレ型の聞き流し周回だけである。該当箇所は `VocabScreen`（`phraseAudio` の自動再生）と `DrillScreen` の `vocab_card`（`question.phraseAudio` の自動再生）の2つで、いずれも `play(src)` を引数なしで呼び、`onPosition`・`durationMs`・`rate` を使わない。

`audioPlayer` は `packages/app/src/App.tsx` のモジュール変数として1つ生成され、各画面へpropsで渡されている。したがって**用途別の実装を注入するのは配線の変更のみで済み、`screens/`・`engine/` の改修はゼロである**。

代替案（聞き流しもWebViewのまま）に落ちて失うのは「画面ロック中の音声継続」だけで、学習機能の欠落はない。

### 1.7 Web Push先行の判断（J-85）

**iOS 16.4以降、ホーム画面に追加したPWAはWeb Pushを受け取れる。** したがって05の7節と本書が前提にしていた「iOSではスケジュール通知が使えないためネイティブ化が必要」という動機は部分的に崩れている。ローカルのスケジュール通知はWeb APIに依然存在しないが、サーバー起点のpushで代替しうる。

J-76はWeb Push＋サーバーcronを代替案として挙げて棄却している。ただしその棄却は「ネイティブ化する前提の中で通知をどう実装するか」の比較としてのみ行われたもので、**「ネイティブ化を回避する手段」としては評価していなかった**。この評価漏れがJ-85の起点である。

ネイティブ化を先に作ると、通知の効果が未検証のままCapacitor・CI・署名・再署名運用という重い仕組みを抱えることになる。これはJ-71の弱点（実測を経ずに運用を確定させる）をそのまま踏む。Web Push検証は費用と運用コストがゼロで、$99・署名・審査・7日ごとの再署名・Xcode・macOSランナーのいずれも要らない。

#### 1.7.1 受け入れる代償とリスク

1. **プライバシー境界に触れる**。push subscriptionのendpointは端末ごとの安定した識別子であり、共有APIに新しい個人紐づき識別子が増える。さらに通知本文に「今日の復習n件」を入れるにはサーバーが各人の復習件数を知る必要があり、これは不変条件（個人紐づきで共有APIに送るのはダメージ換算値＋表示名のみ）に正面から反する。したがって**通知本文は件数を含まない汎用文に限定する**（J-86・T-149の制約）。
2. **Service Workerへの変更が必要**。現在は `vite-plugin-pwa` の `generateSW`（Workbox）を使っており、pushイベントハンドラを持たせるには `injectManifest` 方式への変更等が要る。既存のPWAキャッシュ挙動への回帰リスクがある。**具体的な方式は未確定**（別途調査中）。
3. **通知が共有APIに依存する**。学習コア機能ではないため縮退設計（05の1節）としては許容範囲だが、依存が1つ増える。
4. **iOS PWAのWeb Pushは「ホーム画面に追加済み」かつ「ユーザー操作起点で権限取得」が前提**である。ブラウザタブのままでは受け取れないため、ホーム画面追加への導線が必要になる。
5. **ネイティブ化の動機のうち「ストレージ退避の解消」は残る**。ホーム画面追加のPWAはSafariタブより退避されにくく、iOS 17以降さらに改善しているとされるが、完全な解消ではない（**未検証**）。Web Pushで解決するのは通知だけである。

## 2. 設計方針（T-132でADR化する）

1. **抽象化レイヤの実証**: 本件は T-04 で用意した platform 層（AudioPlayer・PackCache）と、M2で追加した AiClient が想定どおり差し替え可能かを実地に確認する作業でもある。UI・エンジンの改修が必要になった場合、それは抽象化の失敗を意味するため、回避策を書く前に停止して設計を見直す。
2. **不変条件は変わらない**: オフライン正常系・attempts追記のみ・プライバシー境界・コンテンツの license/origin は変更しない。ネイティブ化では通知を端末内で完結させ、共有APIへ新しい送信経路を作らない。**T-149（Web Push）はこの方針の例外**であり、push購読という新しい個人紐づき情報が増える。そのためJ-86（`deviceToken` と結合しない保存）と「通知本文に学習内容を含めない」制約をプライバシー境界の維持条件として課す（1.7.1節）。
3. **Web版を落とさない**: GitHub Pages配信のPWAは継続する（J-74）。ネイティブ側の変更でWeb版のビルドやテストが壊れた状態を完了とみなさない。
4. **費用の上限**: **$0**。Apple Developer Program（$99/年）には登録しない（J-72）。支出が必要になったら停止して発起人の判断を仰ぐ。iOSビルドは GitHub Actions の macOSランナーで行う。publicリポジトリのため無償枠内で収まる想定だが、**未検証**であるためT-146で実測する。
5. **BYOKの疎通は未確定**: `packages/app/src/platform/ai/AnthropicAiClient.ts` は `https://api.anthropic.com/v1/messages` を `anthropic-dangerous-direct-browser-access: true` 付きで直接呼ぶ。`capacitor://localhost` オリジンでCORSが通るかは未検証である。通らない場合は `AiClient` 実装の差し替え（`CapacitorHttp` 利用）が必要になる可能性がある。T-146の検証項目に含める。
