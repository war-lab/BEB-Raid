### 1.1 ネイティブ向けビルド成果物の分離（J-74）

`packages/app/vite.config.ts` は `process.env.GITHUB_PAGES === 'true'` のときだけ `base` を `/BEB-Raid/` に切り替え、それ以外は `/` を使う。

Capacitorが読み込むのは `capacitor://localhost` 配下のローカルアセットであり、`/BEB-Raid/` を前提としたパスでは解決できない。したがってネイティブ向けには `GITHUB_PAGES` を設定しない `base='/'` のビルドが必要である。

現行の `npm run build`（`packages/app`）は `GITHUB_PAGES` 未設定なので既に `base='/'` になるが、Pagesデプロイ用ビルドと取り違えないよう**ネイティブ向けビルドスクリプトを独立して追加する**（T-133の成果物）。

### 1.2 パックキャッシュの実態（J-75）

`packages/app/src/platform/cache/CacheStoragePackCache.ts` は既にService Workerに依存しない実装で、`caches.open('beb-pack-cache-v1')` を直接呼ぶ（Workboxのprecache名前空間とは別名）。「SW非依存の `PackCache` 実装を追加する」作業は存在しない。

`PackCache.get()` が null を返したときのフォールバックは実装済みである。

- `WebAudioPlayer.loadBlob()`・`loadBuffer()`: `await this.packCache.get(src)` が null なら `fetchAudio(src)`（内部で `fetch(src)`）を呼ぶ。
- `services/packSync.ts` の `loadPackQuestions()`: `packCache.get(packUrl)` が null なら `fetchImpl(packUrl)` を呼ぶ。

パック・音声をバンドル同梱にする決定（J-82）により、この `fetch` はローカルアセットへの取得になる。よって**ネイティブでは `get()` が常に null を返す `NullPackCache` で全機能が成立する**。

残る実作業は2つである。

1. `packages/app/src/main.tsx` の `registerSW({ immediate: true })` を無条件呼び出しから、ネイティブでは呼ばない形に変える。
2. 設定画面のキャッシュ使用量表示・手動削除の扱いを決める（常に0件・無効になるため、ネイティブでは非表示にするか「同梱済み」と表示する）。

なお、WKWebViewで `caches` API が使えるかどうかは未検証のまま残る。J-82の決定によりこれは機能の前提ではなくなったが、`CacheStoragePackCache` を代替案として残すため、T-146の検証項目には含める。

### 1.3 iOS実機への導入経路（J-72）

Apple Developer Programに登録しない前提でも、無料Apple IDによる実機sideloadは可能である。経路は次のとおり。

1. GitHub Actions の macOSランナーで、**署名なしの実機向けIPA**（arm64・`CODE_SIGNING_ALLOWED=NO` 相当）をビルドしartifactとして取得する。
2. Windows上の Sideloadly または AltStore が、無料Apple IDで署名しUSB経由で実機へインストールする。

この経路によりローカル通知は無料署名でも動作するため、**M5の最大の動機であるiOSのスケジュール通知を$99を払わずに実機検証できる**。iOSストレージ退避の解消も同様に実機で確認できる。

**以下の制約は無料署名に固有のもので、一般に知られている値である（本プロジェクトでは未検証）。**

| 制約 | 内容 |
|------|------|
| プロビジョニングプロファイルの失効 | 7日で失効し、アプリが起動しなくなる。毎週の再署名・再インストールが必要 |
| 同時sideload数 | 3アプリまで |
| App IDの発行数 | 7日あたり10個まで |
| 参加者への配布 | 不可（各自が7日ごとに再署名するのは非現実的） |

**失効後の再インストールでIndexedDBのデータが保持されるかは未検証である。** 同一bundle IDの上書きインストールなら通常は保持されるが、確証はない。データ消失の解消がネイティブ化の目的である一方、検証手段の側でデータを失う危険があるため、**実機導入前に `packages/app/src/services/backup.ts` の `exportAll()`（設定画面のエクスポート）でデータを退避することを必須の前提とする**（H-10）。データ保持の確認自体もT-146の検証項目に含める。

$99の支出判断は「発起人自身が実機で使えれば十分か、参加者にも配布するか」で決まる。

### 1.4 効果測定のベースライン（J-71）

起票時にベースライン指標として挙げた「参加者のストリーク維持率」は取得手段が存在しない。共有APIが個人に紐づけて保持しているのは「ダメージ換算値＋表示名」のみ（`packages/api/src/raidBossDo.ts` の `RaidContribution` は `displayName` と `damage` の2フィールド）で、これはプライバシー境界（CLAUDE.md・05の1節）に照らして正しい設計である。

そのため**一次指標は「自分の週次学習日数」に固定する**。`packages/app/src/engine/streak.ts` の `countSrsAnswersOn()` が `attempts` を `answeredAt` の範囲と `mode==='srs'` で数えるため、過去分を遡及算出できる。

参加者側の指標は補助扱いとする。匿名集計の `RaidSummary.participantCount` はT-131（2026-07-27）で追加されたばかりで、過去週のKVレコードが存在せず前方向にしか蓄積しない。

#### 1.4.1 算出式と、事前収集が不要である帰結

一次指標の定義を次のとおり固定する。ストリーク成立条件と揃えることで、指標と体感が食い違わないようにする。

```
週次学習日数(週W) = |{ d ∈ W : countSrsAnswersOn(db, d) >= STREAK_REQUIRED_SRS_ANSWERS }|
```

`STREAK_REQUIRED_SRS_ANSWERS` は `packages/app/src/engine/streak.ts` で `5` として定義されている（同ファイル17行目。ストリーク判定にも同じ定数が使われている）。

副指標として `>= 1` の日数も併記する。アプリを開いたが5問に届かなかった日を拾い、「開く回数は増えたが完走しなかった」という状態を見落とさないため。

**この算出は端末内で完結し、サーバー送信を要しない。** また `attempts` は追記のみで削除できない（`packages/app/src/db/` のDexieフックが実行時に削除を遮断する。CLAUDE.mdの不変条件）ため、**測定機構を事前に仕込む必要がなく、過去分を後から算出できる**。

したがってT-132の「ベースライン収集」は、数値をあらかじめ集める作業ではなく、**判定基準（何がどれだけ改善したら成功とみなすか）を先に明文化する作業**に縮小する。数値そのものは判定時点で遡及算出する。

専用の測定UIも必須ではない。`packages/app/src/screens/DashboardScreen.tsx` が既に `db.attempts.where('answeredAt').aboveOrEqual(...)` による日別集計と `engine/heatmapCells.ts` の `buildHeatmapCells()` でのグリッド化を持っており、これを再利用できる。コンソールから1回クエリを実行するだけでも測定は成立する。

### 1.5 通知の要件（J-76・J-83）

`packages/app/src/platform/notifications/Notifier.ts` の `ScheduledNotification` は `{id,title,body,at}` の単発型で、`at` はエポックミリ秒である。実装・参照ともにゼロであるため、J-76の「毎日同時刻に1回」は現行インターフェースでは表現できない。方式はJ-83で決める。

**通知本文には問題文・スコア・レート実値等の学習内容を含めない。** ロック画面に表示されるため、肩越しの覗き見（02の心理的安全性方針）に対して露出が大きくなる。「今日の復習n件」のような件数のみは可とする。

### 1.6 音声再生の要件（J-77）

既存 `WebAudioPlayer` が満たしている要件を実コードから割り出した確定値として下表に示す。全経路をネイティブ実装へ置き換える場合、プラグインはこれらを満たす必要がある。

| 要件 | 確定値・根拠 |
|------|-------------|
| `onPosition` の通知間隔 | 100ms（`WebAudioPlayer` の `POSITION_NOTIFY_INTERVAL_MS`）。許容は150ms以下 |
| `onPosition` の位置精度 | 誤差±100ms未満。根拠は1.6.1 |
| `rate` の範囲とピッチ | 0.7〜1.3、ピッチ保持（J-27で決定。`WebAudioPlayer` は `HTMLAudioElement.playbackRate` ＋ `preservesPitch=true` で実現） |
| `startMs` のシーク精度 | ミリ秒精度（3秒戻し・区間リピート） |
| `durationMs` の打ち切り精度 | ミリ秒精度。`DrillScreen` は `audioMeta.questionEndMs` で質問部の終端を打ち切り、**正答読み上げのリークを防いでいる**。打ち切りが遅れると答えが漏れる（`BattleHostScreen` も同じ扱い） |
| 入力の形式 | `WebAudioPlayer` は `PackCache.get()` が返す `Blob` を受け取る構造である。ネイティブ音声プラグインは通常ファイルパスを要求するが、J-82の同梱によりパス指定が可能になる |

#### 1.6.1 位置精度の根拠

シャドーイングのカラオケ式ハイライトは、パックの `timing`（単語開始位置のミリ秒配列）に対して現在位置を突き合わせる。

`content/packs/pack-shadow-s-001.json` の全30問・708区間で、隣接する単語開始位置の差を実測すると、最小192ms・中位値255ms・48.6%が250ms未満だった（最大1130ms）。

位置通知が500ms〜1秒粒度のプラグインでは、1回の通知で複数語をまたぐためハイライトが機能しない。

#### 1.6.2 聞き流し限定にできる理由

バックグラウンド再生が必要なのは、金フレ型の聞き流し周回だけである。該当箇所は `VocabScreen`（`phraseAudio` の自動再生）と `DrillScreen` の `vocab_card`（`question.phraseAudio` の自動再生）の2つで、いずれも `play(src)` を引数なしで呼び、`onPosition`・`durationMs`・`rate` を使わない。

`audioPlayer` は `packages/app/src/App.tsx` のモジュール変数として1つ生成され、各画面へpropsで渡されている。したがって**用途別の実装を注入するのは配線の変更のみで済み、`screens/`・`engine/` の改修はゼロである**。

代替案（聞き流しもWebViewのまま）に落ちて失うのは「画面ロック中の音声継続」だけで、学習機能の欠落はない。

### 1.7 Web Push先行の判断（J-85）

**iOS 16.4以降、ホーム画面に追加したPWAはWeb Pushを受け取れる。** したがって05の7節と本書が前提にしていた「iOSではスケジュール通知が使えないためネイティブ化が必要」という動機は部分的に崩れている。ローカルのスケジュール通知はWeb APIに依然存在しないが、サーバー起点のpushで代替しうる。

J-76はWeb Push＋サーバーcronを代替案として挙げて棄却している。ただしその棄却は「ネイティブ化する前提の中で通知をどう実装するか」の比較としてのみ行われたもので、**「ネイティブ化を回避する手段」としては評価していなかった**。この評価漏れがJ-85の起点である。

ネイティブ化を先に作ると、通知の効果が未検証のままCapacitor・CI・署名・再署名運用という重い仕組みを抱えることになる。これはJ-71の弱点（実測を経ずに運用を確定させる）をそのまま踏む。Web Push検証は費用と運用コストがゼロで、$99・署名・審査・7日ごとの再署名・Xcode・macOSランナーのいずれも要らない。

#### 1.7.1 受け入れる代償とリスク

1. **プライバシー境界に触れる**。push subscriptionのendpointは端末ごとの安定した識別子であり、共有APIに新しい個人紐づき識別子が増える。さらに通知本文に「今日の復習n件」を入れるにはサーバーが各人の復習件数を知る必要があり、これは不変条件（個人紐づきで共有APIに送るのはダメージ換算値＋表示名のみ）に正面から反する。したがって**通知本文は件数を含まない汎用文に限定する**（J-86・T-149の制約）。
2. **Service Workerへの変更が必要**。現在は `vite-plugin-pwa` の `generateSW`（Workbox）を使っており、pushイベントハンドラを持たせるには `injectManifest` 方式への変更が要る。既存のPWAキャッシュ挙動への回帰リスクがある（1.7.2節のS6）。
3. **通知が共有APIに依存する**。学習コア機能ではないため縮退設計（05の1節）としては許容範囲だが、依存が1つ増える。
4. **iOS PWAのWeb Pushは「ホーム画面に追加済み」かつ「ユーザー操作起点で権限取得」が前提**である。ブラウザタブのままでは受け取れないため、ホーム画面追加への導線が必要になる（1.7.4節）。
5. **ネイティブ化の動機のうち「ストレージ退避の解消」は残る**。ホーム画面追加のPWAはSafariタブより退避されにくく、iOS 17以降さらに改善しているとされるが、完全な解消ではない（**未検証**）。Web Pushで解決するのは通知だけである。

##### 暗号処理と依存ライブラリ

**Web Pushの暗号処理はCloudflare Workers上で完結する。** Cloudflare公式のWeb Cryptoドキュメントの対応表で、VAPID JWTのECDSA P-256署名、RFC 8291のECDH P-256 `deriveBits`、HKDF-SHA256、AES-128-GCM のいずれも対応が確認できる。

ただし鍵フォーマット（`raw` の65バイト非圧縮点・`jwk`）のインポート可否は同ドキュメントに明記がなく**未検証**である。実装時に `wrangler dev --local` でスモークテストを行う。

ライブラリは純WebCrypto実装（`@pushforge/builder` 等）を使う。Node製の `web-push` は `crypto.createECDH` 不在に関する未クローズのissueがあるため避ける。

#### 1.7.3 プライバシー境界の扱い（J-86）

push subscription（`endpoint`・`p256dh`・`auth`）は端末ごとの安定した識別子であり、不変条件の文面（個人紐づきで共有APIに送るのはダメージ換算値＋表示名のみ）には収まっていない。

ただし `endpoint` は正誤詳細・レート実値・本名・社名のいずれでもないため、即座に却下すべきものではない。**不変条件の文面を拡張する判断が必要**であり、これはJ-86の判断材料である。

採る手段は、既存の `questionStats` が採っているものと同じ構造的分離である。`packages/api/src/index.ts` はroute側で `handlePostStats(request, env)` を呼び、`auth.deviceToken` を渡していない（他のハンドラには渡している）。`packages/api/src/statsDo.ts` は `question_stats` 表にdeviceToken列を持たせず、その意図をファイル冒頭のコメントに明記している。購読の保存にも同じ構造を適用する。

**ただし完全な非結合は達成できない。** 同一IPかつ近接時刻での相関は可能であり、KVレコードの `createdAt` やCloudflareのログが手がかりになる。したがって到達すべき水準は「構造的に結合できない」ではなく「**結合するコードを書いていない**」である。この差をそのまま文書とコードコメントに書き、強い保証と誤認させない。

#### 1.7.4 iOS PWAの前提とスコープ

iOS PWAでWeb Pushを受け取るための前提は次のとおり。

- **ホーム画面追加が必須**（通常のSafariタブでは `PushManager` が露出しない。iOS 16.4）。導線は `packages/app/src/pwa/InstallHint.tsx` に既にあるため**追加不要**である。
- **権限要求はユーザー操作起点が必須**。`useEffect` からの `requestPermission()` は使えない。
- `subscribe({ userVisibleOnly: true })` が必須。

通知許可の導線は **`packages/app/src/screens/SettingsScreen.tsx` に「学習リマインド通知」セクションを新設し、トグルのタップを権限要求のトリガーにする**。`InstallHint` に相乗りさせることはできない。`InstallHint` はホーム画面追加**前**に出るバナーで、その時点では `PushManager` が使えずiOSでは確実に失敗する。

既存の `packages/app/src/platform/notifications/Notifier.ts` は流用しない。同ファイルの `Notifier` は `requestPermission`・`schedule`・`cancel` を持つローカル通知前提のインターフェースで、`schedule()` はWebでは実装できない。流用すると実装不能なメソッドを持つ嘘のインターフェースになるため、`requestPermission` と `subscribe` を持つ別インターフェース（例: `PushSubscriber`）を追加する。

**配信対象は発起人1台でよい。** 目的は発起人1人の学習日数が通知で増えるかを見ることなので、20人配信・購読管理UI・通知時刻のカスタマイズは効果確認後に回す。

スコープから外すもの。

- **通知本文への件数差し込み**。S2により確度が低いことに加え、「件数の効果」と「通知そのものの効果」を切り分けられなくなり測定を交絡させる。
- Declarative Web Push、複数種別の通知、購読失効の自動再購読。

#### 1.7.5 J-76の却下理由の不成立

docs/05の7節およびJ-76が挙げた却下理由「Web Push＋サーバーcronはサーバーレス方針と衝突する」は、**現在は成立していない**。

M3で Cloudflare Workers + KV + Durable Objects と週次cronが既に本番稼働している（`packages/api/wrangler.toml` の `[triggers] crons = ["0 0 * * 1"]`、`.github/workflows/api-deploy.yml`）。日次cronの追加はゼロからサーバーを立てる話ではない。

docs/05の7節の改訂は影響範囲が広いため本書では行わず、9節の残課題に含める（同じ残課題として既に立っている前提記述の更新と一体で扱う）。

### 1.8 効果検証を2段構えにする判断（J-87）

検証を次の2段に分ける。第2段は第1段の結果次第で実施しない。

| 段 | 内容 | 実装量 | 期間 | 検証する仮説 |
|----|------|--------|------|-------------|
| 第1段（H-12） | 発起人がiPhone標準のリマインダーまたはアラームを毎朝セットして運用する | **コード0行** | 2週間 | リマインドされると学習日数が増えるか |
| 第2段（T-149） | Web Pushを実装し、日次cronで配信する | 新規7ファイル・変更9ファイル規模（Service Workerの方式移行を含む） | 実装後に別途 | Web Pushという配送手段で第1段と同等以上の効果が出るか |

#### 1.8.1 この順序にする根拠

**負の結果が解釈できるのは第1段だけである。これが第1段を先に置く最大の理由である。**

Web Pushでは、AppleがiOS PWAへの配送タイミングを保証していないため（1.7.2節のS1。一次情報を確認できておらず未検証）、「学習日数が増えなかった」という結果が効果の不在なのか未到達なのかを切り分けられない。自分でセットしたアラームは到達が確実なので、増えなかったという結果もそのまま解釈できる。

残る根拠は3つある。

1. 検証したい仮説は「リマインドが学習日数を増やすか」であり、**配送手段がWeb Pushかネイティブのローカル通知かは仮説の本質ではない**。手段に投資する前に仮説そのものを検証できる。
2. **測定は遡及的に可能である**。`attempts` は追記のみで削除できないため、週次学習日数は過去分を後から算出できる（1.4.1節）。測定機構を事前に仕込む必要がない。
3. Web Push実装の作業量が想定より大きい（新規7ファイル・変更9ファイル規模。Service Workerの方式移行を含む）。仮説が否定されるなら丸ごと不要になる。

#### 1.8.2 第1段の限界

第1段は**方向性を見るための検証**であり、効果の大きさを測るものではない。以下の限界がある。

- 自分でセットしたアラームには「通知から1タップでアプリを開く」導線がない。実アプリの通知より効果が弱い可能性がある。
- 自分でセットした通知と外から来る通知では、慣れ方・無視のしかたが異なる可能性がある。
- n=1であり統計的な有意性は主張できない。交絡（季節性・繁忙期・自作バイアス・M4や読解の同時期改修）が残る。

したがって第1段で効果が出た場合も、その大きさをもってWeb Pushの効果を予測することはしない。判断に使うのは方向（増えたか・変わらなかったか）に限る。

## 2. 設計方針（T-132でADR化する）

1. **抽象化レイヤの実証**: 本件は T-04 で用意した platform 層（AudioPlayer・PackCache）と、M2で追加した AiClient が想定どおり差し替え可能かを実地に確認する作業でもある。UI・エンジンの改修が必要になった場合、それは抽象化の失敗を意味するため、回避策を書く前に停止して設計を見直す。
2. **不変条件は変わらない**: オフライン正常系・attempts追記のみ・プライバシー境界・コンテンツの license/origin は変更しない。ネイティブ化では通知を端末内で完結させ、共有APIへ新しい送信経路を作らない。**T-149（Web Push）はこの方針の例外**であり、push購読という新しい個人紐づき情報が増える。そのためJ-86（`deviceToken` と結合しない保存）と「通知本文に学習内容を含めない」制約をプライバシー境界の維持条件として課す（1.7.1節）。
3. **Web版を落とさない**: GitHub Pages配信のPWAは継続する（J-74）。ネイティブ側の変更でWeb版のビルドやテストが壊れた状態を完了とみなさない。

## 4. 全タスク共通ルール

[22の2節](22_M4実装計画.md)（上流は 17・13・10 の2節）を継承する。本書での差分は以下のとおり。

### 4.1 ブランチ運用

`task/T-1xx-説明` ブランチを dev から切り、dev へドラフトPRを出す。dev直コミットはしない。

worktreeで作業する場合、**worktree直下で `npm ci` を実行してから始める**（T-123で、worktree直下に node_modules が無いとNode解決が親ディレクトリのnode_modulesへ抜け、メインチェックアウト側のdistを参照してビルドが誤って壊れる事象を確認済み）。

### 4.2 新規依存の方針

本書は例外的に**新規依存の追加を伴う**。

- ネイティブ化タスク（T-146・T-133〜T-137）: `@capacitor/core`・`@capacitor/cli`・`@capacitor/ios`・`@capacitor/local-notifications`・音声プラグイン。
- T-149: Web Pushの送信に必要な最小限のもの（VAPID署名等）。`packages/api` は Cloudflare Workers 上で動くため、Node専用APIに依存するライブラリは使えない。**純WebCrypto実装（`@pushforge/builder` 等）を使い、Node製の `web-push` は避ける**（`crypto.createECDH` 不在に関する未クローズのissueがあるため。1.7.2節）。

H-12（第1段）は依存を一切追加しない。アプリ側の変更もない。

追加してよいのは上記の範囲に限る。これ以外が必要になったら停止して確認する。有償プラグイン・有償サービスは対象外である（設計方針4）。

### 4.3 回帰確認（毎タスク）

1. Web版のビルド（`npm run build`）とテスト（`npm test`）が通ること。
2. `VITE_RAID_API_BASE_URL` 未設定（API無効）のとき、ソロ学習の動作・表示が一切変わらないこと。
3. 端末外へ出るデータが増えていないこと。ネイティブ化タスクでは通知を端末内で完結させる。T-149のみ例外で、push購読情報が増える（J-86の制約下に限る）。

### 4.4 停止規則

- UI・エンジン（`screens/`・`engine/`）の改修が必要になったとき（抽象化レイヤの失敗を意味するため。設計方針1）。T-147は例外で、`App.tsx` の `loadQuestionPool` の変更を含む。
- 音声プラグインが1.6節の要件表を満たさないとき（J-77）。聞き流し経路（1.6.2）に限れば要件は `play(src)` のみなので、要件不足はJ-77の推奨案では停止事由にならない。
- 支出が必要になったとき（設計方針4）。
- 完了条件を1つでも満たせないとき（条件を緩めず報告する）。
