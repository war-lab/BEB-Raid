## 1. 結論

昼バトルの最終リザルトが素のリストであるという指摘は、単発の実装漏れではなく**構造的な取り残し**である。20のV-1〜V-8は2026-07-22に完了したが、昼バトル（S7・S8）とゴースト関連の画面は2026-07-27にM4で新設されたため、刷新の対象に一度も入っていない。

現物確認の結果、未適用の箇所は以下の4群である。

1. **昼バトル（S7参加・S8ホスト）**: 専用CSSは `.battle-room-code-input` と `.battle-lobby-hint` の2クラスしかない。順位表・最終リザルト・表彰は `.raid-list`（`list-style: none` のみ）で組まれている。加えて**07の7節がS8に規定した「別テーマ・特大タイポ・外周リングのカウントダウン」「4択の色＋形の二重符号化」が未実装**で、これは表層ではなく規定の未実装にあたる。
2. **ゴースト関連**: `GhostBossResultScreen`（記録プレビュー）とRaidScreenのゴースト弱点マップ・討伐された回数・貢献ダメージリスト・バッジが素の `<p>` と `.raid-list` のまま。加えて**空状態の設計が無く、貢献者0人のときに「貢献ダメージ」の見出しだけが浮く**（実画面で確認済み。2.1.1節）。
3. **成長ランク（S6）**: `.dashboard-growth-rank` はフラットな `--surface` 面で、07の3.5節が規定するランク色と段数刻みの二重符号化が未実装。`--rank-platinum` / `--rank-master` / `--rank-gold` トークンは定義済みだが**どこからも参照されていない**。
4. **20の適用漏れ**: `--bg-grad` トークンはV-1で定義されたが**適用箇所が0件**（20の3.1節は「ScreenLayoutの地に適用」と規定）。ホームの `.home-grid`（昼バトルへの入口を含む）は素のボタンのまま。

一方で、**装飾が少ないこと自体が正しい画面もある**。07の原則3（静かな学習、騒がしい報酬）により、問題を解いている最中・音声を聴いている最中の領域は演出を持たないことが設計上の要件で、飾ると設計を壊す。「ワイヤーフレームのまま」と「意図して静か」の切り分けは2.2.1節で明示し、本書のタスクは前者だけを対象にする。

方向性の主眼は、02の6.2節が求める「最下位でもスポットライトが当たる余地」を視覚で成立させることにある。ただし演出の強度・ホスト画面の地色・4択マーカーの扱いは好みと投影環境に依存するため、独断で確定せず判断事項JV-4〜JV-9として発起人の承認に回す。

## 2. 現状診断（2026-07-27。現物のコード・CSSの読み取りによる静的確認）

### 2.1 診断の方法と限界

20の1節はdev環境の実ブラウザのスクリーンショット全画面確認を方法としたが、本書は**現物のソースコードとCSSの読み取りによる静的確認**で判定した。判定根拠は「専用クラスの有無」「そのクラスがトークン経由で装飾しているか」「素のHTML要素と汎用クラスだけで組まれているか」の3点で、根拠のファイルパスとクラス名を2.3節の表に併記する。

限界（省略しない）:

- **本書の判定そのものは静的確認による**。昼バトルの3画面は `screenshot-tour.mjs` の巡回範囲外で（2.5節）、WebSocket接続とルーム作成を要するため同スクリプト単独では撮れない。
- 追加時期は `git log --diff-filter=A` で確認したが、これは**ファイル新設時点**であり、その後の改修で刷新を受けた可能性は別途CSSで確認した。
- ただし**一部は実画面のスクリーンショットで裏付けが取れている**（下記2.1.1）。裏付けの無い画面（読解・成長ランク・ゴースト記録プレビュー）については、コードとCSSからの判定は確実だが**実機での印象の程度は未検証**である。

### 2.2 ワイヤーフレーム度の判定基準

| 段階 | 定義 |
|---|---|
| 素のまま | 専用クラスが無い、または `list-style: none` 程度で装飾を持たない。階層・強調が罫線と既定のフォントサイズだけで表現されている |
| 部分的 | 一部に専用クラス・トークン参照があるが、20の深度システム（`--surface-grad`・限定光暈）やディスプレイ書体の適用が及んでいない箇所が同一画面内に残る |

### 2.2.1 「ワイヤーフレームのまま」と「意図して静か」の切り分け

07の原則3（静かな学習、騒がしい報酬）と02の2.2節（満員電車での片手操作）により、**学習中の画面は演出を持たないことが設計上の要件**である。装飾が少ないことをそのまま欠陥と読み替えると設計を壊す。両者は以下の基準で切り分ける。

| 判定 | 基準 | 該当 |
|---|---|---|
| **意図して静か**（飾ってはいけない） | 利用者が問題を解いている最中・音声を聴いている最中の領域。演出を足すと集中を削り、バッテリーを消費し、車内で目立つ | ドリルの解答中（`DrillScreen` の選択肢・問題文・タイマー）、読解のパッセージ読解中（`ReadingScreen`・`PassageText`）、シャドーイングの発話中（`ShadowingScreen`・`KaraokeScript`）、語彙カードの仕分け中（`VocabScreen`）、昼バトルの出題中（`BattleScreen` の `question` フェーズ） |
| **ワイヤーフレームのまま**（直す対象） | 区切り・報酬・確認の画面、あるいは情報伝達の要件（二重符号化・階層）が欠けている箇所。演出または階層付けを置くべき場所に何も無い | 昼バトルの途中順位・最終リザルト・表彰、ゴーストのレイド画面の貢献リスト・弱点マップ・バッジ、成長ランク、昼バトルの待機系（ルームコード入力・ロビー）、ホームの `.home-grid` |
| **静かでよいが階層は要る**（最小限だけ直す） | 学習中の画面でも、面の階層・英字ラベル程度の統一は集中を妨げない。ただしアニメーション・光暈は足さない | 読解のパッセージ面（`--surface-grad` と英字パートタグまで）、シャドーイングの面、`CompletionCard`、`ErrorBoundary` |

**判定の帰結**: ドリルの解答中・読解中・シャドーイング中・語彙仕分け中・昼バトルの出題中には**新しいアニメーション・光暈・背景演出を一切追加しない**。既存の正誤フィードバック（枠色＋✓✕・レイアウト不動）も変更しない。これは6.3節の完了条件（V-19・V-12）で機械的に担保する。

### 2.4 なぜ漏れたか

- **昼バトル・ゴーストの3画面**: V-1〜V-8完了（2026-07-22）の5日後に新設された。20の3.4節の画面別適用表はS1・S2・リザルト・診断・S9・S6・S3の7行しか持たず、S7・S8の行が存在しない。M4の実装計画（22）にも表層の指定は無い。
- **成長ランク**: M4のT-130で追加された。`components.css` の当該コメントは「既存カード面言語の範囲。光暈・新規アニメーションは追加しない」と明記しており、**意図的に控えめにした結果**である。ただし07の3.5節が規定するランク色と段数刻みの二重符号化は表層の装飾ではなく情報伝達の要件なので、未実装のまま残すべきものではない。
- **ReadingScreen・ShadowingScreen**: V-3〜V-6の作業範囲（S1・S2・リザルト・診断・S9・S6・S3）に該当する行が無い。ReadingScreenは20のV-7完了の前日に追加されたが、V-7の目視確認リストにも入っていない（20の5節「目視確認した画面」に読解の記載なし）。
- **`--bg-grad`・`.home-grid`**: V-1でトークンだけ作られ、適用担当タスクが割り当てられなかった。`.home-grid` はV-3のコード内コメントが「モックアップにも無い既存機能で構造は変えない」と明記しており、構造を変えない判断は妥当だが**面の意匠まで据え置く必然性は無い**。

### 2.5 スクリーンショット採取スクリプトの到達範囲

`packages/app/scripts/screenshot-tour.mjs` は現存し、モバイル実寸（390×844・DPR2）・両テーマで動作する（`--light` で切替）。ただし巡回するのは以下の8枚のみで、**本書が扱う画面は1つも撮れない**。

到達する画面: 初回起動・ホーム・語彙SRS・ダッシュボード・シャドーイング・設定・ドリル・ドリル正誤フィードバック。

到達しない画面と理由:

| 画面 | 理由 |
|---|---|
| S7 昼バトル参加・S8 昼バトルホスト | ホームの `.home-grid` の入口が `raidApi.isConfigured()` 真のときだけ表示され、さらにWebSocket接続とルーム作成が必要。順位・リザルトはサーバーからの `standings`/`result` メッセージ受信が前提 |
| S5 レイド（ゴースト弱点マップ含む） | 共有APIのシーズンデータと登録済みdeviceTokenが必要 |
| リザルト・ゴースト記録プレビュー | セッション完走が必要（20のV-7も同じ理由で見送っている） |
| 読解 | ドリル内の遷移（`DrillScreen` の `navigate('reading')`）経由で、読解パックがキャッシュ済みである必要がある |

## 3. 優先度と判断基準

### 3.1 判断基準

以下の5点を評価軸とする。上の軸を優先する。

1. **07の原則3（静かな学習・騒がしい報酬）に照らして、演出を置くべき場所か**。区切り・報酬の瞬間なら投資する。学習中の画面（解答中・パッセージ読解中）は**逆に飾ってはいけない**ので、素であること自体が正しい。

4. **第一印象への影響**。新規参加者が最初に触る導線か。
5. **直すコストと崩すリスク**。共有セレクタ（`tokens.css`・`components.css` の共有クラス）に触るものはリスクが上がる。

## 4. ビジュアル方向性

### 4.1 昼バトルの順位表（S7・S8共通の基盤）

現状は `<li>{displayName}: {totalPoints}点</li>` で、順位が読み取れない。以下の構造にする。

```
┌──────────────────────────────────────┐
│ STANDINGS                    ← --ev-blue 英字ラベル
│──────────────────────────────────────│
│ ┌──┐                                 │
│ │ 1│  さとう              1,240 pt   │ ← 1位: --gold 枠・順位バッジ金
│ └──┘  ▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔        │ ← 得点バー（1位=100%基準の相対長）
│ ┌──┐                                 │
│ │ 2│  たなか              1,080 pt   │ ← 2位: --rank-silver
│ └──┘  ▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔           │
│ ┌──┐                                 │
│ │ 3│  すずき                960 pt   │ ← 3位: --rank-bronze
│ └──┘  ▔▔▔▔▔▔▔▔▔▔▔▔▔             │
│ ┌──┐                                 │
│ │ 4│  やまだ ★YOU           820 pt   │ ← 自分の行は --ev-blue の左罫線＋「YOU」
│ └──┘  ▔▔▔▔▔▔▔▔▔▔▔               │
└──────────────────────────────────────┘
```

- 順位は**数字バッジ（形）＋色**の二重符号化にする。色だけで1〜3位を区別しない（原則4）。
- 得点はディスプレイ書体（`--font-display`）＋`tabular-nums`。得点バーの長さは1位を基準にした相対比で、数値も併記する（バーだけに頼らない）。
- 自分の行の識別は参加者画面（S7）でのみ有効。ホスト画面（S8）はホストが解答しないため自分の行が存在しない。
- 途中順位（`standings` フェーズ）と最終リザルト（`result` フェーズ）で**同じコンポーネントを使い、最終リザルトだけ表彰の追加要素を載せる**。途中順位に表彰演出を持ち込むと区切り感が薄れる。

実装は `components/StandingsList.tsx` を新設し、S7・S8の両方から使う。ホスト側のサイズ差は親クラス（例 `.battle-host` 配下）で上書きする方針にして、コンポーネントは分岐を持たない。

**方向性の骨格**（強度はJV-4で確定する）:

│ FINAL RESULT                 ← --ev-blue 英字ラベル・letter-spacing広め
│                                      │

- **ベストグロース賞は表彰台とは別枠の独立カード**にする。02の6.2節の「最下位でもスポットライトが当たる余地」は、順位と別の軸で表彰することで成立する。順位表の中に埋めると軸が混ざって効果が消える。
- 得点のカウントアップはソロの `ResultScreen`（`POINTS_COUNTUP_MS = 700`）と同じ実装パターンを使い、演出時間は07の9節の報酬演出の範囲（600〜900ms）に収める。

- **光暈の扱い**: 1位の得点数字に `--glow-gold` を使うと、20の3.1節が定めた「光暈の適用は金CTA・ボスHPバー・ダメージトースト・リザルト数字の4箇所限定」の解釈拡張になる。「リザルト数字」に昼バトルのリザルトを含めるかはJV-4の帰結として明記し、含める場合は20の3.1節と07への追記を伴う。

### 4.6 ゴーストレイドとレイド画面（S5）

- **貢献ダメージリスト**: 4.1の順位表と同じ構造を流用する（貢献量のバー＋数値＋自分の行の識別）。ただし**正答率は表示しない**（07の7節S5・プライバシー境界）。表示するのはハンディ換算ダメージのみで、現状の情報量を変えない。
- **ゴースト弱点マップ**: 実画面（2.1.1節）で9行の素のテキストリストであることを確認済み。07の8節は弱点マップに「弱い順にソートした横棒」を規定しているが、これは**自分の弱点スコアのマップ**（S6と共通）を指しており、ゴーストのボス防御パターンは別の概念である。したがって横棒化の規定が直接当てはまるかは**未検証**として扱い、方向性は「倍率をチップで、問数を横棒で示す」に留める。07の8節の「レイド画面ではボス防御パターンとの対応をチップで併記」に沿う。

```

┌────────────────────────────────────────┐
│ ×2.0  Part5 ビジネス名詞   ▔▔▔▔▔▔▔  8問 │ ← 倍率チップ --ok・問数を横棒
│ ×2.0  Part2 依頼と提案     ▔▔▔▔      5問 │
│ ×0.5  Part5 時制           ▔▔▔▔▔▔   7問 │ ← 倍率チップ --ink-3
└────────────────────────────────────────┘
```

  - 倍率2.0倍（弱点）は `--ok`、0.5倍（堅い）は `--ink-3`。**倍率の数値を必ずチップ内に併記する**ので色だけに頼らない（原則4）。
  - 並び順は倍率の降順（弱点を先）にして、攻略の判断材料として読みやすくする。行数が9行程度になるので**倍率でグルーピングした見出しを付けるか単純な降順のままにするかは実装時に行数で判断してよい**（情報の増減を伴わないため判断事項にしない）。
  - 横棒の長さは同一マップ内の最大問数を基準にした相対比で、問数も併記する（バーだけに頼らない）。
- **空状態（貢献者0人）**: 実画面で「貢献ダメージ」の見出しだけが浮くことを確認済み（2.1.1節）。`RaidScreen.tsx` 757行の見出しが無条件描画で、直後の `.raid-list` が空配列を展開するだけであることをコードで確認した。方向性は**見出しと空状態の代替文を1つの枠にまとめ、「まだ誰も挑戦していません。最初の一撃を入れると、ここに名前が並びます」のように次の行動が分かる文にする**。空状態にBossSigilのシルエット（`.chart-empty-sigil` と同じ低透明度の装飾）を添える方法はダッシュボードで既に確立しているので流用できる。**煽らない**トーンを維持し、`--warn` や `--ng` は使わない。同じ扱いは獲得バッジ0件・弱点マップ0件にも適用する。
- **討伐された回数**: 02の5.3節の「名誉として表示し、公開処刑にしない」を視覚でも守る。数字を大きくして誇るのではなく、`--gold` の小さなバッジ形で「討伐された回数 12」と置く程度に留める。過度に強調するとボス役の心理的コストが上がる。
