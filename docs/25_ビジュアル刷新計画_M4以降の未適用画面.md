## 1. 結論

イベントバトルの最終リザルトが素のリストであるという指摘は、単発の実装漏れではなく**構造的な取り残し**である。20のV-1〜V-8は2026-07-22に完了したが、イベントバトル（S7・S8）とゴースト関連の画面は2026-07-27にM4で新設されたため、刷新の対象に一度も入っていない。

現物確認の結果、未適用の箇所は以下の4群である。

1. **イベントバトル（S7参加・S8ホスト）**: 専用CSSは `.battle-room-code-input` と `.battle-lobby-hint` の2クラスしかない。順位表・最終リザルト・表彰は `.raid-list`（`list-style: none` のみ）で組まれている。加えて**07の7節がS8に規定した「別テーマ・特大タイポ・外周リングのカウントダウン」「4択の色＋形の二重符号化」が未実装**で、これは表層ではなく規定の未実装にあたる。
2. **ゴースト関連**: `GhostBossResultScreen`（記録プレビュー）とRaidScreenのゴースト弱点マップ・討伐された回数・貢献ダメージリスト・バッジが素の `<p>` と `.raid-list` のまま。加えて**空状態の設計が無く、貢献者0人のときに「貢献ダメージ」の見出しだけが浮く**（実画面で確認済み。2.1.1節）。
3. **成長ランク（S6）**: `.dashboard-growth-rank` はフラットな `--surface` 面で、07の3.5節が規定するランク色と段数刻みの二重符号化が未実装。`--rank-platinum` / `--rank-master` / `--rank-gold` トークンは定義済みだが**どこからも参照されていない**。
4. **20の適用漏れ**: `--bg-grad` トークンはV-1で定義されたが**適用箇所が0件**（20の3.1節は「ScreenLayoutの地に適用」と規定）。ホームの `.home-grid`（イベントバトルへの入口を含む）は素のボタンのまま。

一方で、**装飾が少ないこと自体が正しい画面もある**。07の原則3（静かな学習、騒がしい報酬）により、問題を解いている最中・音声を聴いている最中の領域は演出を持たないことが設計上の要件で、飾ると設計を壊す。「ワイヤーフレームのまま」と「意図して静か」の切り分けは2.2.1節で明示し、本書のタスクは前者だけを対象にする。

方向性の主眼は、02の6.2節が求める「最下位でもスポットライトが当たる余地」を視覚で成立させることにある。ただし演出の強度・ホスト画面の地色・4択マーカーの扱いは好みと投影環境に依存するため、独断で確定せず判断事項JV-4〜JV-9として発起人の承認に回す。

## 2. 現状診断（2026-07-27。現物のコード・CSSの読み取りによる静的確認）

### 2.1 診断の方法と限界

20の1節はdev環境の実ブラウザのスクリーンショット全画面確認を方法としたが、本書は**現物のソースコードとCSSの読み取りによる静的確認**で判定した。判定根拠は「専用クラスの有無」「そのクラスがトークン経由で装飾しているか」「素のHTML要素と汎用クラスだけで組まれているか」の3点で、根拠のファイルパスとクラス名を2.3節の表に併記する。

限界（省略しない）:

- **本書の判定そのものは静的確認による**。イベントバトルの3画面は `screenshot-tour.mjs` の巡回範囲外で（2.5節）、WebSocket接続とルーム作成を要するため同スクリプト単独では撮れない。
- 追加時期は `git log --diff-filter=A` で確認したが、これは**ファイル新設時点**であり、その後の改修で刷新を受けた可能性は別途CSSで確認した。
- ただし**一部は実画面のスクリーンショットで裏付けが取れている**（下記2.1.1）。裏付けの無い画面（読解・成長ランク・ゴースト記録プレビュー）については、コードとCSSからの判定は確実だが**実機での印象の程度は未検証**である。

### 2.2 ワイヤーフレーム度の判定基準

| 段階 | 定義 |
|---|---|
| 素のまま | 専用クラスが無い、または `list-style: none` 程度で装飾を持たない。階層・強調が罫線と既定のフォントサイズだけで表現されている |
| 部分的 | 一部に専用クラス・トークン参照があるが、20の深度システム（`--surface-grad`・限定光暈）やディスプレイ書体の適用が及んでいない箇所が同一画面内に残る |
| 刷新済み | 専用クラスを持ちトークン経由で装飾され、20のV-1〜V-8の対象として実施済み |

**この3段階はあくまで「装飾がどれだけ入っているか」の測定であり、「直すべきか」の判定ではない。** 素であること自体が正しい画面が存在するため、次節で切り分ける。

### 2.2.1 「ワイヤーフレームのまま」と「意図して静か」の切り分け

07の原則3（静かな学習、騒がしい報酬）と02の2.2節（満員電車での片手操作）により、**学習中の画面は演出を持たないことが設計上の要件**である。装飾が少ないことをそのまま欠陥と読み替えると設計を壊す。両者は以下の基準で切り分ける。

| 判定 | 基準 | 該当 |
|---|---|---|
| **意図して静か**（飾ってはいけない） | 利用者が問題を解いている最中・音声を聴いている最中の領域。演出を足すと集中を削り、バッテリーを消費し、車内で目立つ | ドリルの解答中（`DrillScreen` の選択肢・問題文・タイマー）、読解のパッセージ読解中（`ReadingScreen`・`PassageText`）、シャドーイングの発話中（`ShadowingScreen`・`KaraokeScript`）、語彙カードの仕分け中（`VocabScreen`）、イベントバトルの出題中（`BattleScreen` の `question` フェーズ） |
| **ワイヤーフレームのまま**（直す対象） | 区切り・報酬・確認の画面、あるいは情報伝達の要件（二重符号化・階層）が欠けている箇所。演出または階層付けを置くべき場所に何も無い | イベントバトルの途中順位・最終リザルト・表彰、ゴーストのレイド画面の貢献リスト・弱点マップ・バッジ、成長ランク、イベントバトルの待機系（ルームコード入力・ロビー）、ホームの `.home-grid` |
| **静かでよいが階層は要る**（最小限だけ直す） | 学習中の画面でも、面の階層・英字ラベル程度の統一は集中を妨げない。ただしアニメーション・光暈は足さない | 読解のパッセージ面（`--surface-grad` と英字パートタグまで）、シャドーイングの面、`CompletionCard`、`ErrorBoundary` |

**判定の帰結**: ドリルの解答中・読解中・シャドーイング中・語彙仕分け中・イベントバトルの出題中には**新しいアニメーション・光暈・背景演出を一切追加しない**。既存の正誤フィードバック（枠色＋✓✕・レイアウト不動）も変更しない。これは6.3節の完了条件（V-19・V-12）で機械的に担保する。

### 2.4 なぜ漏れたか

- **イベントバトル・ゴーストの3画面**: V-1〜V-8完了（2026-07-22）の5日後に新設された。20の3.4節の画面別適用表はS1・S2・リザルト・診断・S9・S6・S3の7行しか持たず、S7・S8の行が存在しない。M4の実装計画（22）にも表層の指定は無い。
- **成長ランク**: M4のT-130で追加された。`components.css` の当該コメントは「既存カード面言語の範囲。光暈・新規アニメーションは追加しない」と明記しており、**意図的に控えめにした結果**である。ただし07の3.5節が規定するランク色と段数刻みの二重符号化は表層の装飾ではなく情報伝達の要件なので、未実装のまま残すべきものではない。
- **ReadingScreen・ShadowingScreen**: V-3〜V-6の作業範囲（S1・S2・リザルト・診断・S9・S6・S3）に該当する行が無い。ReadingScreenは20のV-7完了の前日に追加されたが、V-7の目視確認リストにも入っていない（20の5節「目視確認した画面」に読解の記載なし）。
- **`--bg-grad`・`.home-grid`**: V-1でトークンだけ作られ、適用担当タスクが割り当てられなかった。`.home-grid` はV-3のコード内コメントが「モックアップにも無い既存機能で構造は変えない」と明記しており、構造を変えない判断は妥当だが**面の意匠まで据え置く必然性は無い**。

## 3. 優先度と判断基準

### 3.1 判断基準

## 4. ビジュアル方向性

### 4.1 イベントバトルの順位表（S7・S8共通の基盤）

現状は `<li>{displayName}: {totalPoints}点</li>` で、順位が読み取れない。以下の構造にする。

```
┌──────────────────────────────────────┐
│ STANDINGS                    ← --ev-blue 英字ラベル
│──────────────────────────────────────│
│ ┌──┐                                 │
│ │ 1│  さとう              1,240 pt   │ ← 1位: --gold 枠・順位バッジ金
│ └──┘  ▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔        │ ← 得点バー（1位=100%基準の相対長）
│ ┌──┐                                 │
│ │ 2│  たなか              1,080 pt   │ ← 2位: --rank-silver
│ └──┘  ▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔           │
│ ┌──┐                                 │
│ │ 3│  すずき                960 pt   │ ← 3位: --rank-bronze
│ └──┘  ▔▔▔▔▔▔▔▔▔▔▔▔▔             │
│ ┌──┐                                 │
│ │ 4│  やまだ ★YOU           820 pt   │ ← 自分の行は --ev-blue の左罫線＋「YOU」
│ └──┘  ▔▔▔▔▔▔▔▔▔▔▔               │
└──────────────────────────────────────┘
```

- 順位は**数字バッジ（形）＋色**の二重符号化にする。色だけで1〜3位を区別しない（原則4）。
- 得点はディスプレイ書体（`--font-display`）＋`tabular-nums`。得点バーの長さは1位を基準にした相対比で、数値も併記する（バーだけに頼らない）。
- 自分の行の識別は参加者画面（S7）でのみ有効。ホスト画面（S8）はホストが解答しないため自分の行が存在しない。
- 途中順位（`standings` フェーズ）と最終リザルト（`result` フェーズ）で**同じコンポーネントを使い、最終リザルトだけ表彰の追加要素を載せる**。途中順位に表彰演出を持ち込むと区切り感が薄れる。

実装は `components/StandingsList.tsx` を新設し、S7・S8の両方から使う。ホスト側のサイズ差は親クラス（例 `.battle-host` 配下）で上書きする方針にして、コンポーネントは分岐を持たない。

### 4.2 イベントバトルの最終リザルトと表彰（発端の指摘への回答）

**方向性の骨格**（強度はJV-4で確定する）:

```
┌──────────────────────────────────────┐
│ FINAL RESULT                 ← --ev-blue 英字ラベル・letter-spacing広め
│                                      │
│              ┌────┐                  │
│      ┌────┐  │ 1  │                  │ ← 表彰台（上位3名）
│      │ 2  │  │さとう│  ┌────┐        │   1位の台が最も高い
│      │たなか│  │1,240│  │ 3  │        │   数字＋高さ＋色の三重符号化
│      │1,080│  │     │  │すずき│        │
│      └────┘  └────┘  │ 960 │        │
│                        └────┘        │
```

- **表彰台は上位3名のみ**。4位以下は4.1のリストで続ける。全員が見る画面なので順位の全量は必ず出す。
- **ベストグロース賞は表彰台とは別枠の独立カード**にする。02の6.2節の「最下位でもスポットライトが当たる余地」は、順位と別の軸で表彰することで成立する。順位表の中に埋めると軸が混ざって効果が消える。
- 得点のカウントアップはソロの `ResultScreen`（`POINTS_COUNTUP_MS = 700`）と同じ実装パターンを使い、演出時間は07の9節の報酬演出の範囲（600〜900ms）に収める。
- **段階開示するか（3位→2位→1位→ベストグロース）はJV-4で決める。** 段階開示は投影で盛り上がる一方、通信断・遅参者がいる実運用では待ち時間になる。
- **reduced-motion時の代替（必須）**: カウントアップと段階開示を行わず、最初から全順位・全得点・表彰を静止表示する。`base.css` の全停止ルール（`animation-duration: 0.01ms`）はCSSアニメーションのみを止めるため、**JSタイマーによる段階開示は自前で `matchMedia('(prefers-reduced-motion: reduce)')` を見て分岐する**（`ResultScreen.tsx` の既存パターンを踏襲）。
- **光暈の扱い**: 1位の得点数字に `--glow-gold` を使うと、20の3.1節が定めた「光暈の適用は金CTA・ボスHPバー・ダメージトースト・リザルト数字の4箇所限定」の解釈拡張になる。「リザルト数字」にイベントバトルのリザルトを含めるかはJV-4の帰結として明記し、含める場合は20の3.1節と07への追記を伴う。

方向性:

**記号A–Dは視覚表示から外す**（JV-7=案B「置換」の帰結。V-12で実装）。記号は `visually-hidden` として残るため支援技術には伝わり、情報は失われない。**投影で「正解はAです」のように口頭で記号を使う運用をする場合は、形と記号の対応（A=▲ B=■ C=● D=◆）をホストが把握している必要がある**（形の対応表は `ChoiceButton` から公開しており、S7・S8が同一の表を参照する）。

- 外周リングは `conic-gradient` または SVG の `stroke-dasharray` で表現する。**常時アニメーションではなく1秒刻みの離散更新**にする（07の9節「学習中の常時アニメーション禁止」の精神を投影画面にも適用し、GPU負荷とちらつきを避ける）。reduced-motion時は残秒数の数値表示のみに縮退する。

### 4.4 S7参加者画面の4択と待機系

- **4択の形マーカー（▲■●◆）**: 07の7節S7/S8が規定する。ホスト画面と手元画面で同じ形を使うことで、色覚多様性と投影の色ずれの両方に耐える。JV-7は案B（イベントバトルのみ置換）で承認され、V-12で実装済み。実装は `ChoiceButton` に `markerVariant?: 'symbol' | 'shape'` を足し、既定（ソロ学習の全ドリル画面）を記号A–Dのまま据え置く形にした。形の対応表は `ChoiceButton` が公開し、S8ホスト画面も同じ表を参照して同じ形が同じ選択肢に付くことをコードで一意にしている。**手元・投影のいずれも視覚表示は形のみで、記号A–Dは `visually-hidden` として支援技術に残す**（4.3節のホスト画面の図は形と記号を並べて描いているが、置換を選んだJV-7の決定を優先した）。キーごとの色はマーカーだけに当て、選択肢の枠色は正誤フィードバック（`--ok` / `--ng`）専用のまま残す。
- **待機系（ルームコード入力・ロビー・音声再生中・切断）**: 過剰演出はしない。以下に留める。
  - ルームコード入力: 入力欄をディスプレイ書体の特大（4文字なので `--fs-display` 相当）にし、`--surface-grad` のカードに収める。第一印象になる画面なのでワードマークを1つ置く。
  - ロビー: 参加者一覧をピル形のチップの並びにする（人が増えるのが見えることが待機中の唯一の情報）。
  - 音声再生中（ホスト側 `presenting`）: 再生中であることを示す静止アイコン＋残時間。波形の常時描画はしない（07の9節）。**この状態は `BattleHostScreen` にしか存在せず、参加者画面（`BattleScreen`）の `Phase` に該当フェーズが無い**（V-13実装時に確認）。したがってV-13の対象外とし、ホスト画面を扱うV-11に委ねる。
  - 切断（`closed`）: 既存の文言（`battleCloseMessage.ts`）を変えず、面をカード化して見出しと本文の階層を付けるだけに留める。
- **出題中（`question` フェーズ）は演出を足さない。** 手元で解答している最中は学習中と同じ扱いで、07の原則3に従い静かに保つ。既存の正誤フィードバック（枠色＋✓✕・レイアウト不動）を変更しない。

バッジは `raid-first-clear`（固定1個）と `raid-clear:<bossId>`（週次ボスごとに増える）の2系統で、後者は将来分を列挙できず、端末には現在週の `raidState` しか残らないため「全バッジ定義」を静的に持つことはできない。そこで未取得表示の対象を**固定バッジ＋進行中ボスの討伐バッジ**に定めた（発起人判断 2026-08-13）。「今週これを取れる」が見えることが表示の目的で、過去週の取り逃しを並べることではない。実装は `engine/raidBadgeList.ts` の `buildRaidBadgeList`。
- **討伐演出（紋章の割れ＋金の粒子）**: 07の7節S5が規定し、20の3.3節が「S5の演出強化時に追加」としてスコープ外にした項目。**JV-9が2026-07-29に承認され（案A）、V-21として実装済み。** 実装の要点は次のとおり（詳細は `BossSigil.tsx` の冒頭コメント）。
  - `BossSigil` に `defeated` プロパティを足し、**渡さないときのDOMは1要素も変えていない**（週次ボス・ダッシュボードのシルエットは演出のコストを負わない）。テストで既定と `defeated={false}` のDOM一致を検証している。
  - 割れは**同じ幾何を2枚のクリップで切り出して逆向きにずらす**方式。多角形を実際に分割して座標を作り直すと、辺数がシードから導出した値と合わなくなり決定性テストの見ている図形が変わるため採らなかった。破断線の角度はシード依存で、同一ボスは常に同じ割れ方になる。
  - 粒子は**固定6個のSVG円**で、動かすのは `transform` と `opacity` だけ。多重 `box-shadow` と要素の量産はどちらも20の2.3節6（低端末のGPU負荷）に触れるため使わない。紋章は56pxしかないので、`overflow: visible` で粒子がviewBoxの外へ抜けられるようにしている。
  - 総時間は**800ms**（07の9節の報酬演出600〜900msの範囲内）。
  - **reduced-motion時はアニメーションを行わず、割れた最終状態を静止で見せる**（回転を含めてアニメーションの最終状態と同一にする。平行移動だけにすると56pxでは3px弱のずれしか出ず割れが読み取れない）。粒子は出さない。討伐の事実は割れた紋章と「討伐成功！」の文が担うので情報は欠落しない。
