## 1. 緊急度の高い不具合・欠陥（M2ブラッシュアップ最優先）

### 1.1 セッション中断復帰の未配線【critical】

- `services/session.ts` の `resumeSession` はテストからしか参照されない死にコード。リロード・タブ破棄・SW自動更新（`registerType:'autoUpdate'` は新SW適用時にリロードしうる）で進行中セッションへの復帰導線が無い。
- さらに `HomeScreen` の `startSession` は既存の activeSession を**無警告で上書き**するため、中断した残り問題は永久に失われる。
- **修正案**: App起動時（bootチェックと同時）に `resumeSession` を確認し、スナップショットがあればホームに「続きから再開（残りN問）」導線を表示。新規セッション開始時に進行中セッションがあれば確認を挟む。
- 併せて、**ドリル/語彙画面にセッション途中でホームへ戻る「中断」ボタンが無い**（電車を降りる瞬間に抜けられない）。ステータス帯に中断導線を追加し、復帰はスナップショット復元に乗せる。

### 1.2 起動時の白画面リスク【critical】

- `App.tsx` の起動 `Promise.all`（hasProfile＋loadQuestionPool）に `.catch` が無い。iOS Safari プライベートモード・ストレージ退避・Dexie バージョン競合等で reject すると `bootChecked=false` のまま**恒久的な白画面**になり、ユーザーには何も表示されない。
- **修正案**: catch でエラー画面（再試行ボタン＋エクスポート案内）を表示。起動失敗系のテストを追加。

### 1.3 テーマ・文字サイズが起動時に適用されない【major】

- `THEME_PREFERENCE_KEY` / `FONT_SIZE_KEY` を読むのは SettingsScreen マウント時のみ。ライトテーマ＋文字サイズLを選んだユーザーも、**毎回の起動〜設定画面を開くまでダーク＋Mで表示される**。`'system'` 選択時の `prefers-color-scheme` 変更リスナーも無い。
- **修正案**: App起動時に設定を読んで `setTheme`/`setFontSizeScale` を呼ぶ初期化を追加（bootチェックと並行可）。

### 1.4 音声再生失敗からの復帰不能【major】

- `DrillScreen` / `DiagnosticScreen` の `handlePlayStart` / `startAudioSetPlayback` が `play()` の reject を捕捉しない。音声404・デコード失敗時に `playState='playing'` で固着し、**リロード以外の脱出手段が無い**。パック同期失敗後のオフライン利用・manifest改版でファイル名が変わった場合に現実に発生しうる。診断30問中の音声失敗は初回体験を直撃する。
- **修正案**: catch で playState を戻し「再生できませんでした。再試行/スキップ」を表示。

### 1.5 解答書き込み失敗の静かな握りつぶし【major】

- `finalizeAnswer` 系4関数は DB書き込み失敗・stale-snapshot 例外を全て void で握りつぶす。書き込み失敗後もUIは正誤を表示して次へ進めるが、DB側スナップショットは進んでおらず、**以降の全解答が例外で拒否され続け、通知の無いまま解答が記録されなくなる**。
- **修正案**: エラー時にトースト表示＋DBのスナップショット再読込によるセッション再同期。attempts 書き込みと rating/tagStats/SRS 更新が別トランザクションである点は 4.1 の answerPipeline 集約で同時に解消する。

### 1.6 データ保全の穴【major】

- `navigator.storage.persist()` を一度も要求していない。attempts を「消さない」設計（Dexieフックで削除遮断まで実装済み）に対し、ストレージ自体は best-effort のままで、iOS Safari の7日間非使用削除・クォータ逼迫時の自動退避で**全学習データが失われるリスク**が放置されている。
- `importAll` が settings ストアを clear するため、バックアップ復元でBYOK APIキーが**端末からも無言で消える**（EXPORT_EXCLUDED_KEYS はエクスポート除外のみで、インポート時の clear が既存キーを巻き込む）。
- **修正案**: ①起動時に `persist()` を要求し、`storage.estimate()` で使用量を監視。②importAll の clear 前に EXPORT_EXCLUDED_KEYS 該当の既存行を退避して復元後に書き戻す。

## 3. コンテンツ（問題集）の問題点と改善計画

### 3.1 難易度分布の構造欠陥【M3ブロッカー】

非語彙の全設問495問の実測分布: **d1:15 / d2:246(49.7%) / d3:191(38.6%) / d4:43(8.7%) / d5:0**

- rating.ts の写像（150+170d）では d4=830、d5=1000。**P0診断はR≈830（TOEIC換算約820点）超を上方識別できない**
- docs/03 6節のレイドボス「D4-5中心のセット」は在庫不成立（d5ゼロ・d4も43問、うち part34 は0問）
- d1 も15問（3%）しかなく、R<400台の初学者は実質 d2（写像490）から始まる
- 全設問パックの targetLevel が [600,600] のままで、860帯ユーザー向け設問在庫はメタデータ上ゼロ扱い
- **改善**: ①d4-5帯の設問増産（Part5の複文・長文化、Part3/4の本試験長尺化=3.6参照、と兼ねるのが効率的）②d1帯の入門問題補充 ③パック targetLevel の実態反映

### 3.2 タグ体系と弱点判定の噛み合い不全

- **「意図推定」タグは採点対象0問のデッドタグ**（担い手が shadowing 5件のみで、shadowing は正誤採点されず tagStats に入らない）
- 「先読み」6問・「パラフレーズ照合」10問はプール極小で、WEAK_MIN_SAMPLE=5 と直近100問移動窓に対し、弱点化しても同じ数問を再出題するだけ
- ディクテーション40問が**全問単一タグ「弱形・連結」**で内部識別力ゼロ。L1→L2卒業判定（弱形タグ正答率75%）が同一40問の反復に依存。助動詞弱形/冠詞/前置詞/連結のサブタグ分割が妥当
- 「米英豪加アクセント」タグ28件の実体は US14/UK14 で、**AU/CA音声は全コンテンツに0件**（Piper に en_AU が無い既知の縮退）。タグ名と実効が乖離したまま弱点マップに表示される。タグ改名か豪音声の別TTS調達が必要
- タグ間在庫格差が最大5.8倍（疑問詞聞き取り81問 vs 頻出動詞14問）。弱点タグになりやすい少数タグほど在庫が薄い逆相関

### 3.3 keyVocab循環の機能不全【本アプリの独自価値に直結】

- keyVocab 271語の問題数ヒストグラム: **q1:184語（68%）** / q2:40 / q3:5 / q4:2 / q5-8:40。類題パック117問は39語に極端に集中
- `similarOrFallback` は類題ゼロなら発生元問題そのものを再出題するため、68%の語で 03の3.2「答えの丸暗記防止」が機能しない
- 語彙カード600語のうち **329語（55%）はどの設問の keyVocab にも登場せず**、「単語帳で覚える→問題で使う」の循環が片道。特にB（860帯）は対応する設問パック自体が無く構造的
- **改善**: 類題増産は「q1 の184語に2問目を足す」方向が最も効率が良い。B帯設問パックの新設（3.1の d4-5 増産と統合可能）

### 3.4 在庫量と判定窓の不整合

- **audio_set 在庫20セット = L3→L4卒業判定の「直近20セット」窓と同数**。判定を満たす時点で全セット既見となり、2巡目は内容既知で正解率が実力と無関係に上がる。判定窓に対して在庫は最低2〜3倍（40〜60セット）必要
- リスニング在庫（dictation 40・shadowing 30・p34 20セット）は1日2セッションで1〜2週間で一巡する。SRS前提の語彙と違いリスニングは「初見の聞き取り」が価値なので、**増産優先度は Part5 追加より高い**

### 3.6 本試験形式との乖離（中長期の設計判断）

1. **Part5の文長**: 自作平均9.8語（86%が11語以下）vs 公式平均14.7語（9割が12語以上）。修飾句・固有名詞を含む文構造が無く、**空所位置の特定と無関係部分の読み飛ばしという実戦の半分の難しさが欠落**。d3-d4 を名乗る問題ほど公式の文長に寄せるべき
2. **Part3/4の長さ**: 自作44〜66語（13〜20秒）vs 本試験90〜110語（30〜40秒）。3問分の根拠を保持する負荷が半分。意図推定設問・図表問題も0問。L4「実戦」段階の素材が存在しない

4. **出題パターンの偏り**: 動詞の形39問中25問（64%）が to不定詞/原形で、公式最頻出の主述一致・完了形・受動態がほぼ無い。Part2 は全150問が疑問文で、本試験で毎回2〜4問出る平叙文プロンプトが皆無。比較タグに as...as・倍数表現が無い
5. **固有名詞の欠如**: 公式は架空の社名・人名が頻出し文脈の具体性を作る。自作は The company/The firm 集中（既知の文型単調11%の主因）。**架空固有名詞プールを作って生成時にローテーションするだけで改善する**

### 4.3 Workers側の設計方針（ADR化推奨）

1. **KV無料枠は書込1,000回/日** — 05の8節はリクエスト数しか見積もっていない。20人×50問/日を attempt 単位で KV に書くと初日で枠を使い切る。**レイドHP・damageLogs・冪等キー管理は週次ボス1体=1 Durable Object（SQLiteストレージ）に集約**し、KV は招待コード・members 等の低頻度データに限定。クライアントも attempt 単位でなく**セッション終了時バッチ送信**
2. **冪等性**: DO の SQLite に attemptId 主キー表＋INSERT OR IGNORE。バッチ送信に「受理済みID一覧」を返し、クライアントは全件受理確認後に pendingSync から削除（送信途中切断でも安全に再送可能）。週次ボス終了後は ID 表ごと破棄
3. **packages/api 新設**: wrangler.toml＋TypeScript＋vitest（@cloudflare/vitest-pool-workers で DO 含めテスト可能）。shared-schema を app/api 双方から参照しペイロード型を単一正本に。デプロイは GitHub Actions＋CLOUDFLARE_API_TOKEN（Secrets）。dev/prod 2環境を分ける。public リポジトリなので秘密は Secrets のみ
4. **CORS/SW**: Pages（*.github.io）と Workers（*.workers.dev）は別オリジン。許可オリジン限定のCORS必須、プリフライトOPTIONSもリクエスト数見積りに含める。**vite-plugin-pwa のランタイムキャッシュが APIドメインを捕捉しないよう明示除外**しないと、オフライン時に古いレイドHPが成功レスポンスとして返る事故が起きる
5. **時刻基準**: 週次レイドの月曜出現・金曜期限・期間内判定の時刻基準が未定義。ボスの startAt/endAt はサーバーが epoch ms で配り、期間判定はサーバー受信時の answeredAt 照合＋サーバー側クランプとする（クライアント時計を信用しない）

### 4.4 プライバシー境界のコードレベル強制

- ①shared-schema に `DamageSyncPayload`（attemptId, bossId, damage, questionCount 程度）を閉じた型として定義
- ②attempts→payload 変換関数を1箇所（services/raidSync.ts 等）に限定
- ③変換出力を Object.keys のホワイトリスト照合でユニットテストし、questionId・isCorrect・レート実値・responseMs が含まれたら失敗させる（ESLintでは値の混入を防げないためテストが本命)
- ④questionStats は認証ミドルウェアで deviceToken 検証後、ハンドラに渡す前にトークンを落とす構造（保存レコード型に deviceToken フィールドを持たせない）。なお受信タイムスタンプ・IPログとの突合で理論上は結合可能性が残るため、「保存データとして結合しない」が保証範囲である旨を 04 に注記（過大な約束を防ぐ）
- ⑤deviceToken のバックアップ複製問題: 機種変の正規手順がインポートである以上、同一トークン2端末の併存は起きる。「同一トークン=同一人物の複数端末として合算許容」と割り切り、荒れた場合のトークン再発行手順を docs に明記（バックアップから除外する案は機種変で貢献が分断されるため劣る）

### 4.5 段階導入（縮退設計を常時保つ6段階）

各段階で「API無効時にソロ動作が一切変わらない」ことを回帰テストに含め、全損縮退（05の1節）を常時検証する:

2. **疎通**: packages/api 骨格＋deviceToken 登録＋ヘルスチェック
3. **集計**: バッチダメージ送信＋DO集計＋冪等（この時点で4人レイドの裏側が成立）
4. **画面**: S5＋S1のHPバー（表示のみ。「最終同期時刻の明示＋討伐確定はDOが正」の表示規約）

6. **バッジ**: badges ストア（定義済み・未書込）への初書込。レイド系バッジは同期時にサーバーの討伐確定から端末側で導出（サーバーはバッジを持たない=共有データ極小の原則維持）
