# 09. 開発体制（並行開発・契約・ブランチ運用）

## 1. このドキュメントの位置づけ

- 複数人で並行開発するための **実行体制・順序・運用ルール** を定める。
- タスクの内容・依存関係・完了条件の正本は [08_M1タスク分解](08_M1タスク分解.md)。本書は 08 のタスクを「誰が・どの順で・どう衝突せずに」進めるかを定めるもので、08 に従属する。矛盾した場合は 08（さらに上流は 01〜07）が優先し、本書を修正する。
- 現在の進捗・ブロッカー状況は [STATUS.md](STATUS.md) を正とする（本書には進捗を書かない）。
- 設計判断の記録は [adr/](adr/README.md) に残す（ADR運用）。

## 2. 契約（先に固定する共有面）

並行開発の衝突点は共有資産に集中する。以下を「契約」と呼び、**契約が固まるまで依存タスクの本格着手をしない**。逆に契約さえ固まれば各トラックはほぼ独立に進められる。

| # | 契約 | 対応タスク | 状態 | 内容 |
|---|------|-----------|------|------|
| C-1 | 問題パックスキーマ | T-05 | **確定済み** | `shared-schema` パッケージの問題パックJSON型・manifest型・バリデータ。app と cli の共通言語（04の2節が正本）。以後 T-41・T-91・T-287・T-347 で改訂（改訂は都度単独PR） |
| C-2 | IndexedDB スキーマ | T-06 | **確定済み** | Dexie 全ストア定義（04の3節の全ストアを J-7 のとおり最初に一括定義）。エンジンと UI の共通言語。v2でexamScores（T-42）、v3でraidState（T-88）を追加し現在13ストア |
| C-3 | platform 抽象化レイヤ | T-04 | **確定済み** | `AudioPlayer` / `PackCache` / `Notifier` インターフェース。ESLint で直接 Web API 使用を禁止済み |
| C-4 | 学習エンジンのインターフェース | T-09/T-10/T-12/T-13 の入出力型 | **確定済み** | SRS・レーティング・弱点判定・クイックパック生成の入出力型。実装より先に型だけ確定し、UI 側はモック実装で進める（T-04 と同じインターフェース先行パターン）。M2のT-44で拡張 |

### 契約の変更ルール

- 確定済みの契約（C-1〜C-4）を変更する場合は、**変更のみの単独PR**にする（機能実装と混ぜない）。
- PR に影響範囲（どのトラック・どのタスクに影響するか）を明記し、全トラックの担当者をレビュアーに入れる。
- 設計判断を伴う変更（フィールド追加の是非、型の分割方針など）は ADR を起こす。

## 3. トラック分割

依存グラフ（08の4節）に基づき、リポジトリ上の競合がほぼ発生しない3トラックに分ける。

| トラック | 範囲 | 主なタスク | 主なディレクトリ | 特性 |
|---------|------|-----------|----------------|------|
| **Track A: アプリ・UI** | 画面・音声再生・PWA | T-15〜T-23 | `packages/app/src/`（components / pwa / 画面） | iOS実機の音声再生（T-15）という**最大の技術リスク**を持つ。縦切りスライス（4節）で進める |
| **Track B: 学習エンジン** | 純ロジック（DOM 非依存） | T-07, T-09〜T-14 | `packages/app/src/engine/`（新設） | ユニットテストのみで進行可能。C-4 の型を先に切り、Track A へモックを提供してから実装を差し替える |
| **Track C: コンテンツパイプライン** | CLI・コンテンツ生成 | T-24〜T-34 | `packages/cli/` | 他トラックとの競合ほぼゼロ。**人手レビューと TTS が M1 全体の律速**（08の4節）のため、最優先で走らせる。B-1 / B-2 のブロッカー解消もこのトラックの初手 |

- 共通の前提: C-1（T-05）と C-2（T-06）は全トラックの依存元のため、**最初に直列で片付ける**（分担してもよいが、確定するまで他タスクの本格着手をしない）。
- 2人体制なら A+B を1人・C を1人、3人体制なら1トラックずつが基本の割り当て。

## 4. Track A の縦切りスライス

Track A 内は水平レイヤー順（データ層→エンジン→UI）ではなく、**「1機能を端から端まで通す」縦切りスライス**で進める。理由: 最大リスク（音声・実機）を最速で検証でき、各スライスの終わりに動くものが残るため方向のズレを早期発見できる。

| スライス | 内容 | 使うタスク | コンテンツ |
|---------|------|-----------|-----------|
| S-A1 | **Part2瞬発（最小）**: 音声→3択→正誤→記録が iOS 実機で動く | T-07（最小）, T-15, T-16, T-17 | 手打ちダミー問題 5〜10問（T-24〜33 のパイプラインを待たない） |
| S-A2 | **語彙SRS**: スワイプ仕分け→SRS が回る | T-09（Track B成果）, T-19 | 手打ち語彙カード数十件 |
| S-A3 | **レーティング+ダッシュボード** | T-10（Track B成果）, T-22 | S-A1/S-A2 で溜まった解答データ |
| S-A4 | **クイックパック+ホーム**: 弱点駆動出題の一連が通る | T-11〜T-14（Track B成果）, T-13, T-21, T-20 | ダミーコンテンツ |
| S-A5 | **本番コンテンツ差し替え+統合**: Track C の成果物に差し替え | T-35〜T-38, T-23 | 実パック（Track C 成果） |

- ダミーコンテンツは**必ず C-1 のスキーマに準拠**させる（差し替え時の手戻りを防ぐ）。license/origin はダミー値でよいが、フィールド自体は埋める。
- スライス境界ごとに dev ブランチ上で通し確認を行う（モック→実装差し替えの結合バグはここで捕まえる）。

## 5. ブランチ・PR運用

```
main ← スライス境界・フェーズ境界でまとめて PR（レビュー必須）
 └ dev ← 日常の統合ブランチ（task ブランチから PR で入れる）
     └ task/T-xx-説明 ← 各自の作業ブランチ
```

- **main**: ブランチ保護あり。ただし2026-08-06の実測では**必須ステータスチェックが未設定・必要承認数0・`enforce_admins` 無効**で、`dev` は無保護である（docs/31 K-9）。是正は人間タスク H-18（docs/32 10節）で、J-116によりエージェントは実施しない。マージ単位はスライス完了・フェーズ完了などの節目。
- **dev**: 統合ブランチ。task ブランチから PR で入れる（並行開発中のレビューは任意。速度優先とし、品質担保は main への PR で行う）。
- **task ブランチ**: `task/T-xx-説明` 形式（例: `task/T-05-pack-schema`）。`feature/` プレフィックスは使わない。
- CI（lint / build / test）は全 PR で通ること。
- 契約変更（2節）だけは dev 行きでも単独 PR + 全員レビューとする。

**現行の運用正本は [30](30_改修計画_全量レビュー棚卸し.md) 4.1節**（task/ブランチを切って dev へドラフトPR。1タスク1PRを原則とする）。[13](13_M2実装計画.md) 2.4節・[19](19_改修計画_モード完走性とセッション導線.md) の「dev へ直接コミットしてよい」は当時の期間限定の特例で、現在は適用しない。

## 6. ADR 運用

- 01〜08 の設計正本に**書かれていない技術判断**（ツール選定、実装方式の選択、スコープ解釈など）が発生したら [adr/](adr/README.md) に記録する。
- 01〜08 の内容を変更する判断は ADR ではなく、該当ドキュメント自体を更新する（00_README のレビュー反映履歴慣行に従う）。ADR はその変更の「なぜ」を補足したい場合にのみ併用する。
- 書式・運用ルールは [adr/README.md](adr/README.md) を参照。

## 7. 現在地の可視化

- [STATUS.md](STATUS.md) を**唯一の進捗正本**とする。ただし2026-08-06のT-256（[30](30_改修計画_全量レビュー棚卸し.md) 13節）により、STATUS.mdは「現在地のみ」を300行以内に保つ構成へ変更した。構成は固定4節（未解決ブロッカー・マイルストーン別の現在地・次のアクション・直近2週間の変更）である。
- **完了記録はSTATUS.mdに書かない。** 実装の詳細・検証ログ・経緯は次のいずれかに書く。
  - タスクの実装詳細・検証結果: 該当する自走タスクシート（`docs/13`・`docs/15`・`docs/17`・`docs/22`・`docs/24`・`docs/28`・`docs/30` 等）の該当タスクの節・履歴表。STATUS.mdからはリンクのみとする（二重管理をしない）。
  - 日付ごとの完了記録の集積: [docs/history/YYYY-MM.md](history/) へ月次でアーカイブする。2026-08-06時点で2026-07分・2026-08分が存在する。新しい月に入ったら当該月のファイルを新設する。
- 更新タイミング: タスクの着手・完了・ブロッカー状態の変化のたびに、**同じ PR 内で** STATUS.md（該当する場合は1.1節の人間タスク表・1.2〜1.3節のブロッカー）を更新する（進捗更新だけの独立コミットを後回しにしない）。
- STATUS.md が実態と食い違っていることに気づいたら、気づいた人がその場で直す。
