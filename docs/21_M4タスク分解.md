## 2. 設計方針（ADR化推奨。着手時に `docs/adr/` へ正式記録する）

1. **無料枠の再見積り**: 昼バトルは週1回×20人×15問のWebSocketメッセージ数で、Workers無料枠（10万リクエスト/日）に対し余裕（05の4.3の見積りの範囲内）。Durable ObjectのWebSocketは**Hibernation API**の利用を前提に設計する（接続維持中の課金を抑える標準手段）。無料枠・API仕様の現況は着手時（T-124）に公式ドキュメントで再確認し、前提が崩れていたら停止する。
2. **ルーム揮発の原則**: battleRoomsはDO内の揮発状態のみ（04の4節）。順位確定・結果配信後に個人別データを破棄する。バトルの確定結果（自分の誤答・得点・誤答問題の復習デッキ登録）は各端末が自分のIndexedDBへ保存する。
3. **オンライン専用の例外明示**: 昼バトルは同席・同期が本質のためオフライン正常系の対象外とする（レイド・ソロの縮退設計は不変）。API無効・WebSocket不通時はS7/S8入口を出さない（縮退の第一ゲートはM3の `isConfigured()` と同じ）。
4. **ゴーストはM3基盤の拡張**: 新規インフラを作らず、週次ボスDO・同期・S5を拡張する（J-66）。契約変更（`RaidBossState` へのtype/defense追加・ゴースト記録API）は shared-schema 単独PR。
5. **同意の構造的強制**: ゴースト記録の保存レコード・受領APIは同意フラグ必須の型とし、questionStatsのdeviceToken非結合（14の4.4-④）と同じ「型レベルで違反を作れない」方式を踏襲する。
