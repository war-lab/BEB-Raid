# 0012. 週次ボス手動生成エンドポイント（POST /admin/raid/generate）の追加

- **日付**: 2026-08-03（事後記録。2026-08-04の全量レビューQ-91で記録漏れを検出し起票）
- **ステータス**: 承認済み
- **関連**: docs/17 3.10節「運用エンドポイント」・docs/STATUS.md 2026-08-03「週次ボスの手動生成エンドポイントを追加」・docs/30 3節 J-100（cronの修正方針）・J-101（EMA更新の重複防止）
- **関連コミット**: `44c7e4c`（本ADRの主題。エンドポイントの追加）・`8de62f7` と `f72c1fc`（T-179。生成処理の冪等化）・`3761419`（T-180。cronの日次化）

## 背景

週次ボスは cron（`generateWeeklyBoss`、当時は毎週発火）でのみ生成され、発火しなかった週を手当てする手段が無かった。

2026-07-27・2026-08-03 と2週連続でcronの自動発火が確認できず、原因は本ADR起票時点で未特定である。有力仮説は「Cloudflare Workers のcron式が曜日を`1=日曜〜7=土曜`と解釈するため、`crons = ["0 0 * * 1"]`が意図した月曜ではなく日曜0:00 UTCに発火し、`isoWeekInfo`が終わりかけの週を返してボス生成をスキップする」というものだが、本番ログで確定していない（docs/STATUS.md・docs/29 付録A-1）。

原因調査には日数を要する一方、レイドは参加者が実際に取り組んでいる週次イベントであり、不発のまま放置すると当該週の参加機会が失われる。2026-07-22の`boss-2026-W30`は一時的なデバッグエンドポイントで手動生成しており、そのコードは残っていなかった。cron不発のたびに同様の一時対応を繰り返すのは非効率であるため、認可付きの常設エンドポイントとして`POST /admin/raid/generate`を追加した。

この判断は2つの内容を含む。

第一に、**共有APIの攻撃面を増やす変更**である。管理系エンドポイントを本番APIに新設するため、認可設計の妥当性を記録に残す必要がある。

第二に、**「cron不発の原因が未特定のまま、運用の手当てで回す」という運用方針の決定**である。原因が分かるまで待つのではなく、症状（今週レイドが立たない）を都度解消しながら並行して原因調査を進める選択をした。

## 検討した選択肢

### 案A: 認可付きの常設エンドポイントを追加する（採用）

利点は、cronの原因調査と切り離して当該週のレイドを即座に成立させられること、2026-07-22の一時対応のように使い捨てのデバッグコードを都度書く必要がないこと。

欠点は、本番APIに管理系エンドポイントという新しい攻撃面が増えること。認可トークンの管理という運用負荷が発生すること。

### 案B: cronの原因究明を先に完了させ、それまでは手当てをしない

利点は、攻撃面を増やさずに済むこと。

欠点は、原因調査に要する期間（本番ログの確定には最短でも次回発火を待つ必要があり、日〜週単位）だけレイドが不成立になる週が発生すること。参加者が実際に活動している共有機能であるため、この欠点は看過できないと判断した。

### 案C: cronの`crons`設定（曜日フィールド）をその場で書き換える

利点は、生成処理に手を入れずに済むこと。

欠点は、「1=日曜」という解釈が本番ログで確定していない仮説の段階でパラメータを動かす修正であり、仮説が誤っていた場合に発火日を別の誤った日へ動かすだけになる。採らない（この論点は本ADRではなくJ-100として別途決着させ、後述のとおりT-179・T-180で解消した）。

## 判断

案Aを採る。`POST /admin/raid/generate`を追加し、次の安全側設計とする。

**認可**: 専用シークレット`ADMIN_TOKEN`（Bearer認証）。未設定の環境では404を返し、設定するまでルートを露出しない。既存の`INVITE_CODE`は流用しない。登録済みメンバー全員が知っている値であり、運用操作の認可には強度が不足するためである。本番へは`wrangler secret put ADMIN_TOKEN --env production`で設定済み、dev環境は未設定（＝404のまま）とした。

**冪等ガード**: `generateWeeklyBoss`は当時、ボスDO初期化（冪等）と`emaDailyDamage`の更新（非冪等）を含んでいた。同じ週の実績でEMAを二度平滑化すると、翌週以降のボスHP算出が前週値へ寄る事故（`index.ts`の`CRON_WEEKLY_BOSS`のコメントに記載の経路と同じもの）が起きる。そのためハンドラは当週ボスの存在を先に確認し、存在すれば生成処理を呼ばずに現状を返す（`{created:false, boss}`）。この設計により、エンドポイントは当週ボスの存在確認としても機能する。

**検証**: `packages/api/src/adminHandlers.test.ts`に6件（生成される／既存があれば生成せずEMAも触らない／トークン相違で401／ヘッダ無しで401／未設定で404／GETは404）。

## 影響・トレードオフ

共有APIの攻撃面が1エンドポイント増える。`ADMIN_TOKEN`の漏洩が起きた場合、当週ボスの強制生成（＝EMA未更新の状態確認）が可能になるが、EMA更新を伴わないため、上限は「余分な存在確認ができる」程度に留まる。

「原因不明のまま手当てで運用を回す」判断により、cronの根本原因調査を先送りしている。原因が判明しないまま手当てが常態化すると、運用エンドポイントへの依存が固定化し、根本原因の調査が着手されなくなるリスクがある。

## 経緯

### 2026-08-03時点の位置づけ: cron不発時の唯一の手当て

起票当時、`generateWeeklyBoss`のEMA更新は非冪等だったため、本エンドポイントは「既存ボスがなければ生成し、あれば何もしない」というガードで安全側に倒す設計になっていた。cronが日曜発火の仮説どおりだとしても、日次化のような恒久対応は別タスクとし、当面は本エンドポイントを唯一の手当てとして運用する方針だった。

### T-179・T-180による位置づけの変更: 日次化後も残す運用手段へ

その後、T-179（commit `8de62f7`・`f72c1fc`）で`generateWeeklyBoss`本体を冪等化し、RaidBossDO側に週の生成権を主張する操作を設けた。同じ週に対する二重呼び出しがEMAを二度平滑化しない構造になった。

`f72c1fc`は統合レビューで見つかった移行ギャップへの対応である。生成権の主張が新設テーブルだけを見ていたため、本ADRの起票時点で既に生成済みだった週（`boss-2026-W32`）では主張が成立してしまい、デプロイ後の初回発火でEMAが二重平滑化される経路が残っていた。`state`行の存在も主張の条件に加えて塞いだ。

T-180（commit 3761419）はこの冪等化を前提に、cronの発火間隔を週次から日次（`0 0 * * *`）へ変更した。曜日フィールドを使わない設計にすることで、「1=日曜」か「1=月曜」かというCloudflareのcron曜日解釈から独立し、発火漏れや遅延があっても翌日に自己修復するようにした（判断根拠はdocs/30 J-100・J-101）。

この変更により、本エンドポイントの位置づけは「cron不発時の唯一の手当て」から**「日次化後も残す運用手段」**へ変わった。日次cronが自己修復する前提のもとでも、次の場面で本エンドポイントは引き続き必要である。

- 日次化後もCloudflare側の障害・デプロイ不整合等でcronが連日不発になり得るため、即時復旧の手段として残す。
- 当週ボスの存在確認という副次用途（`{created:false, boss}`）は、日次化後も監視・デバッグの手段として有効である。

T-179・T-180はdevへマージ済みである。`wrangler.toml`の`crons`は`0 0 * * *`、`index.ts`の`CRON_WEEKLY_BOSS`も日次に一致しており、cron式の整合はT-288のテストが`wrangler.toml`を読んで照合する。本ADRの認可設計・冪等ガードの記述は変更していない。
