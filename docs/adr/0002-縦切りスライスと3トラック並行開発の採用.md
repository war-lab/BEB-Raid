# 0002. 縦切りスライスと3トラック並行開発の採用

- **日付**: 2026-07-07
- **ステータス**: 承認済み
- **関連**: docs/08（タスク正本）、docs/09（本判断の詳細を体制ドキュメントとして展開）

## 背景

F1 完了時点で開発体制が複数人並行に変わる見込みとなった。08 のフェーズ構成（F1→F6）は水平レイヤー順（データ層→エンジン→UI→コンテンツ）であり、そのまま直列に消化すると次の問題がある。

- 「実際に使える1機能」が動くのが F4 完了まで見えない
- 最大の技術リスク（iOS Safari の自動再生制限下での連続音声再生 = T-15。実機検証は T-36）が後半に寄っており、詰まった場合に手前の作業が手戻りリスクを抱える
- 複数人で分担する際の衝突点・分担境界が定義されていない

## 検討した選択肢

### 案1: 08 のフェーズ順のまま直列消化

- 利点: 計画の変更が不要。依存関係どおりで迷いがない
- 欠点: 上記の3問題がそのまま残る。並行開発の分担指針がない

### 案2: 完全な縦切り（機能ごとにスキーマからUIまで独立に作る）

- 利点: 機能単位の独立性が最大
- 欠点: SRS/レーティングエンジンと shared-schema は複数機能で共有されるため、純粋な垂直分割は不可能。スキーマを機能ごとに継ぎ足すと J-7（全ストア一括定義でマイグレーションを減らす）に反する

### 案3: 契約先行 + 3トラック並行 + Track A 内は縦切りスライス（採用）

- 共有面（パックスキーマ・DBスキーマ・platform/エンジンのインターフェース）を「契約」として最初に固定し、以降は競合しない3トラック（A: UI / B: エンジン / C: コンテンツパイプライン）で並行する
- Track A 内は縦切りスライスで進め、最初のスライス（Part2瞬発の最小構成）で iOS 実機の音声リスクを最速検証する
- コンテンツは当面手打ちダミー（スキーマ準拠）で進め、Track C の本番コンテンツに後から差し替える

## 判断

案3を採用。決め手は次の2点。

1. 依存グラフ（08の4節）上、F5（CLI）は shared-schema 以外にアプリ本体との接点がなく、F3（エンジン）は純ロジックで DOM 非依存 — つまり契約さえ固定すれば並行性が構造的に高い
2. 08 自身が T-20 で「開発中はダミーパックで先行可」と部分的に縦切りを認めており、これを全体に広げる判断は正本との矛盾が小さい

08 は「タスク定義・依存関係・完了条件の正本」として変更せず維持し、実行順序と体制は 09 に分離した（人数変動時に 08 を書き換えずに済むため）。

## 影響・トレードオフ

- ダミーコンテンツ→本番コンテンツの差し替え工程が追加で発生する（スキーマ準拠を強制することで手戻りを小さく抑える前提。ただしスキーマ外の品質問題 — 音声の長さ・言い回し等 — による UI 調整の可能性は残る）
- エンジンのモック→実装差し替え時に結合バグが出やすい。スライス境界での dev 通し確認で捕まえる運用とした（09の4節）
- 人手レビュー（コンテンツ目視判定）は並行化の恩恵が薄く、人数を増やしても律速のままである点は解消されない
