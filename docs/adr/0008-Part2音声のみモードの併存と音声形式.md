# 0008. Part2音声のみモードの併存と音声形式（3応答連結＋オフセット配列）

- **日付**: 2026-07-29
- **ステータス**: 承認済み
- **関連**: T-151（スキーマ）・T-152（TTS生成）・T-153/H-15（音声再生成）・T-154（アプリ）／docs/14 3.6-3（本ADRが決着させる未決事項）・docs/02 3.1節・docs/04 2節・docs/11

## 背景

現状のPart2は、設問だけを音声で流し、3つの応答をテキストの選択肢として表示する。

実データもその構造になっている。
`content/packs/pack-p2-s-*.json` の150問は `choices` 3件がテキストで、`script` は「設問 — 正答応答」のみを持つ。
音声ファイルは設問と正答応答を連結した1本で、`audioMeta.questionEndMs` までを解答前に再生して正答応答の読み上げを解答後まで遅らせている。
誤答応答2件の音声は存在しない。

本試験のPart2は3つの応答すべてを音声で読み上げ、受験者は耳で比較する。
現状の形式は「設問を聞いて応答は読む」ため、鍛えている能力がリスニングと読解の混成になっている。
docs/14 3.6-3 はこの乖離を指摘したうえで、「本試験に寄せるならTTSとUIの拡張が必要、現形式を維持するなら訓練目標の再定義を明示すべき」として判断を保留していた。

## 検討した選択肢

### 形式の扱い

**案1: 音声のみモードをトグルで併存させる（採用）**

利点は、既存のテキスト選択肢形式が残るので後退リスクがないこと、応答音声が未生成の問題が混ざっても縮退できるため段階導入が可能なこと。
欠点は、モードが2つになりテストとドキュメントの分岐が増えること。

**案2: 全面置き換え**

利点は本試験に忠実な形式に統一できること。
欠点は、テキスト選択肢という易しい入口を失うこと、150問すべての音声再生成が完了するまで機能を出せないこと。

### 音声ファイルの持ち方

**案A: 1ファイルに「設問＋応答A＋応答B＋応答C」を連結し、各応答の開始msを配列で持つ（採用）**

**案B: 応答ごとに別ファイルを作る**

**案C: 既存ファイルを残し、3応答版を別ファイルとして追加する**

## 判断

音声のみモードを既存形式と併存させ、Part2単独モードの起動フローに置くトグルで切り替える。
トグルは `partialAudioMode`（冒頭だけ再生の特訓）と同じセッションスコープの非永続とする。
同じモーダルに並ぶ兄弟オプションで永続方針を食い違わせないため。

音声は案Aを採る。
`audio/part2/<word>.mp3` のパスと役割を変えずに中身を4セグメントの連結に差し替え、各応答の開始msを `audioMeta.responseOffsetsMs` に持たせる。
テキスト選択肢モードは従来どおり `questionEndMs` で打ち切って再生するため、挙動は変わらない。

案Aの決め手は、新しい音声URLが1本も増えないことである。
`services/packSync.ts` の `collectAudioUrls` は `q.audio` と `q.phraseAudio` だけを集めるので、案BとCではここの改修が必須になり、漏れると「音声のみモードだけオフラインで無音」という最も避けたい縮退が起きる。
案Aは中身の差し替えでpack JSONの値が変わり、manifest の `hash` 差分から `syncPacks` が音声を再フェッチするので、既存のキャッシュ無効化の仕組みに乗るだけで済む。

再生実装の単純さも案Aを支える。
音声のみモードの再生は全長を1回再生するだけで足りる。
案Bは設問から応答Cまでを跨いで逐次再生する必要があるが、`playSequence` は `PlayOptions` を全ソース共通に適用する設計のためソースごとのオフセットを表現できず、`playGeneration` と `stop()` の世代管理と絡んだ実装になる。

容量は案AがPart2の8.0MBを約19MBに増やす。
案Cは設問音声を二重に持つため同程度増えるうえ、ファイル数が倍になる。
案Bは300〜450本の新規ファイルを生み、`PackCache.usage()` の逐次読み出しも重くなる。

`responseOffsetsMs` と対にして `responsesTextDigest`（生成時の choices のダイジェスト）を必須とし、ビルド時の不一致をエラーにする。
読み上げ順は `choices` の key 昇順で音声に焼き込まれるため、TTS後に選択肢のテキストを編集すると音声と key の対応が崩れ、`answer` が実質誤りになる。
画面上は正常に見えるので、`answer_mismatch` と同じ重大度で止める必要がある。

## 影響・トレードオフ

受け入れたデメリットは次の3つである。

第1に、既存150本のmp3を差し替えるためpublicリポジトリにバイナリ差分が出る。
`packages/cli/scripts/regen-curly-audio.mjs` に前例があり、Part2は全問が対象なので部分再生成の意味がない。

第2に、モードが2つに増える。
アプリ側は「プールを絞る」層と「問題単位で従来UIに落ちる」層の2段でフォールバックし、未対応の問題が混ざっても進行不能にしない。

第3に、選択肢を後編集すると `responsesTextDigest` の不一致でビルドが落ちる。
これは意図した挙動で、レビュー運用としてdocs/11に「TTS後の選択肢編集には応答音声の再生成が必要」と明記する。

音声のみモードでは表示順のランタイムシャッフル（T-79・J-36）を使えない。
読み上げ順が焼き込まれているため、key 昇順で表示する。
丸暗記対策はコンテンツ側の決定的ローテーション（`rotatePart2Choices`）が担っているので、この制約による後退はない。

選択肢の記号は形マーカー（▲■●◆）ではなく A/B/C を使う。
形マーカーはJV-7でイベントバトル専用と決めており（docs/25 4.4節）、本試験のマークシートも (A)(B)(C) であるため、そちらの方が忠実でもある。

将来見直す条件は、Part1（`audio_photo`）を実装して同じ「3応答を音声で流す」構造が必要になった場合である。
そのときは `responseOffsetsMs` の適用formatを広げるか、選択肢と音声区間の対応を一般化した表現に移す。
