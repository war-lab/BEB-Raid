# 0007. 通知手段の選択とM5ネイティブ化の前提（Web Push先行・ネイティブ化はiOS限定で保留）

- **日付**: 2026-07-27
- **ステータス**: 承認済み（発起人が2026-07-27に決定）
- **関連**: docs/23_M5ネイティブ化計画.md（J-72・J-82・J-85・J-86・T-149・T-146）、docs/05_アーキテクチャ設計.md 7節、docs/06_ロードマップ.md 3節、docs/02_機能設計.md 7節

## 背景

発起人が2026-07-27にM5（Capacitorネイティブ化）の実施を決定した。その直後、着手前の調査で前提が複数崩れていることが判明した。

ネイティブ化の主動機は、05の7節が記述する「iOSのPWAではスケジュールされたローカル通知が打てない」という制約である。SRS期限・ストリークの通知を実現するにはWeb Push＋サーバー側cronが必要になり、これはサーバーレス方針と衝突する、という論証だった。

この論証には評価漏れがあった。**iOS 16.4以降、ホーム画面に追加したPWAはWeb Pushを受け取れる。** ローカルのスケジュール通知はWeb APIに依然存在しないが、サーバー起点のpushで代替しうる。

docs/23のJ-76はWeb Push＋サーバーcronを代替案として挙げて棄却しているが、その棄却は「ネイティブ化する前提の中で通知をどう実装するか」の比較としてのみ行われた。「ネイティブ化を回避する手段」としては評価していない。

あわせて、費用と実機検証の前提も整理が必要だった。Apple Developer Program（$99/年）は、無料の徹底を優先したTTS調達（06の3節のB-2でPiperを選定）とは方針が異なる継続支出である。

## 検討した選択肢

### 案A: 予定どおりネイティブ化を先に進める

- 利点: 通知・ストレージ退避・バックグラウンド音声の3つを一度に解消できる。
- 欠点: 通知の効果が未検証のまま、Capacitor・CI・署名・再署名運用という重い仕組みを抱える。docs/23のJ-71が「実測してからゲート判定する」順序を求めていたのに、実測の機会を作らずに運用を確定させることになる。

### 案B: iOS PWAのWeb Pushで通知の効果を先に実測し、ネイティブ化の着手を保留する

- 利点: 費用と運用コストがゼロ（$99・署名・審査・7日ごとの再署名・Xcode・macOSランナーのいずれも不要）。J-71が本来求めていた順序を初めて実行できる。効果が出なければネイティブ化そのものを見送れる。
- 欠点: プライバシー境界に触れる（push購読endpointという個人紐づき識別子が増える）。Service Workerの構成変更が必要で、既存のPWAキャッシュ挙動への回帰リスクがある。通知が共有APIに依存する。ネイティブ化の動機のうち「ストレージ退避の解消」は解決しない。

### 案C: 通知を諦める

- 利点: 何も作らずに済む。
- 欠点: SRS学習は「期限が来たことに気づく」ことが前提であり、通知の欠如は学習継続率に直結する。01の目的（380→760）に対して放置できない。

## 判断

**案Bを採る。** 加えて、ネイティブ化に進む場合の前提を以下のとおり確定させた。

### 1. 通知手段の順序（J-85）

M5の着手を保留し、先にiOS PWAのWeb Pushで通知の効果を実測する（T-149）。着手可否とスコープはその結果で再判断する。M5の実施決定自体は撤回していない。

決め手は、案Aが「効果の不明な機能のために不可逆な運用コストを先に確定させる」構造になっていた点である。案Bは同じ目的を$0で先に試せる。

### 2. Web Pushに課す制約（J-86）

- **通知本文は件数を含まない汎用文に限定する。** 「今日の復習n件」をサーバーが送るには各人の復習件数をサーバーが知る必要があり、不変条件（個人紐づきで共有APIに送るのはダメージ換算値＋表示名のみ）に正面から反する。
- **購読情報は `deviceToken` と結合できない形で保存する。** 結合すると、レイド貢献（表示名＋ダメージ）と通知購読が同一キーで結び付き、個人単位の学習行動をサーバー側で推定できるようになる。具体的な保存方式はT-149で設計する（本ADR時点では未確定）。
- 通知が使えない状態（権限拒否・共有API停止・購読失敗）でも学習機能を一切劣化させない（05の1節の縮退設計）。

### 3. ネイティブ化の対象プラットフォームと費用（J-72）

- **iOSのみ**を対象とし、Androidは初回スコープから外す。ネイティブ化の動機であるスケジュール通知の欠如はiOS固有であり、Androidの退路はPWA継続が担う。
- **Apple Developer Program（$99/年）には登録しない。** 動作確認の範囲はiOSシミュレータと、発起人自身の実機（無料Apple IDでのsideload）とする。
- iOSビルドは GitHub Actions の macOSランナーで行う（ローカル環境はWindowsでXcodeが使えない）。publicリポジトリのため無償枠内で収まる想定だが、**未検証**である。
- 無料署名の制約（プロビジョニングプロファイルが7日で失効する・同時sideloadは3アプリまで・App IDは7日あたり10個まで）は、いずれも一般に知られている値であり本プロジェクトでは未検証である。**参加者への配布はできない**（各自が7日ごとに再署名するのは非現実的）。したがって$99の支出判断は「発起人自身が実機で使えれば十分か、参加者にも配布するか」で決まる。

### 4. 問題パック・音声の配置（J-82）

**アプリに同梱する**（`content/` 現状51MB）。GitHub Pagesからの取得はしない。

決め手は3つある。初回起動時点から完全オフラインで成立する。WKWebViewで `caches` APIが使えるかという未検証リスクを回避できる。実装量がほぼゼロである（`packages/app/scripts/copy-content.mjs` が `content/` を `dist/` へコピーし、Capacitorは `dist` を webDir として同梱する）。

代償として、コンテンツ追加ごとに再配布が必要になることを受容する。

### 5. スパイクの位置づけ（T-146）

ネイティブ化に着手する場合、最初のタスクはWKWebViewの未検証項目を潰すスパイクとする。性格は「出荷可能なアプリの構築」ではなく技術検証であり、その結果が$99の支出判断の入力になる。

現時点では**保留中**であり、着手条件はT-149の完了と発起人による再判断である。

### 6. 調整可能パラメータのリモート配信

配信方式は本ADRの対象外とする。docs/23のT-148として起票し、**詳細設計は実装PRと同じPRで別ADRに記録する**（adr/README.md の「判断を実装に反映するPRと同じPRに含める」規則に従う）。

## 影響・トレードオフ

- **ストレージ退避の解消は先送りになる。** Web Pushで解決するのは通知だけである。ホーム画面追加のPWAはSafariタブより退避されにくく、iOS 17以降さらに改善しているとされるが、完全な解消ではない（未検証）。エクスポート／インポートによる保険は引き続き唯一の対策である。
- **バックグラウンド音声再生も先送りになる。** 画面ロック中の聞き流し継続は、ネイティブ化に着手しない限り実現しない。
- **プライバシー境界の運用が1段複雑になる。** これまで共有APIに送る個人紐づき情報は「ダメージ換算値＋表示名」だけだった。push購読が加わるため、以後は「購読情報がダメージ・表示名と結合していないこと」を維持条件として見張る必要がある。
- **上位文書（05の7節・06のM5項）の前提記述が古くなる。** 「iOSのPWAではスケジュールされたローカル通知が打てない」は事実として残るが、それがネイティブ化の主動機であるという論証は成立しなくなった。影響範囲が広いため本ADRおよびdocs/23では改訂せず、docs/23の9節に残課題として記録した。T-149の実測結果が出た時点で書き換えるのが妥当である。
- **見直す条件**: T-149の効果測定（H-11）で週次学習日数の改善が確認できない場合、通知そのものの価値を疑う段階に戻る。改善が確認できた場合は、ネイティブ化で追加的に得られるもの（ストレージ退避の解消・バックグラウンド音声）に対して$0のスパイク（T-146）を実施し、$99の支出可否を判断する。
