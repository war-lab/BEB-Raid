# 0007. 通知手段の選択とM5ネイティブ化の前提（Web Push先行・ネイティブ化はiOS限定で保留）

- **日付**: 2026-07-27
- **ステータス**: 承認済み（発起人が2026-07-27に決定）
- **関連**: docs/23_M5ネイティブ化計画.md（J-72・J-82・J-85・J-86・J-87・T-149・T-146・H-12）、docs/05_アーキテクチャ設計.md 7節、docs/06_ロードマップ.md 3節、docs/02_機能設計.md 7節
- **改訂**: 2026-07-27 Amendment（J-87。効果検証を2段構えにする）を末尾に追記。判断1の正文は同Amendmentが上書きする

## 背景

発起人が2026-07-27にM5（Capacitorネイティブ化）の実施を決定した。その直後、着手前の調査で前提が複数崩れていることが判明した。

ネイティブ化の主動機は、05の7節が記述する「iOSのPWAではスケジュールされたローカル通知が打てない」という制約である。SRS期限・ストリークの通知を実現するにはWeb Push＋サーバー側cronが必要になり、これはサーバーレス方針と衝突する、という論証だった。

この論証には評価漏れがあった。**iOS 16.4以降、ホーム画面に追加したPWAはWeb Pushを受け取れる。** ローカルのスケジュール通知はWeb APIに依然存在しないが、サーバー起点のpushで代替しうる。

docs/23のJ-76はWeb Push＋サーバーcronを代替案として挙げて棄却しているが、その棄却は「ネイティブ化する前提の中で通知をどう実装するか」の比較としてのみ行われた。「ネイティブ化を回避する手段」としては評価していない。

あわせて、費用と実機検証の前提も整理が必要だった。Apple Developer Program（$99/年）は、無料の徹底を優先したTTS調達（06の3節のB-2でPiperを選定）とは方針が異なる継続支出である。

## 検討した選択肢

### 案A: 予定どおりネイティブ化を先に進める

- 利点: 通知・ストレージ退避・バックグラウンド音声の3つを一度に解消できる。
- 欠点: 通知の効果が未検証のまま、Capacitor・CI・署名・再署名運用という重い仕組みを抱える。docs/23のJ-71が「実測してからゲート判定する」順序を求めていたのに、実測の機会を作らずに運用を確定させることになる。

### 案B: iOS PWAのWeb Pushで通知の効果を先に実測し、ネイティブ化の着手を保留する

- 利点: 費用と運用コストがゼロ（$99・署名・審査・7日ごとの再署名・Xcode・macOSランナーのいずれも不要）。J-71が本来求めていた順序を初めて実行できる。効果が出なければネイティブ化そのものを見送れる。
- 欠点: プライバシー境界に触れる（push購読endpointという個人紐づき識別子が増える）。Service Workerの構成変更が必要で、既存のPWAキャッシュ挙動への回帰リスクがある。通知が共有APIに依存する。ネイティブ化の動機のうち「ストレージ退避の解消」は解決しない。

### 案C: 通知を諦める

- 利点: 何も作らずに済む。
- 欠点: SRS学習は「期限が来たことに気づく」ことが前提であり、通知の欠如は学習継続率に直結する。01の目的（380→760）に対して放置できない。

## 判断

**案Bを採る。** 加えて、ネイティブ化に進む場合の前提を以下のとおり確定させた。

### 1. 通知手段の順序（J-85）

M5の着手を保留し、先にiOS PWAのWeb Pushで通知の効果を実測する（T-149）。着手可否とスコープはその結果で再判断する。M5の実施決定自体は撤回していない。

決め手は、案Aが「効果の不明な機能のために不可逆な運用コストを先に確定させる」構造になっていた点である。案Bは同じ目的を$0で先に試せる。

### 2. Web Pushに課す制約（J-86）

- **通知本文は件数を含まない汎用文に限定する。** 「今日の復習n件」をサーバーが送るには各人の復習件数をサーバーが知る必要があり、不変条件（個人紐づきで共有APIに送るのはダメージ換算値＋表示名のみ）に正面から反する。
- **購読情報は `deviceToken` と結合できない形で保存する。** 結合すると、レイド貢献（表示名＋ダメージ）と通知購読が同一キーで結び付き、個人単位の学習行動をサーバー側で推定できるようになる。具体的な保存方式はT-149で設計する（本ADR時点では未確定）。
- 通知が使えない状態（権限拒否・共有API停止・購読失敗）でも学習機能を一切劣化させない（05の1節の縮退設計）。

### 3. ネイティブ化の対象プラットフォームと費用（J-72）

- **iOSのみ**を対象とし、Androidは初回スコープから外す。ネイティブ化の動機であるスケジュール通知の欠如はiOS固有であり、Androidの退路はPWA継続が担う。
- **Apple Developer Program（$99/年）には登録しない。** 動作確認の範囲はiOSシミュレータと、発起人自身の実機（無料Apple IDでのsideload）とする。
- iOSビルドは GitHub Actions の macOSランナーで行う（ローカル環境はWindowsでXcodeが使えない）。publicリポジトリのため無償枠内で収まる想定だが、**未検証**である。
- 無料署名の制約（プロビジョニングプロファイルが7日で失効する・同時sideloadは3アプリまで・App IDは7日あたり10個まで）は、いずれも一般に知られている値であり本プロジェクトでは未検証である。**参加者への配布はできない**（各自が7日ごとに再署名するのは非現実的）。したがって$99の支出判断は「発起人自身が実機で使えれば十分か、参加者にも配布するか」で決まる。

### 4. 問題パック・音声の配置（J-82）

**アプリに同梱する**（`content/` 現状51MB）。GitHub Pagesからの取得はしない。

決め手は3つある。初回起動時点から完全オフラインで成立する。WKWebViewで `caches` APIが使えるかという未検証リスクを回避できる。実装量がほぼゼロである（`packages/app/scripts/copy-content.mjs` が `content/` を `dist/` へコピーし、Capacitorは `dist` を webDir として同梱する）。

代償として、コンテンツ追加ごとに再配布が必要になることを受容する。

### 5. スパイクの位置づけ（T-146）

ネイティブ化に着手する場合、最初のタスクはWKWebViewの未検証項目を潰すスパイクとする。性格は「出荷可能なアプリの構築」ではなく技術検証であり、その結果が$99の支出判断の入力になる。

現時点では**保留中**であり、着手条件はT-149の完了と発起人による再判断である。

### 6. 調整可能パラメータのリモート配信

配信方式は本ADRの対象外とする。docs/23のT-148として起票し、**詳細設計は実装PRと同じPRで別ADRに記録する**（adr/README.md の「判断を実装に反映するPRと同じPRに含める」規則に従う）。

## 影響・トレードオフ

- **ストレージ退避の解消は先送りになる。** Web Pushで解決するのは通知だけである。ホーム画面追加のPWAはSafariタブより退避されにくく、iOS 17以降さらに改善しているとされるが、完全な解消ではない（未検証）。エクスポート／インポートによる保険は引き続き唯一の対策である。
- **バックグラウンド音声再生も先送りになる。** 画面ロック中の聞き流し継続は、ネイティブ化に着手しない限り実現しない。
- **プライバシー境界の運用が1段複雑になる。** これまで共有APIに送る個人紐づき情報は「ダメージ換算値＋表示名」だけだった。push購読が加わるため、以後は「購読情報がダメージ・表示名と結合していないこと」を維持条件として見張る必要がある。
- **上位文書（05の7節・06のM5項）の前提記述が古くなる。** 「iOSのPWAではスケジュールされたローカル通知が打てない」は事実として残るが、それがネイティブ化の主動機であるという論証は成立しなくなった。影響範囲が広いため本ADRおよびdocs/23では改訂せず、docs/23の9節に残課題として記録した。T-149の実測結果が出た時点で書き換えるのが妥当である。
- **見直す条件**: T-149の効果測定（H-11）で週次学習日数の改善が確認できない場合、通知そのものの価値を疑う段階に戻る。改善が確認できた場合は、ネイティブ化で追加的に得られるもの（ストレージ退避の解消・バックグラウンド音声）に対して$0のスパイク（T-146）を実施し、$99の支出可否を判断する。

## 2026-07-27 Amendment: 効果検証を2段構えにする（J-87）

本節は上記本文の判断1（通知手段の順序）に対する差分である。本文の記述は当時の判断としてそのまま残し、以後の正文は本節とする。詳細は docs/23 の1.7.2〜1.7.5節・1.8節。

### 決定

**T-149（Web Push実装）の前段に、コストゼロの手動検証を置く。** 検証を2段構えにする。

1. **第1段（新規・先行。H-12）**: 発起人がiPhone標準のリマインダーまたはアラームを毎朝セットし、**2週間**運用する。アプリ側の実装は一切行わない（コード0行）。検証する仮説は「リマインドされると学習日数が増えるか」。
2. **第2段（T-149）**: 第1段で効果が確認できた場合に限り、Web Pushを実装する。効果が確認できなければ、**Web PushもCapacitorのローカル通知（T-135）も作らない**という判断があり得る。

案Bを採るという本文の判断は撤回していない。実測の手段としてWeb Pushを置く順序を1段後ろにずらす変更である。

### 根拠

**最大の理由は、Web Pushでは負の結果が解釈不能になることである。** AppleはiOS PWAへのWeb Pushの配送タイミングを保証していない（一次情報を確認できておらず**未検証**）。到達記録が無ければ「学習日数が増えなかった」が効果の不在なのか未到達なのかを切り分けられない。手動アラームなら到達が確実なので、増えなかったという結果もそのまま解釈できる。

残る根拠は3つある。

1. 検証したい仮説は「リマインドが学習日数を増やすか」であり、**配送手段がWeb Pushかネイティブのローカル通知かは仮説の本質ではない**。手段に投資する前に仮説そのものを検証できる。
2. **測定は遡及的に可能である。** `attempts` は追記のみで削除できない（`packages/app/src/db/` のDexieフックが実行時に遮断する）ため、週次学習日数は過去分を後から算出できる。**測定機構を事前に仕込む必要がない。** この事実により、docs/23のT-132が持っていた「ベースライン収集」の役割は判定基準の明文化に縮小した。
3. Web Push実装の作業量が想定より大きい（新規7ファイル・変更9ファイル規模。Service Workerの `generateSW` から `injectManifest` への方式移行を含む）。仮説が否定されるなら丸ごと不要になる。

### 第1段の限界

第1段は**方向性を見るための検証**であり、効果の大きさを測るものではない。

- 自分でセットしたアラームには「通知から1タップでアプリを開く」導線がない。実アプリの通知より効果が弱い可能性がある。
- 自分でセットした通知と外から来る通知では、慣れ方・無視のしかたが異なる可能性がある。
- n=1であり統計的な有意性は主張できない。交絡（季節性・繁忙期・自作バイアス・M4や読解の同時期改修）が残る。

したがって第1段で効果が出た場合も、判断に使うのは方向（増えたか・変わらなかったか）に限る。

### T-149に追加した必須要件

**到達ログを持たないT-149の実装は承認しない。** 通知本文または `tag` に受信時刻を入れて目視で記録する方式を採る（IndexedDBに依存しない方式にする理由は、iOSでService Workerのpushハンドラから `indexedDB` が `undefined` になる報告があるため。Apple Developer Forums thread 769794、iOS 18.1.1。Appleの応答・WebKit bugzillaの対応項目・回避策のいずれも確認できておらず、iOS 26での修正状況は**未検証**）。

### 判断1に対する補足（却下理由の不成立）

本文および docs/05 の7節・docs/23 のJ-76が挙げた却下理由「Web Push＋サーバーcronはサーバーレス方針と衝突する」は、**現在は成立していない**。M3で Cloudflare Workers + KV + Durable Objects とcronが既に本番稼働しており（`packages/api/wrangler.toml` の `[triggers] crons`。**2026-08-06訂正・T-358・K-92**: 曜日式`0 0 * * 1`は本番不発の原因になったため`0 0 * * *`の日次発火へ是正済み。`.github/workflows/api-deploy.yml`）、日次cronの追加はゼロからサーバーを立てる話ではなく、既に稼働実績もある。

docs/05の改訂は影響範囲が広いため、docs/23の9節の残課題（上位文書の前提記述の更新）に含めて扱う。

### 判断2（J-86）に対する補足

購読情報を `deviceToken` と結合しない保存方式は、既存の `questionStats` と同じ構造的手段を採る（`packages/api/src/index.ts` のroute側で `handlePostStats` に `auth.deviceToken` を渡さない、`packages/api/src/statsDo.ts` の `question_stats` 表にdeviceToken列を持たせない）。

**ただし完全な非結合は達成できない。** 同一IPかつ近接時刻での相関は可能であり、KVレコードの `createdAt` やCloudflareのログが手がかりになる。到達すべき水準は「構造的に結合できない」ではなく「**結合するコードを書いていない**」であり、この差を文書とコードコメントに明記する。

あわせて、push subscription（`endpoint`・`p256dh`・`auth`）は不変条件の文面（個人紐づきで送るのはダメージ換算値＋表示名のみ）に収まっていない。`endpoint` は正誤詳細・レート実値・本名・社名のいずれでもないため即却下ではないが、**文面を拡張する判断が必要**である。これはJ-86の判断材料であり、本Amendment時点では未決である。

### T-149の前提条件（別対応）

`packages/api/src/index.ts` の `scheduled` ハンドラが `controller.cron` を見ずに無条件で `generateWeeklyBoss` を呼んでいる。**未修正のまま日次cronを追加すると `emaDailyDamage` の平滑化が毎日走り、レイド難易度調整が無症状で壊れる。**

**2026-08-06訂正（T-358）**: この修正は完了済み。`scheduled`は`controller.cron`の値で`switch`分岐する実装になっており、週次ボス生成のcron式自体も`0 0 * * *`の日次発火へ是正済み（`index.ts`の該当コメント参照）。T-149の前提条件は解消したが、Web Push用の新規cronを追加する際は同じ`switch`に分岐を1本足すこと。

### 見直す条件（更新）

第1段（H-12）で週次学習日数の増加が確認できない場合、T-149とT-135のいずれも実施せず、通知そのものの価値を疑う段階に戻る。増加が確認できた場合はT-149へ進み、以後は本文の「見直す条件」に従う。
