# 0009. 誤タップ救済のための解答永続化の遅延（取り消し猶予400ms）

- **日付**: 2026-07-29
- **ステータス**: 承認済み
- **関連**: docs/05 6節（オフラインが正常系）・CLAUDE.md の不変条件（解答は即時保存・attempts は追記のみ）・docs/03 7.2節（当て勘判定）

## 背景

`DrillScreen` は選択肢をタップした瞬間に解答を確定する。
`finalizeAnswer` が同期的に `setResult` して色と✓✕を出し、続けて `recordAnswerPipeline` が `attempts` に書き込む。
再解答は `if (result) return` で遮断される。

`attempts` は追記専用で、Dexie のフックが削除と更新を実行時に遮断している。
つまり一度書かれた解答は取り消せない。

この組み合わせは、揺れる電車内での誤タップが即座に、かつ不可逆に誤答として記録されることを意味する。
影響先はレート・SRS のスケジューリング・弱点タグ統計・レイドダメージで、いずれも学習の方向を決める値である。

## 検討した選択肢

### 案A: 永続化を短時間遅らせ、その間だけ取り消しを出す（採用）

視覚フィードバックは即時のまま、`attempts` への書き込みだけを400ms遅らせる。
猶予中は「取り消し」を出す。

利点は、まだ書いていないので追記専用の不変条件を破らずに済むこと、テンポが変わらないこと。
欠点は、`DrillScreen` に未確定状態という新しい状態が増えること。

### 案B: 色と✓✕の表示も遅らせ、同じ問題への再解答を許す

利点は、正誤を見る前に取り消せるので同じ問題に再挑戦できること。
欠点は、全問のフィードバックが400ms遅れてテンポが落ちること。
現在の即時描画は「電車内で読み取りやすい」ことを狙った設計なので、これを捨てる代償が大きい。

### 案C: 取り消し後もその場に留まり、再解答を許す

案Aと同じく永続化を遅らせるが、取り消したら同じ問題をもう一度解けるようにする。

これは採れない。
視覚フィードバックが即時である以上、取り消しを押す時点で正解が既に見えている。
見た後の再解答を許せば `attempts.isCorrect` が偽陽性になり、同時期に進めた測定精度の改善（語彙の提示順・ダミーの同質化）を自分で壊すことになる。

## 判断

案Aを採る。

**取り消しの意味は「この解答を記録せず、次の問題へ進む」**とする。
`attempts` を書かずに `advanceSession` でその item を消化し、非モーダル通知「この解答は記録しませんでした」を出す。
救済されるのは「誤タップの誤答がレート・SRS・弱点統計・レイドダメージに残ること」だけで、正解の取得はできない。

猶予は **400ms**、対象は **`text_blank` と `audio_qa`** に限る。
`text_blank` は制限時間が無く片手タップの誤タップが最も多い。
`audio_qa` も誤タップの主戦場だが、**時間切れ経路は猶予を挟まず即記録する**。
時間切れは誤タップではなく、猶予を入れると「タイマー切れを取り消す」抜け道になるためである。

`audio_set` のサブ設問は対象外とした。
`subQuestionResults` と `computeSetResult` の巻き戻しが2系統になり、効果より複雑さが勝つ。
`dictation` は「確定」が既に二段確認になっている。
`vocab_card` は4択タップの時点でまだ書き込みが起きておらず（記録は自己評価タップ時）、誤タップ救済の設計そのものが別問題になる。

**猶予中は解説・「次へ」・「ここで終了して結果を見る」を出さない。**
出すと取り消し前に解説と英文全体を読めてしまう。
猶予中に出すのは選択肢の色と✓✕、そして取り消しボタンだけである。
「ここで終了して結果を見る」を確定後に限ることで、アンマウント時のflushと `navigate('result')` の競走も同時に防げる。

**アンマウント時（中断・途中終了・読解画面への切替）は破棄せず記録する。**
解答は実際に行われており、`attempts` は分析の基盤なので捨てる方が損失が大きい。
`answerCurrentQuestion` が attempt と snapshot を同一トランザクションで進めるため、途中離脱でも「解答済みなのに再出題」「未解答なのにスキップ」のどちらも起きない。

`beforeunload` は扱わない。
IndexedDB への同期書き込みができないためで、未書き込みなら次回のセッション再開時に未解答として再出題される。
これはオフラインを正常系とする既存方針と整合する。

**`responseMs` はタップ時刻で確定させる。**
commit 時刻で計算すると猶予分の400msが乗り、`GUESS_THRESHOLD_MS = 2000` の当て勘判定（docs/03 7.2節）を跨いで結果が変わる。
同時期に当て勘をリザルトへ表示するようにしたので、ここがずれると学習者に見える数字が変わる。

## 影響・トレードオフ

不変条件「解答・SRS更新は IndexedDB へ即時保存」（CLAUDE.md・docs/05）を400msだけ意図的に緩めた。
緩和幅を固定の短時間に限り、アンマウント時にflushすることで、「解答したのに残っていない」状態が持続しないようにしている。

設定 `mistapUndoEnabled` で無効化できる（既定ON）。
`SettingsScreen` にトグルを置いた。
導線のない設定は使われないまま腐る（`vocabAutoPlayPhrase` が実際にそうなった）ため、設定を作るなら画面も同時に用意する。

テストへの影響が実装上の最大のリスクだった。
`DrillScreen.test.tsx` の共通ヘルパ `answerAndSettle` は40箇所以上から使われており、400msが入ると全体が遅く不安定になる。
既存テストは Dexie のデッドロックを避けるために `setTimeout` を意図的にフェイクしていないので、一律フェイクの逃げ道もない。
そこで共通の `setupSession` で設定をOFFにし、猶予そのものの検証だけ専用の describe でONにする形にした。
既存テストは無改修・遅延ゼロのまま通る。

400msという値は推定で、実機の親指操作で「気づいて取り消せる」時間かは未検証である。
ドッグフードのプレイテストで調整する（`PARTIAL_AUDIO_DURATION_MS` と同じ扱い）。

将来見直す条件は、`audio_set` のサブ設問にも誤タップの訴えが出た場合である。
そのときは `subQuestionResults` の巻き戻しを含めた設計をやり直す必要がある。
