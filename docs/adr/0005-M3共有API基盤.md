- **日付**: 2026-07-17
- **ステータス**: 承認済み（J-45〜J-50は発起人が2026-07-17に推奨案で一括承認。J-32のGO判断も同日）

## 背景

M3（共有API・レイド機能）は 06_ロードマップ で5行しか定義がなく、実装着手に足りる設計の穴が複数あった（API契約・認証方式・ダメージ係数・ボスHP入力・帰属ルール・週次運転トリガー）。14_改善提案 4.2〜4.3節で判断リストとWorkers側の設計方針を整理し、16_M3タスク分解 でJ-45〜J-50として確定案・代替案・リスクを併記した。本ADRはその判断が承認されたことを受け、Workers側の技術構成を正式に記録する。

## 検討した選択肢

### KVへのattempt単位書込 vs Durable Object集約

- KV書込の無料枠は1,000回/日。20人×50問/日をattempt単位でKVに書くと初日で枠を使い切る。
- 採用: レイドHP・damageLogs・冪等キー管理は**週次ボス1体=1 Durable Object（SQLiteストレージ）に集約**し、KVは招待コード・members等の低頻度データに限定する。クライアントもattempt単位でなくセッション終了時バッチ送信にする。

### 認証方式

- JWT等のトークン失効機構を持つ本格認証は、M3の目的（小規模レイド）に対し実装コストが過大。
- 採用: 招待コード1個（Secrets環境変数）を配布し、初回アクセスでdeviceToken（端末が既に発行済みのUUID）をKVに登録。以後はdeviceTokenのみで認証する最小構成（J-46）。

### API契約の管理方式

- OpenAPI等の別スキーマ言語の導入は型生成ツールチェーンが増え、Sonnetクラスの自走コストが上がる。
- 採用: shared-schemaに送信専用型（DamageSyncPayload等）を定義し、app/api双方がimportする単一正本方式（04と同じ思想。J-45）。

## 判断

1. **1週間ボス=1 Durable Object（SQLite）**。テーブルは`state`（1行）と`damage_attempts`（attemptId主キー・INSERT OR IGNOREで冪等）。現在HPは`maxHp - SUM(damage)`で都度SQL集計する。
2. **冪等性**: バッチ送信のレスポンスに受理済みattemptId一覧を返し、クライアントは全件受理確認後にpendingSyncから削除する（送信途中切断でも安全に再送可能）。
3. **packages/api新設**: wrangler.toml＋TypeScript＋vitest（`@cloudflare/vitest-pool-workers`。DO含めローカルでテスト可能）。shared-schemaをapp/api双方から参照。デプロイはGitHub Actions＋`CLOUDFLARE_API_TOKEN`（Secrets）。dev/production 2環境。
4. **CORS/SW**: Pages（`https://war-lab.github.io`）とWorkers（`*.workers.dev`）は別オリジンのためCORS必須（`ALLOWED_ORIGINS`環境変数の完全一致照合＋プリフライトOPTIONS対応）。vite-plugin-pwaのランタイムキャッシュがAPIドメインを捕捉しないことをT-96で確認する。
5. **時刻基準**: ボスの`startAt`/`endAt`はサーバーがepoch msで配る。期間判定はサーバー受信時のansweredAt照合＋サーバー側クランプ（クライアント時計を信用しない。J-49）。
6. **ダメージ式のモード係数**: `{ raid: 1.0, solo: 0.5, srs: 0 }`で確定（J-47。T-89の仮値をそのまま採用）。03の6.1に係数表として追記する（本ADRと同PR）。
7. **ボスHPの討伐率係数**: 03の6.2で既に確定済みの0.85をそのまま使う（J-48の実装で新たな値を作らない）。

## 影響・トレードオフ

- DO SQLiteの5GB無料枠に対し週次ボス1体分のattemptId表＋damageLogsは数MB程度で十分（16の2節の見積り）。
- KVはmembers等の低頻度データに限定するため、参加者が数百人規模に増えた場合は読取枠（100,000回/日）の再見積りが必要になる（M3の想定=20人規模では問題ない）。
- 招待コード方式は失効・再発行が「コード再配布→再登録」の手動運用にとどまる。参加者が増え運用負荷が高まったら本格認証への切替を再検討する。
- サーバー時計基準の期間判定により、クライアント側の時計ズレやなりすましによるダメージ捏造を防ぐ一方、オフライン滞留分の正当な遅延到着は期間内なら加算される（J-49）。
