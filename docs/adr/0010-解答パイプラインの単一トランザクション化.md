# 0010. 解答パイプラインの単一トランザクション化（J-35の見直し）

- **日付**: 2026-07-31
- **ステータス**: 承認済み
- **関連**: docs/15 3節 J-35（当初の判断）・docs/28 T-176（保存失敗時の再試行）・CLAUDE.md の不変条件（縮退設計・attempts は追記のみ）

## 背景

`recordAnswerPipeline` は1問の解答を6段で書く。

1. attempt記録（`answerCurrentQuestion` または `recordAttempt`）
2. 誤答なら `processWrongAnswer`（key単語をSRS復習デッキへ）
3. `updateTagStatsForAnswer`
4. `applyRatingUpdate`
5. `reviewSrsCard`
6. レイドダメージを `pendingSync` へエンキュー

J-35 は「①の原子性は `answerCurrentQuestion` 内で確保済み」として②以降を含む単一トランザクション化を見送り、失敗時は呼び出し側がエラーバナー＋スナップショット再読込で回復する方針にした。見送りの理由はDexieのストア跨ぎコストである。

この設計は**部分書き込みを許す**。①が成功して④で失敗すると、attemptは残りレートは未更新のまま残る。スナップショットの再読込ではこのずれは修復されない。

T-176（docs/27 のS-27）で「保存を再試行する」をUIに出したことで、これが実害になった。レビューで指摘された内容は次のとおり。

- **Reading経路**（snapshotなし・`recordAttempt`）: ①成功後に後段が失敗すると、再試行でパイプライン全体が再実行され**同じ解答のattemptがもう1件増える**。
- **Drill経路**（snapshotあり・`answerCurrentQuestion`）: ①でattemptとsnapshotを進めた後に後段が失敗すると、再試行は `StaleSnapshotError` で弾かれ、**失敗した④⑤は永久に補完されない**。

attempts・ratings・srsCards は学習履歴の正本であり、二重化も欠損も許容できない。

## 検討した選択肢

### 案A: ①〜⑤を単一トランザクションにする（採用）

失敗時は何も書かれないので、同じ入力での再試行が構造的に冪等になる。部分書き込みという状態自体が消えるため、T-176の再試行だけでなくJ-35時代から潜在していたずれも同時に解消する。

Dexieのコスト懸念は残るが、①〜⑤は元々6回の個別トランザクションを張っていた。1回に束ねる方が往復は減る（実測はしていない。判断はコストではなく正しさを優先した）。

### 案B: attempt IDで冪等化する

決定的なattempt IDを使い、再試行時は既存のattemptをスキップする。①の重複は防げるが、**Drill経路のsnapshot前進は巻き戻らない**ため `StaleSnapshotError` の問題が残る。①をスキップする分岐＝実質的な段階管理が別途必要になる。

### 案C: 完了した段を記録して未完了分だけ再開する

正しく作れるが、パイプラインに段階の状態を持たせる設計変更が要る。案Aで同じ効果が得られるうえ実装量は少ない。

### 案D: 再試行UIを撤回する

S-27（正解を見せた後に再解答を求める）に戻る。部分書き込みのリスクもJ-35時代のまま残るため、問題を隠すだけになる。

## 判断

**①〜⑤を単一のDexieトランザクションで書く。**

トランザクションに含めるテーブルは `attempts` / `settings` / `srsCards` / `tagStats` / `ratings` / `ratingHistory` である。内側の各エンジンも `db.transaction` を張るが、Dexieの入れ子は親へ join するため、**親のスコープに内側が使う全テーブルを列挙する必要がある**（漏れると内側で例外になる）。

**⑥ pendingSync のエンキューはトランザクションの外に置き、失敗を飲み込む。**

レイドダメージは共有API向けの副作用である。その失敗で学習記録を巻き戻すのは縮退設計（共有APIが全損してもソロ学習は無傷）に反する。⑥が失敗した解答分のダメージは失われるが、送信自体が「pendingSyncキュー経由の冪等送信」で取りこぼしを許す設計になっている。

従来は⑥の失敗もパイプライン全体の例外になり、UIがエラーバナーを出していた。この挙動は変わる（解答は成立し、警告ログのみ）。

## 影響・トレードオフ

J-35の「トランザクション境界は現状維持」を上書きする。docs/15 の当該記述は当時の判断としてそのまま残し、以後の正本は本ADRとする。

`recordAnswerPipeline` の外形（引数・戻り値）は変えていないため、呼び出し側（DrillScreen・ReadingScreen・VocabScreen）の改修は不要である。

トランザクションが長くなるぶん、同一DBへの並行書き込みは待たされる。1問の解答は数十msの処理でユーザー操作に対して十分速く、同時書き込みを行う他の経路（バックグラウンド同期は `pendingSync` と `raidState` のみを触る）とはテーブルが重ならない。

**Dexieトランザクション内では非Dexieのawaitを挟めない**という制約が新たに効く。①〜⑤の各段はDexie操作のみであることを確認して採用した。将来ここに `fetch` 等を足す場合は、トランザクションの外へ出すか `Dexie.waitFor` を使う必要がある。

検証は「後段の失敗でattemptも巻き戻る」「同じ入力で再試行するとちょうど1件書かれる」「Drill経路で同じsnapshotのまま再試行できる」「pendingSyncの失敗では解答が成立する」の4件を `answerPipeline.test.ts` に、UI経路の冪等性を `ReadingScreen.test.tsx` に置いた。**従来のテストは「①自体が失敗する」ケースしか見ておらず、途中成功を検証していなかった**（レビュー指摘）。
