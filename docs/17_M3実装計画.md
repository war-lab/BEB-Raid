## 2. 全タスク共通ルール（ガードレール）

**[13の2節](13_M2実装計画.md)（さらに上流は [10の2節](10_F4-F6実装計画.md)）を全面的に継承する**。M3での差分・上書きは以下のとおり。

### 2.1 ブランチ運用（13の2.4の上書き）

- **M3タスクはdev直コミット禁止**。M2ブラッシュアップの別セッションが同一リポジトリで並走しているため、必ず `task/T-9x-説明` ブランチで作業し、dev への **PR（ドラフト作成→CI通過→マージ）** で入れる（発起人判断 2026-07-17）。
- 着手時に必ず `git fetch` して**最新の dev から分岐**する。同一作業ツリーで別セッションが作業中の場合（`git status` に自タスクと無関係の変更がある場合）は、`git worktree` で作業ツリーを分離してから着手する。
- **触ってよい領域**: `packages/api/`（新設）・`packages/shared-schema/`（T-91のみ）・`packages/app/` のシート記載ファイル・`docs/`・`.github/workflows/`。**`packages/cli/` と `content/` はM2セッションの作業領域なので触らない**（必要になったら停止）。
- 契約変更（T-91）は09の2節どおり**契約変更のみの単独PR**とする。

### 2.2 新規依存の方針（13の2.3の上書き）

- **許可済み新規依存（packages/api の devDependencies のみ）**: `wrangler`・`@cloudflare/workers-types`・`@cloudflare/vitest-pool-workers`・`vitest`（api用設定）。バージョンは着手時の最新安定版。
- **packages/app・packages/shared-schema への新規依存はゼロ**（M2と同じ原則）。API呼び出しは fetch 直呼びで実装する。
- これ以外が必要になったら停止して人間に確認。

### 2.3 不変条件（毎タスクで回帰確認する）

1. **縮退設計**: `VITE_RAID_API_BASE_URL` 未設定（API無効）のとき、ソロ学習の動作・表示が一切変わらないこと。全タスクの完了条件に「API無効時の既存テスト全通過」を含める（16の3節冒頭・05の1節）。
2. **プライバシー境界**: 共有APIへ送る個人紐づきデータは `DamageSyncPayload`（ホワイトリスト照合テスト済み）と表示名のみ。questionStats・報告は deviceToken と結合できない形でのみ保存する（04の4節）。
3. **attempts追記のみ**・オフライン正常系（04）。
4. **publicリポジトリにシークレットを置かない**: 招待コードは wrangler secret、CloudflareトークンはGitHub Secrets のみ。テスト・例示はダミー値であることを明記する。`.dev.vars` は gitignore する。

### 2.4 停止規則（Sonnet運用の要）

- シート・3節に無い設計判断が必要になったら停止する。
- Cloudflareの無料枠・API仕様が16の2節の前提（KV書込1,000回/日等）と食い違うことを発見したら停止する。
- 完了条件を1つでも満たせない場合、条件を勝手に緩めず停止して報告する。

## 3. 事前決定事項（J-45〜J-50の正文＋実装方式）

16の1節の判断（承認済み）を実装可能な水準まで具体化する。数値・命名はすべて本節が正本（変更する場合は本節を直す）。

### 3.1 API契約（J-45）

エンドポイントは以下の6本のみ。認証は `Authorization: Bearer <deviceToken>` ヘッダ（3.2節）。

| メソッド/パス | 認証 | リクエスト | レスポンス（200） | 実装タスク |
|--------------|------|-----------|------------------|-----------|
| GET `/health` | なし | — | `{ ok: true }` | T-90 |
| POST `/register` | 招待コード | `RegisterRequest`（inviteCode・deviceToken・displayName・dailyGoal） | `{ ok: true }` | T-92 |
| GET `/raid/current` | Bearer | — | `RaidBossState`（404=今週のボス未生成） | T-95 |
| POST `/raid/sync` | Bearer | `RaidSyncRequest`（payloads: DamageSyncPayload[]） | `RaidSyncResponse`（acceptedIds・boss） | T-95 |
| POST `/stats/questions` | Bearer | `QuestionStatsRequest`（stats: QuestionStatPayload[]） | `{ accepted: number }` | T-100 |
| POST `/reports` | Bearer | `QuestionReportPayload`（questionId・reason） | `{ ok: true }` | T-101 |

- 型は全て shared-schema に定義し、app/api 双方が import する（T-91。単一正本方式）。
- エラー形式は `{ error: { code: string, message: string } }` に統一。401=未登録/誤コード、400=型不正、404=ボスなし。
- **`DamageSyncPayload` に `answeredAt`（epoch ms）を追加する**（T-91）。現行のT-89実装（attemptId・bossId・damage・questionCount）にはこれが無く、J-49の「answeredAtがボス期間内なら期限後受信でも加算」がサーバー側で判定できないため。answeredAt はダメージの帰属時刻であり、個人単位の正誤詳細には当たらない（04のプライバシー境界の範囲内。damageLogs に answeredAt 列を追記=04も更新）。
- レスポンスの `RaidBossState` は貢献表示（02のレイド画面要件）のため `contributions: { displayName, damage }[]` を含む。表示名＋ダメージ換算値のみで04の境界内。

### 3.2 認証・登録（J-46）

- 招待コードは **wrangler secret `INVITE_CODE` 1個**。漏洩時は `wrangler secret put` で再設定し、参加者へ再配布（手動運用）。ローカル開発・テストは `.dev.vars`（gitignore対象）にダミー値を置く。
- deviceToken は**端末側で既に発行済み**（`profile.deviceToken`。M1で「発行のみ・送信しない」として実装済み=04の3節）。登録APIは新規発行ではなく、**端末のtokenをKVへ登録する**方式とする。
- KVレイアウト: キー `member:<deviceToken>` → 値 `{ displayName: string, dailyGoal: 'light'|'normal'|'heavy', registeredAt: number, emaDailyDamage?: number }`（JSON）。members一覧は `list({ prefix: 'member:' })` で取得（20人規模なら読取枠に対し十分小さい）。
- 再登録（同一tokenでの再POST）は**上書き許容**とする（displayName・dailyGoal の変更手段を兼ねる。専用の更新APIを作らない）。
- 認証ミドルウェア: Bearer の deviceToken が KV に存在しなければ 401。クライアントは401を受けても **pendingSync を削除しない**（再登録後に再送で復旧）。
- バックアップ複製で同一tokenが2端末に載った場合は「同一人物の複数端末として合算許容」（14の4.4-⑤の割り切り）。荒れた場合の再発行手順=設定画面からのプロファイル再作成はM3では作らず、運用（手動DB操作）で対応。

### 3.3 ダメージとレイド対象（J-47 / J-47-2）

- モード係数は `{ raid: 1.0, solo: 0.5, srs: 0 }` で確定（`engine/damageConfig.json` に実装済み=T-89。03の6.1への係数表追記は T-90 のADR起票と同PRで行う）。
- **mode='raid' はS5レイド画面からの専用セッション起動のみに付与**する（J-47-2）。通常のクエスト・単独モードは solo のまま（係数0.5で貢献はする＝T-89実装どおり。1.0になるのはS5経由のみ）。
- レイド専用セッションの構成: `generateQuickPack` の**7分プリセットをそのまま流用**し、セッション開始時の mode を `'raid'` にするだけとする（出題内容はレイド専用に変えない。AttemptMode に 'raid' は定義済み）。

### 3.4 週次ボス（J-48 / J-49 / J-50）

- **bossId** = `boss-<ISO年>-W<ISO週番号2桁>`（例: `boss-2026-W30`）。ISO週の導出関数は api 内に実装しユニットテストを付ける。
- **生成**: Cloudflare Cron Trigger `0 0 * * mon`（UTC 0:00 月曜 = JST 9:00 月曜）で当週ボスを生成。`startAt` = 生成時刻、`endAt` = 同週金曜 15:00 UTC（= 金曜24:00 JST）。
- **クローズ**: 専用cronは設けない。DOがアクセスのたびに `hp <= 0`（討伐）または `now > endAt`（期限）から status（`active` / `defeated` / `closed`）を導出する。討伐済みボスは同週内は参照可能なまま残す。週明けは新ボス生成まで `/raid/current` が404を返す（端末側は raidState キャッシュで前回結果を表示できる）。
- **HP算出（J-48）**:
  - 申告値の換算表: `light=5問/日, normal=15問/日, heavy=30問/日`。
  - 参加者1人あたりの想定日次ダメージ = `emaDailyDamage`（KVのmemberレコード。前週実績あり）が存在すればそれ、無ければ `申告問題数 × DAMAGE_PER_QUESTION`。
  - `HP = round( Σ(全登録メンバーの想定日次ダメージ) × 5日 × BOSS_HP_FACTOR )`。下限 = `normal 1人分相当`（`15 × DAMAGE_PER_QUESTION × 5 × BOSS_HP_FACTOR`。登録0人週の異常値防止）。
  - `DAMAGE_PER_QUESTION`・`BOSS_HP_FACTOR`（**03の6.2で確定済みの討伐率係数=0.85をそのまま使う**。新値を作らない）は `packages/api/src/raidConfig.ts` に定数として外出しし、`$comment`相当のコメントで「暫定・実測調整」と由来を明記する。**DAMAGE_PER_QUESTION の初期値は実装時に導出する**: `engine/rating.ts` の basePoints 算出を難易度3・初期レート帯で実行するテストを一時的に書いて中央値を実測し、その値 × raid係数1.0 を転記する（導出過程をコメントに残す）。
  - **EMA補正**: 週次生成cronの中で、前週ボスDOから deviceToken 別ダメージ合計を取得し、`前週日次 = 合計 / 5` として `emaDailyDamage_new = 0.5 × 前週日次 + 0.5 × emaDailyDamage_old`（初回は前週日次をそのまま）をKVのmemberレコードへ書き戻す（書込は週1×人数分でKV枠に対し無視できる）。
- **帰属（J-49）**: 受理条件は `payload.answeredAt ∈ [startAt, endAt]`。バッチ受信が endAt 後でも answeredAt が期間内なら加算する。クライアント時計は信用しない: `answeredAt > 受信時刻 + 5分` のペイロードは受信時刻へクランプしてから判定する。
- **参加の表現**: サーバー側に join API は作らない（API極小）。HP算出の母数は**登録メンバー全員**、participantCount は damageLogs の deviceToken distinct 数とする。端末側の「参加」（S5の参加ボタン）は raidState 書込（joined=true）＋ `raidSyncEnabled` 設定ONのみ（T-89の既存ゲートと整合）。
- **ボスプロファイル**: M3では content 層に置かず、`packages/api/src/bossProfiles.ts` に静的ローテーション配列（10体程度。`{ name, flavor }`。TOEIC/ビジネス題材の架空モンスター名）を定義し、週番号で決定的に選ぶ。`profileJson` = このオブジェクトのJSON文字列（クライアントの raidState.profileJson と同形）。

### 3.5 Durable Object 設計（T-94）

- クラス `RaidBossDO`。**1ボス=1インスタンス**（`idFromName(bossId)`）。SQLiteストレージを使う。
- テーブル:
  - `state`（1行）: bossId, profileJson, maxHp, startAt, endAt, defeatedAt(null可)
  - `damage_attempts`: attemptId TEXT PRIMARY KEY, deviceToken TEXT, damage INTEGER, questionCount INTEGER, answeredAt INTEGER, receivedAt INTEGER
- 現在HP = `maxHp − SUM(damage)`（都度SQL集計。行数は週次20人×数百問規模で問題ない）。
- 冪等性: `INSERT OR IGNORE`（attemptId主キー）。レスポンスには**受理済みattemptId一覧**（今回受理＋既に受理済みだった重複分の両方）を返す。クライアントは一覧に含まれるIDのみ pendingSync から削除する。
- 討伐判定: 加算後に HP≤0 になった時点の受信時刻を defeatedAt に記録。討伐後・期限後のダメージは受理しない（acceptedIdsに**含めて**返す=クライアント側キューは掃除させるが、加算はしない。この区別のためレスポンスに `applied: boolean` は持たせず、HPが正の間に送る動機付けはUI側の表示で行う）。
- 週次クローズ後のデータ: 次週ボス生成cronがEMA集計を読み取った後も削除はしない（DO SQLiteは5GBまで無料。掃除はM4以降の運用課題とする）。

### 3.6 クライアント同期（T-96）

- **抽象化レイヤ**: 新規 `platform/net/RaidApi.ts` にインターフェースを定義し、fetch実装（`FetchRaidApi`）とテスト用フェイクを併設する（05の7節の差し替え可能レイヤ方針。外部API呼び出しはplatform実装内に閉じる=13の3.7の運用ルール踏襲）:

  ```ts
  interface RaidApi {
    isConfigured(): boolean
    register(req: RegisterRequest): Promise<void>
    fetchCurrentBoss(): Promise<RaidBossState | null>   // 404はnull
    syncDamage(payloads: DamageSyncPayload[]): Promise<RaidSyncResponse>
    sendQuestionStats(stats: QuestionStatPayload[]): Promise<number>   // T-100で追加
    sendReport(report: QuestionReportPayload): Promise<void>          // T-101で追加
  }
  ```

- **ベースURL**: ビルド時環境変数 `VITE_RAID_API_BASE_URL`。未設定または空文字なら `isConfigured()=false` とし、**レイド関連UIを一切表示せず通信もゼロ**（縮退の第一ゲート）。dev/prod のURL切替はビルド環境変数で行う。
- **送信サービス**: 新規 `services/raidSync.ts`。pendingSync の `kind='raidDamage'` を全件（1リクエスト上限200件。超過分は次回）読み、`syncDamage` → レスポンスの acceptedIds に含まれるレコードのみ削除 → レスポンスの boss で raidState を更新（`lastSyncedAt = Date.now()`）。
- **送信トリガー**は3箇所: ①セッション完了（ResultScreen表示後の非同期・失敗無視）②アプリ起動時（boot完了後の非同期・失敗無視）③S5の手動同期ボタン（失敗をUI表示する唯一の経路）。
- **失敗時**: ネットワーク失敗・5xxは何もしない（キュー保持・次トリガーで自然再送）。401は保持したまま raidState に要再登録フラグを立てず、S5表示時に「登録が無効です。招待コードで再登録してください」を出す（判定は同期時のエラー種別をメモリ保持でよい）。
- **SWキャッシュ**: vite-plugin-pwa は別オリジンへの runtimeCaching を既定では行わないことを `vite.config.ts` の workbox 設定で確認し、**APIオリジンを対象とする runtimeCaching を追加しない**ことをT-96の確認項目とする（確認結果をSTATUS.mdに記録。もし既定で捕捉される設定が見つかったら明示除外を追加）。

### 3.7 S5・S1のUI（T-97〜T-99）

- **S1（HomeScreen）**: `RaidApi.isConfigured() && raidState.joined` のときのみ、ホーム上部にボスHPバー（ボス名・HP残%・残り日数）を表示。タップでS5へ。未参加時は既存グリッドに「レイド」入口ボタンのみ（isConfigured時のみ表示）。
- **S5（RaidScreen・新規 `screens/RaidScreen.tsx`）**:
  - 未登録（profile.deviceToken がKV未登録=初回）: 招待コード入力・表示名（profile.displayNameを既定値）・1日の目安（少なめ/普通/多め）→ `register`。
  - 登録済: 現ボス表示（HPバー・残り時間・自分の貢献ダメージ・contributions一覧=表示名とダメージのみ）・「参加する」（raidState書込＋`raidSyncEnabled`=ON）・「レイドに挑む」（mode='raid' で7分セッション起動=3.3節）・手動同期ボタン。
  - 討伐時: status='defeated' 受信で討伐演出（07の9節の演出規定内。T-77のリザルト演出の部品流用可）。
- **オフライン表示規約（T-99）**: raidState.lastSyncedAt から「最終同期: N分前」（60分超は「N時間前」、24時間超は「N日前」）を常時表示。HPバー付近に「討伐の確定はサーバー側の判定が正です」の注記1行。オフライン時（同期失敗時）は最終同期表示を強調色にする。
- 登録済み判定は「registerが一度成功したか」を settings キー `raidRegisteredAt`（epoch ms）で端末に記録して行う（毎回サーバー照会しない）。

### 3.8 questionStats・問題報告（T-100 / T-101）

- **集約先**: 週次ボスとは別のシングルトンDO `StatsDO`（`idFromName('global')`）。テーブル: `question_stats(questionId TEXT PRIMARY KEY, correct INTEGER, wrong INTEGER, timeout INTEGER)`（UPSERT加算）、`reports(questionId TEXT, reason TEXT, count INTEGER, PRIMARY KEY(questionId, reason))`。
- **deviceToken非結合の構造的強制**（14の4.4-④）: 認証ミドルウェアがトークン検証後、ハンドラへは**ペイロードのみ**を渡す。保存レコード型・SQLite表に deviceToken 列を持たせない（型レベル検証＋テスト=16のT-100完了条件）。04の4節に「受信ログとの突合による理論上の結合可能性は残るため、保証範囲は『保存データとして結合しない』」の注記を追記（同PR）。
- **クライアント送信（T-100）**: 設定キー `questionStatsEnabled`（既定OFF。SettingsScreenにトグル＋「問題の難易度調整のための匿名統計です」の説明1行）。送信は raidSync と同じトリガーに相乗り。watermark方式: settings `questionStatsLastSentAt` 以降の attempts を questionId 別に集計（`shadow:` プレフィックスは除外=常にisCorrect固定で統計価値がないため）して送信し、成功時に watermark を更新。pendingSyncは使わない（集計値の再計算で足り、冪等キー管理が不要なため）。
- **問題報告（T-101）**: ExplanationCard に「問題がおかしい」ボタン（isConfigured かつ登録済みのときのみ表示。オフラインは disabled）→ 理由選択（`wrong_answer` 誤答扱い / `unnatural` 不自然 / `bad_explanation` 解説誤り）→ 直接fetch送信（キューイングしない。失敗時はトースト「送信できませんでした」のみ）。
- **cli取得**: `packages/cli` はM2セッションの領域（2.1節）のため、統計のビルド入力への自動反映（cliコマンド）は**M3では実装しない**。管理用に GET `/stats/questions`（Bearer必須・全件JSON返却）だけ T-100 で用意し、手動確認・手動投入の運用とする（06の「自動取得に切替」の完全化はcli側タスクとしてM3クローズ時に判断）。

### 3.9 レイド系バッジ（T-102）
