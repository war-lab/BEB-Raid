### 3.1 API契約（J-45）

エンドポイントは以下の6本が基本契約（app/api双方が正本として扱う）。認証は `Authorization: Bearer <deviceToken>` ヘッダ（3.2節）。これとは別に、3.8節が定める管理用の `GET /stats/questions`（T-100・cli等の運用者が手動確認する用途）が存在する。app（クライアント）はこのGETを呼ばない。**認証はdeviceTokenのBearerではなく `ADMIN_TOKEN`（3.2節末尾・adminHandlers.tsの認可を共用）**（T-249・29のQ-31。以前は一般メンバーのdeviceTokenでも読めており、「管理用」の意図とアクセス制御が一致していなかった）。

| メソッド/パス | 認証 | リクエスト | レスポンス（200） | 実装タスク |
|--------------|------|-----------|------------------|-----------|
| GET `/health` | なし | — | `{ ok: true }` | T-90 |
| POST `/register` | 招待コード | `RegisterRequest`（inviteCode・deviceToken・displayName・dailyGoal） | `{ ok: true }` | T-92 |

### 3.2 認証・登録（J-46）

- 招待コードは **wrangler secret `INVITE_CODE` 1個**。漏洩時は `wrangler secret put` で再設定し、参加者へ再配布（手動運用）。ローカル開発・テストは `.dev.vars`（gitignore対象）にダミー値を置く。
- deviceToken は**端末側で既に発行済み**（`profile.deviceToken`。M1で「発行のみ・送信しない」として実装済み=04の3節）。登録APIは新規発行ではなく、**端末のtokenをKVへ登録する**方式とする。
- KVレイアウト: キー `member:<deviceToken>` → 値 `{ displayName: string, dailyGoal: 'light'|'normal'|'heavy', registeredAt: number, emaDailyDamage?: number }`（JSON）。members一覧は `list({ prefix: 'member:' })` で取得（20人規模なら読取枠に対し十分小さい。1,000人超での全件走査は `kvList.ts` の `listAllKeys`＝cursor対応版を使う。T-244・29のQ-23で1ページ目のみ読む不具合を修正した）。
- 再登録（同一tokenでの再POST）は**上書き許容**とする（displayName・dailyGoal の変更手段を兼ねる。専用の更新APIを作らない）。再登録時も registeredAt・emaDailyDamage は既存値を引き継ぐ（表示名変更のたびにHP算出用のEMAが消えるのを防ぐ）。
- displayName は前後空白を trim した上で保存し、**32文字を上限**とする（trim後が空・上限超は400）。貢献一覧として全メンバーへ配信される値のため、KV肥大と他メンバーの画面崩れを構造的に防ぐ（`register.ts` の `MAX_DISPLAY_NAME_LENGTH`）。
- 認証ミドルウェア: Bearer の deviceToken が KV に存在しなければ 401。クライアントは401を受けても **pendingSync を削除しない**（再登録後に再送で復旧）。
- バックアップ複製で同一tokenが2端末に載った場合は「同一人物の複数端末として合算許容」（14の4.4-⑤の割り切り）。荒れた場合の再発行手順=設定画面からのプロファイル再作成はM3では作らず、運用（手動DB操作）で対応。

**`/register` の防御（T-242・29のQ-21・J-103。2026-08-05追加）**: 無認証・無レート制限のままだと、publicリポジトリで既知のURLに対し招待コードの総当たりを妨げるものが無く、招待コードを知る者は任意個の偽deviceTokenを登録して`totalDailyDamage`（3.4節）を吊り上げられた。J-103の正文どおり次の3点のみを実装する（サーバー側でのdeviceToken発行は契約変更になるため採らない）。

- **deviceTokenの形式強制（UUID v4）**: `register.ts` の `DEVICE_TOKEN_PATTERN`。アプリは `crypto.randomUUID()` を使うため新規登録には影響しない。**既存メンバーの認証（`auth.ts` の `authenticateRequest` によるKV `member:<token>` 照合）には適用しない**（本番KVの既存トークン形式を事前確認できないため、非UUIDトークンを持つ既存端末の認証を壊さない安全側の判断）。適用範囲は新規登録・表示名更新（＝再登録）の2経路のみ。
- **登録総数の上限**: `register.ts` の `MAX_REGISTERED_MEMBERS`（暫定500）。新規登録のみに適用し、既存メンバーの再登録（表示名更新）は上限到達後も許可する。
- **招待コード誤りの回数計測とレート制限**: `CF-Connecting-IP` ごとにKV `registerFail:<ip>` へ失敗回数と直近ウィンドウ開始時刻を記録し、15分間に10回誤ると以降 429 を返す。正しいコードでの登録成功時にカウンタをクリアする。

### 3.4 週次ボス（J-48 / J-49 / J-50）

- **bossId** = `boss-<ISO年>-W<ISO週番号2桁>`（例: `boss-2026-W30`）。ISO週の導出関数は api 内に実装しユニットテストを付ける。
- **生成**: Cloudflare Cron Trigger `0 0 * * *`（**2026-08-06訂正・T-358・K-92**: 毎日 0:00 UTCへ日次化した。曜日式`0 0 * * 1`は「1=月曜」という誤解に基づく記述で、Cloudflareの実際の解釈は「1=月曜」ではなく仕様上の曜日番号とcron実装の解釈にズレがあり、本番で週次ボスが不発になる事故につながった。`generateWeeklyBoss`側の生成権主張（`claimGeneration`。docs/30 J-101・T-179）が週1回のみの生成を保証するため、cron自体は日次でも安全で、発火漏れ・遅延を翌日に自己修復できる）で当週ボスを生成。`startAt` = **ISO週の開始時刻（月曜 0:00 UTC = 月曜9:00 JST）**とする（cron発火時刻ではない。発火の遅延・再実行時に「週開始〜発火時刻」の answeredAt を持つダメージが期間外として捨てられるのを防ぐため）。`endAt` = 同週金曜 15:00 UTC（= 金曜24:00 JST＝土曜0:00 JST）。**帰属期間は月曜9:00 JST〜土曜0:00 JSTで固定であり、土曜0:00 JSTから月曜9:00 JSTまでの週末はダメージ非加算期間である**。この窓の実長は4日15時間（4.625日）だが、HP算出に使う `RAID_DAYS` は5である（K-93。ボスが約8%硬くなる既知の乖離で、窓もHP係数も本番稼働中の週をまたぐバランス影響が大きいため変更対象外。J-121）（answeredAtがこの区間にあるペイロードは3.4節の帰属判定で加算されない。J-121。窓自体の変更は本番稼働中の週をまたぐバランス影響が大きいため対象外）。
- **クローズ**: 専用cronは設けない。DOがアクセスのたびに `hp <= 0`（討伐）または `now > endAt`（期限）から status（`active` / `defeated` / `closed`）を導出する。討伐済みボスは同週内は参照可能なまま残す。週明けは新ボス生成まで `/raid/current` が404を返す（端末側は raidState キャッシュで前回結果を表示できる）。
- **HP算出（J-48）**:
  - 申告値の換算表: `light=5問/日, normal=15問/日, heavy=30問/日`。
  - 参加者1人あたりの想定日次ダメージ = `emaDailyDamage`（KVのmemberレコード。前週実績あり）が存在すればそれ、無ければ `申告問題数 × DAMAGE_PER_QUESTION`。
  - `HP = round( Σ(全登録メンバーの想定日次ダメージ) × 5日 × BOSS_HP_FACTOR )`。下限 = `normal 1人分相当`（`15 × DAMAGE_PER_QUESTION × 5 × BOSS_HP_FACTOR`。登録0人週の異常値防止）。
  - `DAMAGE_PER_QUESTION`・`BOSS_HP_FACTOR`（**03の6.2で確定済みの討伐率係数=0.85をそのまま使う**。新値を作らない）は `packages/api/src/raidConfig.ts` に定数として外出しし、`$comment`相当のコメントで「暫定・実測調整」と由来を明記する。**DAMAGE_PER_QUESTION の初期値は実装時に導出する**: `engine/rating.ts` の basePoints 算出を難易度3・初期レート帯で実行するテストを一時的に書いて中央値を実測し、その値 × raid係数1.0 を転記する（導出過程をコメントに残す）。
  - **EMA補正**: 週次生成cronの中で、前週ボスDOから deviceToken 別ダメージ合計を取得し、`前週日次 = 合計 / 5` として `emaDailyDamage_new = 0.5 × 前週日次 + 0.5 × emaDailyDamage_old`（初回は前週日次をそのまま）をKVのmemberレコードへ書き戻す（書込は週1×人数分でKV枠に対し無視できる）。
- **帰属（J-49）**: 受理条件は `payload.answeredAt ∈ [startAt, endAt]`。バッチ受信が endAt 後でも answeredAt が期間内なら加算する。クライアント時計は信用しない: `answeredAt > 受信時刻 + 5分` のペイロードは受信時刻へクランプしてから判定する。
- **参加の表現**: サーバー側に join API は作らない（API極小）。HP算出の母数は**登録メンバー全員**、participantCount は damageLogs の deviceToken distinct 数とする。端末側の「参加」（S5の参加ボタン）は raidState 書込（joined=true）＋ `raidSyncEnabled` 設定ONのみ（T-89の既存ゲートと整合）。
- **ボスプロファイル**: M3では content 層に置かず、`packages/api/src/bossProfiles.ts` に静的ローテーション配列（10体程度。`{ name, flavor }`。TOEIC/ビジネス題材の架空モンスター名）を定義し、週番号で決定的に選ぶ。サーバー側の `profileJson` = このオブジェクトのJSON文字列。ただしAPIレスポンス（`RaidBossState`）に載せるのは `name` のみで、クライアントの raidState.profileJson は `{ name }` だけを保持する（`flavor` 等の演出用フィールドはM3では未配信・未使用。討伐演出等での活用はM4以降）。

### 3.5 Durable Object 設計（T-94）

- クラス `RaidBossDO`。**1ボス=1インスタンス**（`idFromName(bossId)`）。SQLiteストレージを使う。
- テーブル:
  - `state`（1行）: bossId, name, profileJson, maxHp, startAt, endAt, defeatedAt(null可)（name は `RaidBossState` 構築時に profileJson をパースせずに済むよう非正規化した列。profileJson内のnameと同値）
  - `damage_attempts`: attemptId TEXT PRIMARY KEY, deviceToken TEXT, damage INTEGER, questionCount INTEGER, answeredAt INTEGER, receivedAt INTEGER
- 現在HP = `maxHp − SUM(damage)`（都度SQL集計。行数は週次20人×数百問規模で問題ない）。
- 冪等性: attemptId主キーによる重複排除。実装方式は `INSERT OR IGNORE` ではなく「SELECTで既存確認→未存在なら INSERT」の2段とした（重複・非加算・新規受理の分類と討伐判定を同じループ内で行うため。DOはシングルスレッド実行のため2段でも競合はなく、挙動は `INSERT OR IGNORE` と同等）。レスポンスには**受理済みattemptId一覧**（今回受理＋既に受理済みだった重複分の両方）を返す。クライアントは一覧に含まれるIDのみ pendingSync から削除する。
- 討伐判定: 加算後に HP≤0 になった時点の受信時刻を defeatedAt に記録。**討伐後**（defeatedAt設定済み）または**帰属期間外**（answeredAtが[startAt,endAt]の外。J-49）のダメージは加算しない（acceptedIdsに**含めて**返す=クライアント側キューは掃除させるが、加算はしない）。**「受信（receivedAt）がendAtを過ぎている」こと自体は加算を妨げない**（J-49の趣旨どおり、オフライン滞留分の遅延到着はansweredAtが期間内なら期限後受信でも加算する。実装時に「期限受信後は一律拒否」と誤読しかけた= T-95実装時に発見・修正。RaidBossDOのステータス表示（active/defeated/closed）はnowとendAtの比較で別途決まるが、これはsyncDamageの加算判定とは独立の表示専用ロジックである）。この区別のためレスポンスに `applied: boolean` は持たせず、HPが正の間に送る動機付けはUI側の表示で行う。
- **週次クローズ後のデータの掃除方針（T-247・29のQ-29。2026-08-05実装）**: 削除経路が無いとbossIdごとに別インスタンスのSQLiteが無期限に蓄積する。実運用の規模（数十人）では年単位でも支障が無い規模だが（DO SQLiteは5GBまで無料）、方針を未定義のままにしないため実装した。`generateWeeklyBoss`（scheduled.ts）の末尾で、`RAID_BOSS_RETENTION_WEEKS`（raidConfig.ts。暫定8週=約2ヶ月）より前に週が終了したボスDOへ`cleanupIfExpired(cutoff)`を呼び、`ctx.storage.deleteAll()`でSQLiteを丸ごと削除する（state・damage_attempts・generation_claimの全テーブルを含む）。前週分のダメージ集計はcron実行直後にEMA・ゴーストクローズ・raidSummary（KV）へ既に転記済みで、それより古い週のDOはどの経路からも参照されない（直近参照は常に「当週」「前週」のみ）ため、削除しても実害が無い。掃除の失敗は週次ボス生成自体の成否に影響させない（副次処理のためtry/catchで隔離しログのみ残す）。

#### デプロイ方針の改訂（2026-07-30）

**改訂前**: main への push は dev環境のみを更新し、production は `workflow_dispatch` の手動実行だけとしていた（誤った本番自動デプロイを避ける意図）。

**改訂の理由**: GitHub Pages（`deploy.yml`）は main への push で自動配信されるため、APIだけが取り残される非対称が残っていた。実際に本番APIが2026-07-22のM3世代のまま公開アプリがM4のUIを持つ状態になり、イベントバトルのルーム作成が404 `not_found` を返した（経緯は `docs/STATUS.md` の2026-07-30の節）。手順の遵守に依存する設計では再発を防げないため、取り残しの防止をワークフローへ移した。

**改訂後**: main への push で dev と production の両方へ自動デプロイする。**「mainの内容は常に本番と同じ」を不変条件にする**という判断で、GitHub Pages（`deploy.yml`）と同じ扱いに揃えた。承認ゲート（Environment の必須レビュアー）は置かない。

| 項目 | 設定 |
|---|---|
| ワークフロー | `strategy.matrix.environment` を push時 `["dev","production"]`・手動実行時は選択環境の1件にする。`fail-fast: false` は片方の環境の失敗でもう片方を打ち切らないため |
| デプロイ前ゲート | 従来どおり shared-schemaビルド → `tsc --noEmit`（api build）→ apiテストを通してからデプロイする。壊れたコードが本番へ出る経路はここで塞ぐ |
| 誤った本番反映の防止 | mainへの直pushではなくPRレビューが担う（自動デプロイの是非をデプロイ時点で判断する仕組みは持たない） |
| 後着デプロイの防止 | job単位の `concurrency`（`api-deploy-<環境>`・`cancel-in-progress: true`）。連続pushで古いコミットのデプロイが後着し本番を巻き戻すのを防ぐ |
| `environment:` キー | Environmentsタブに環境別のデプロイ履歴を残す目的で付ける。**保護ルールは意図的に設定していない**（設定するとmainへのpushが承認待ちで止まり、取り残しの再発経路に戻る） |

**この方針の代償**: main へ入れた時点で本番APIが即座に切り替わるため、`packages/api` や `packages/shared-schema` を含むPRを main へマージするときは、本番へ出して差し支えない状態か（互換性のない契約変更を公開アプリより先に出さないか）をマージ前に確認する。段階的に出す必要がある変更は、後方互換のある順序（サーバー先行・クライアント後追い）でPRを分ける。

#### 運用エンドポイント: POST /admin/raid/generate（2026-08-03追加）

週次ボスは cron（当時は `0 0 * * 1` の週次発火。**2026-08-06に`0 0 * * *`の日次発火へ是正済み。T-358・K-92**）でしか生成されず、**発火しなかった週を手当てする手段が無かった**。2026-07-27・2026-08-03 の自動発火がいずれも確認できなかったため（経緯は `docs/STATUS.md`）、cronの原因調査と切り離して今週のレイドを成立させられる経路を用意した。

| 項目 | 内容 |
|---|---|
| 認可 | 専用シークレット `ADMIN_TOKEN`（Bearer）。**未設定なら404を返す**（設定するまで攻撃面を作らない） |
| INVITE_CODEを流用しない理由 | 登録済みメンバー全員が知っている値で、運用操作の認可には強度が足りない |
| 既存ボスがある場合 | **生成処理を呼ばず現状を返す**（`{created:false, boss}`）。存在確認としても使える |
| 応答 | `{ created, bossId, boss }` |

「無いときだけ生成する」を関数の外側で守るのが要点である。`generateWeeklyBoss` は③ボスDO初期化は冪等だが、**①`emaDailyDamage` の更新は冪等でない**——同じ週の実績でEMAを二度平滑化すると翌週以降のボスHP算出が前週値へ寄る。cronの再発火・手動実行の重複でこれを起こさないため、ハンドラ側で存在確認してから呼ぶ。

このエンドポイントはcron不発の恒久対策ではない（cron自体の原因調査は別件）。発火するようになっても害はないため残す。
