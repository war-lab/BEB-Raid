### 3.1 API契約（T-123で shared-schema に定義）

M3の6本（17の3.1節）に以下を追加する。認証はM3と同じ Bearer deviceToken。

| メソッド/パス | 認証 | リクエスト | レスポンス（200） | 実装タスク |
|--------------|------|-----------|------------------|-----------|
| POST `/battle/rooms` | Bearer | — | `{ code: string }`（4文字英数大文字。衝突時は再生成） | T-124 |
| GET `/battle/rooms/:code/ws` | Bearer相当（下記） | WebSocket Upgrade | 101 | T-124 |
| POST `/ghosts` | Bearer | `GhostRecordPayload` | `{ ok: true }` | T-127 |
| DELETE `/ghosts/own` | Bearer | — | `{ ok: true }`（記録が無くても200・冪等） | T-127 |
| GET `/raid/summary` | Bearer | — | `RaidSummary[]`（管理用・週次結果一覧） | T-131 |

- **WebSocketの認証**: ブラウザのWebSocketはAuthorizationヘッダを付けられないため、`Sec-WebSocket-Protocol` に `bearer.<deviceToken>` を載せる方式とする。サーバーはKV存在確認後にサブプロトコルをechoして受理、未登録は1008でクローズ。トークンをURLクエリに載せる方式は使わない（アクセスログ残留を避ける）。
- **`RaidBossState` の拡張**: `bossType: 'synthetic' | 'ghost'`、`defense?: { questionId: string, multiplier: number }[] | null`（ghost時のみ）、`ghost?: { displayName: string, defeatedCount: number } | null`。既存クライアントとの互換のため追加は全て省略可能フィールドとし、`SCHEMA_VERSION` は据え置く。
- **`GhostRecordPayload`**: `{ consent: true, displayName: string, records: { questionId: string, correct: boolean }[] }`。**`consent` は リテラル型 `true`**（`boolean` にしない）。ビルダー関数 `buildGhostRecordPayload` は同意画面の確認結果を引数に取り、未同意なら例外を投げる（questionStatsの `deviceToken` 非含有と同じ構造的強制の思想。14の4.4-④）。
- WebSocketメッセージは `BattleClientMessage` / `BattleServerMessage` のdiscriminated union（3.2節）を shared-schema に定義し、app/api双方がimportする。

### 3.2 昼バトルの進行プロトコル（T-124〜T-126）

**BattleRoomDOはコンテンツ非依存**とする: DOは問題文・選択肢・正解を一切持たず、`questionId` と換算点のみを扱う。正誤判定は各参加端末がローカルパックで行い（J-63）、出題内容の表示・音声再生はホスト画面が担う。

- **ルームのライフサイクル**: `lobby → question(n) → … → result → closed`。ホスト切断（WebSocketクローズ）または作成から2時間経過で強制クローズ。クローズ時に全接続を閉じ、**DOのメモリ・ストレージに個人別データを残さない**（永続ストレージは最初から使わない）。
- **メッセージ（shared-schemaのunion。主要なもの）**:
  - Client→Server（参加者）: `join { displayName, expectedPointsPerQuestion }`（期待点=直近の自己平均基礎点。換算値のみ=J-63）／`answer { questionIndex, points }`（points=クライアント算出の基礎点。誤答は0）
  - Client→Server（ホスト。ルーム作成者のdeviceTokenのみ受理）: `openQuestion { questionIndex, questionId }`（音声の再生完了後に送る=05の4.2「再生完了イベントで解答受付を開く」）／`closeQuestion { questionIndex }`／`finish`
  - Server→Client: `roomState { participants: { displayName }[] }`／`questionOpen { questionIndex, questionId, deadlineAt }`（deadlineAt=DO受信時刻+30秒。DO側タイマーが正）／`standings { entries: { displayName, totalPoints }[] }`（各問クローズ後）／`result { entries, bestGrowth: { displayName } }`／`error { code }`
- **解答受理**: `questionOpen` 後〜deadlineAt（または `closeQuestion`）の間のみ。1参加者1問1回（2回目以降は無視）。受信順位はDOの受信時刻順。
- **速度ボーナス（J-64正文）**: DO側で加算する。`最終点 = points + (points > 0 ? round(points × 0.2 × (1 − (受信順位−1) / 参加者数)) : 0)`。points=0（誤答）はボーナスなし。クライアントは基礎点のみ送り、ボーナスをクライアントで計算しない（受信順位=サーバー時刻基準の原則）。
- **ベストグロース賞**: `growth = 合計最終点 ÷ (expectedPointsPerQuestion × 出題数)` が最大の参加者（同率は先着）。`expectedPointsPerQuestion` が0以下のjoinは1にクランプする。
- **出題セット（J-65正文）**: ホスト画面がルーム作成時に、キャッシュ済み配信パックから `part ∈ {2, 5}` の問題を**12問**（Part2:Part5 = 6:6。在庫不足時はある方で補填）無作為抽選する。抽選結果（questionIdリスト）はホスト画面が保持し、DOへは進行時に1問ずつ `openQuestion` で渡す。参加端末は `questionOpen` の questionId をローカルパックから引いて選択肢を表示する。**参加端末に該当パックが無い場合は当該問題を「パック未取得」表示とし、解答不可（0点）で流す**（ロビー画面に「最新パックを取得してから参加」の案内を出して予防する）。
- **個人結果の端末保存**: 各参加端末はバトル終了時に、自分の解答を通常の `attempts`（mode='battle'）として記録し、誤答のkeyVocabを既存の復習循環へ登録する（02の6.2「誤答は各自の復習デッキへ自動登録」）。レート更新は行わない（mode='battle' はレート対象外=03の5.4の趣旨。イベントの速答文脈は平常の実力測定と条件が異なるため）。

### 3.3 ゴースト週次組込（J-66/J-67正文。T-127）

- **KVレイアウト**: `ghost:<deviceToken>` → `{ displayName: string, consent: true, records: { questionId, correct }[], createdAt: number, defeatedCount: number, lastUsedBossId: string | null }`。1人1記録（再POSTは上書き=記録の作り直し）。
- **週次cron（既存scheduledハンドラへの分岐追加）**: ボス生成時に `list({ prefix: 'ghost:' })` で承認済み記録を探し、**`lastUsedBossId` が直近2週のbossIdでない記録のうち `createdAt` が最も古いもの**を1件選ぶ。あれば `bossType='ghost'` でボスを生成し、`lastUsedBossId` を更新。無ければ従来どおりsynthetic。
- **defense変換**: `correct → multiplier 0.5`（堅い）、`!correct → multiplier 2.0`（弱点）（03の6.3の確定値。倍率は `raidConfig.ts` へ `GHOST_MULTIPLIER_SOLID = 0.5`・`GHOST_MULTIPLIER_WEAK = 2.0` として外出し）。
- **HP**: 通常式（17の3.4節） × `GHOST_HP_FACTOR`（初期値1.0。raidConfig.tsへ外出し・暫定）。目標勝率レイド隊60–70%（03の6.3）に向けた調整はT-131の運用手順で行う。
- **ボス名**: `ゴースト・<displayName>`。表示名がレイド参加者全員に見えることは同意画面の明示事項に含める（3.5節）。
- **撤回（`DELETE /ghosts/own`）**: KVの `ghost:<deviceToken>` を即時削除。**当週ボスがこの記録由来（profileJsonに記録者tokenを保持して判定）なら、当週DOへ差し替えを指示**: 名前をsyntheticローテーション名へ、defenseを空へ、bossTypeを'synthetic'へ変更（HP・累計ダメージ・討伐状態は維持）。クライアントは次回同期の `RaidBossState` で自然に追従する（プッシュ通知はしない）。
- **討伐回数（名誉表示。02の5.3）**: 次週cronの週次クローズ処理で、前週がghost週かつ討伐成立していたら該当 `ghost:` レコードの `defeatedCount` を+1する（レコードが撤回済みなら何もしない）。`RaidBossState.ghost.defeatedCount` として配信し、S5が「討伐された回数: N回」を名誉として表示する。

### 3.4 クライアントのゴースト対応（T-129）

- `raidState` に `bossType`・`defenseJson`（questionId→multiplierのマップ）・`ghostJson` を追加キャッシュする（Dexieの既存 `raidState` ストアの非インデックスフィールド追加。スキーマversionは上げない）。
- **倍率適用**: `answerPipeline` のダメージ算出（既存 `engine/damage.ts` 経由）の結果に、`bossType==='ghost'` かつ defenseに該当questionIdがある場合のみ multiplier を乗算してから pendingSync へ書く。mode係数（raid 1.0 / solo 0.5）との併用は乗算。defense外の問題は倍率1.0。
- **弱点可視化（02の5.3）**: S5に弱点マップを表示する。**挑戦前に見せるのは Part・タグ単位の集計のみ**（例: 「弱点: Part5 前置詞 ×2.0 が3問」）とし、個別questionIdは事前に開示しない（正答の狙い撃ちを防ぐ）。セッション中に defense 該当問題が出題されたら、解答後の解説カードに「堅い ×0.5」「弱点 ×2.0」バッジと今回の実ダメージを表示する。
- **synthetic週の回帰**: defense不在時（synthetic週・API無効）は挙動・表示ともM3と完全同一であることを回帰テストで担保する。

### 3.5 ボス役セッション（T-128）

- 入口はS5に「ボス役に立候補」ボタン（isConfigured かつ登録済みのときのみ表示）。
- **同意画面**（セッション開始前に全文表示・チェックボックス+開始ボタン）で明示する内容: ①自分の問題別の正誤がレイド参加者全員に「堅い/弱点」として見えること ②表示名がボス名として全員に見えること ③いつでも撤回でき、撤回すると記録はサーバーから即時削除されること。
- **出題**: キャッシュ済み配信パックから `difficulty >= 4` の問題を**30問**無作為抽選（レート対象の format のみ。vocab_card・shadowing・dictation は除外）。在庫が30問に満たない場合は difficulty 3 を許容して補填し、**それでも10問未満なら停止して人間に報告**（高難度在庫の増産判断が必要なため）。
- セッションは mode='battle' で通常のattempts記録も行う（ボス役自身の学習にもなる=02の5.3。mode='battle'はダメージ係数0=03の6.1のためレイド貢献には乗らない。レート更新も行わない=3.2節と同じ扱い）。
- 完走後に**記録プレビュー**（正誤一覧と「弱点として公開される問題数」）を表示し、送信ボタンで `POST /ghosts`。送信前ならいつでも破棄できる。

### 3.6 S7/S8のUI（T-125/T-126）

- **抽象化レイヤ**: 新規 `platform/net/BattleSocket.ts` にWebSocketのインターフェース（connect/送信/受信コールバック/クローズ）を定義し、ブラウザWebSocket実装とテスト用フェイクを併設する（RaidApiと同じ方針。UI・サービス層から素のWebSocketを直接触らない）。
- **S7（参加。新規 `screens/BattleScreen.tsx`）**: ルームコード入力（4文字・大文字化）→ ロビー（参加者一覧・「最新パックを取得してから参加」案内）→ 出題中（選択肢ボタンのみの大ボタンUI=02の6.1。解答後は自分の基礎点を即時表示）→ 各問後の順位表示 → 最終リザルト（順位・ベストグロース賞・自分の誤答一覧→復習デッキ登録済みの明示）。入口はHomeScreenのナビゲーション行（isConfigured時のみ表示）。
- **S8（ホスト。同 `BattleScreen.tsx` 内のホストモード or 別コンポーネント。実装時にファイル分割は任意）**: ルーム作成→抽選プレビュー（再抽選可）→ 参加者が揃ったら開始 → 問題投影（問題文・選択肢・音声再生=既存 platform/AudioPlayer 経由。**再生完了イベントで `openQuestion` 送信**）→ カウントダウン表示（deadlineAt基準）→ 各問順位 → 最終順位・ベストグロース表彰。PC想定のためレイアウトは横長を許容するが、既存トークン・コンポーネント言語（07）の範囲で作る。
- ホストも参加者として解答はしない（進行専任。ホスト端末のdeviceTokenはルーム作成・進行メッセージの認可にのみ使う）。

### 3.7 成長ランク（J-68正文。T-130）

- **端末内導出のみ**。サーバー送信なし。
- 算定（暫定式。`engine/growthRankConfig.json` へ外出し）: `rankPoints = max(0, 現在の総合レート − 初期レート) + 学習日数`。初期レート = `ratingHistory`（section='total'）の最古スナップショット値。学習日数 = attempts が1件以上存在する日の数（既存のストリーク/ヒートマップ集計と同じ日付基準を再利用）。
- 閾値（暫定）: ブロンズ 0 / シルバー 40 / ゴールド 90 / プラチナ 150 / マスター 230。
- 表示: DashboardScreen にランク名・現在ポイント・次ランクまでの残り。演出は既存のカード面言語の範囲（新規の光暈・アニメーションを増やさない=20の2.3節の光暈4箇所限定を維持）。

### 3.8 バランス調整の運用装置（T-131）

- **週次サマリ**: 週次cronのクローズ処理で `raidSummary:<bossId>` をKVへ書く: `{ bossId, bossType, maxHp, remainingHp, defeated: boolean, defeatedAt, participantCount }`（個人別データは含めない）。
- **管理用 `GET /raid/summary`**（Bearer必須）: サマリ全件を配列で返す（20人×52週でもKV読取枠に対し無視できる）。クライアントアプリはこれを呼ばない（運用者がcurl等で確認する用途。17の3.8節の `GET /stats/questions` と同格）。
- **調整手順**: 本書の**付録A**に、観測指標→調整対象係数の対応表を実装時に完成させる（現在値・定義ファイル・出典を列挙）。対象係数: `BOSS_HP_FACTOR`（討伐率が70%未満で下げ/95%超で上げ）・`GHOST_HP_FACTOR`・`GHOST_MULTIPLIER_SOLID/WEAK`（ゴースト週の勝率60–70%目標）・速度ボーナス率0.2（昼バトルの接戦度。H-4のFB記録が入力）。

## 付録A: バランス調整係数一覧（T-131完了。2026-07-27時点）

調整はH-4（昼イベント実開催）・週次サマリ（`GET /raid/summary`）の実測が揃ってから行う。本表は「何を見て・どの係数を・どちらへ動かすか」の対応表であり、値そのものの変更判断は都度発起人が行う（3.8節）。

| 係数 | 現在値 | 定義ファイル | 観測指標 | 調整の向き |
|------|--------|-------------|----------|-----------|
| `BOSS_HP_FACTOR` | 0.85 | `packages/api/src/raidConfig.ts` | 週次討伐率（`GET /raid/summary`の`defeated`が直近数週で何%か。bossType='synthetic'週のみで判定） | 討伐率が70%未満なら**下げる**（ボスを弱くする）。95%超なら**上げる**（張り合いを出す）。目標帯は03の6.2（週次レイドは「今週みんなで倒す」が会話に出る難度）に準ずる |
| `GHOST_HP_FACTOR` | 1.0 | `packages/api/src/raidConfig.ts` | ghost週の討伐率（`GET /raid/summary`で`bossType='ghost'`の週のみを抽出した`defeated`比率。目標60–70%=03の6.3） | 討伐率が60%未満なら**下げる**（ゴーストを弱くする）。70%超なら**上げる**。synthetic週の`BOSS_HP_FACTOR`調整とは独立に評価する（乗算対象のベースmaxHpが週ごとに変わるため、絶対値ではなく討伐率で見る） |
| `GHOST_MULTIPLIER_SOLID` | 0.5 | `packages/api/src/raidConfig.ts` | ghost週の討伐率（GHOST_HP_FACTORと同じ実測データを共有する。挑戦者側の体感は「堅い」問題がどれだけダメージを吸うかに依存するため、HP係数と合わせて調整する） | 討伐率が60%未満で「堅い」問題が壁になっている（弱点可視化のFB・実測で堅い問題への集中砲火が空振りしている）なら、0.5→0.6等へ**上げる**（防御を弱める）。討伐率が70%超で緊張感が無いなら**下げる**（0.5→0.4等） |
| `GHOST_MULTIPLIER_WEAK` | 2.0 | `packages/api/src/raidConfig.ts` | ghost週の討伐率（同上。弱点集中による討伐の容易さが指標） | 討伐率が70%超で弱点集中だけで瞬殺されているなら2.0→1.5等へ**下げる**。60%未満で弱点を突いても伸びないなら**上げる**（2.0→2.5等） |
| 速度ボーナス率（`SPEED_BONUS_RATE`） | 0.2 | `packages/api/src/battleRoomDo.ts` | 昼バトルの接戦度（1位と最下位の最終順位差・得点差。ルーム揮発のためサーバー保存はせず、H-4開催時にホスト画面の最終順位をFBシートへ手動記録したものを入力とする） | 上位者が固定化し接戦にならない（速度ボーナスでレート差がさらに開く）なら**下げる**（0.2→0.1等）。順位が実力と無関係に運ゲー化する（低レート者が速度ボーナスだけで頻繁に上位を取る）なら**上げすぎ**なので同様に下げる方向で調整する。逆に「得点が均されすぎて全員同着に近い」場合のみ**上げる**（0.2→0.3等） |
