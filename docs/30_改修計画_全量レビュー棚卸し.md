# 30. 改修計画 全量レビュー棚卸し（T-179〜T-264）

## 1. 結論

[29_全量レビュー棚卸し](29_全量レビュー棚卸し.md) の所見112件を、86タスク（T-179〜T-264）と9フェーズに落とした自走用タスクシートである。

判断J-100〜J-113は3節で正文を確定させた。実装を止めないため、原則としてすべて事前決定した。発起人の判断が要る4件は15節に分離し、既定の扱い（多くは記録のみ）を決めてあるので、待たずに他を進められる。

フェーズ1は本番で機能が壊れている6件で、ここだけは先に片付ける。フェーズ2は無症状で誤ったデータが蓄積する11件。フェーズ3以降は並行して進められる。

## 3. 事前決定事項（J-100〜J-113の正文）

### J-100 cronの修正方針

**生成処理を冪等化した上で、cronを日次発火（`0 0 * * *`）に変える。** 曜日フィールドを使わない。

理由は2つある。第一に、「Cloudflareは1=日曜」という解釈は公式ドキュメントの記述に基づくが本番ログで確定していない。番号を書き換える修正は、解釈が誤っていた場合に発火曜日を別の誤った日へ動かす。第二に、日次発火なら発火漏れ・遅延が翌日に自己修復する。週1回しか走らない処理は失敗の発見が最短でも1週間後になる。

日次化の前提として、生成が2回目以降に完全な無操作になる必要がある（J-101）。この順序を守らないとEMAが毎日平滑化され、HPが急速に壊れる。**T-179を先に完了させ、テストで冪等性を確認してからT-180に着手する。**

29の付録A-1の確認は引き続き有用である。日曜発火が確定すればコメントの誤りも訂正できる（T-180に含む）。ただし確認は本タスクのブロッカーではない。

### J-101 EMA更新の重複防止

**RaidBossDO側に週の生成権を主張する操作を設け、`generateWeeklyBoss` の冒頭で取得する。** 取得できなければ即座にreturnする。

DOは単一スレッドで動くため、SQLiteの主キー制約による1行INSERTで原子的な主張になる。KVやハンドラ側のチェックでは並行リクエストの競合を防げない。

生成が途中で例外を投げた場合は主張を解放してから再送出する。解放しないと、ボスが存在しないまま週が「生成済み」に固定される。

### J-102 ゴーストの防御倍率とプライバシー不変条件

**不変条件の明示的な例外として `docs/05` に記載し、ADRを起こす。** 実装は変更しない。

ゴースト週の防御倍率は本人の問題別正誤と1対1に対応し、表示名付きで配信される。同意を前提とした設計（22の3.3節）だが、CLAUDE.mdの「個人紐づきはダメージ換算値＋表示名のみ」という記述と文面上は矛盾する。記載がないまま運用すると、後続の実装者が不変条件違反と判断して壊すか、逆に無自覚に範囲を広げる。

### J-103 `/register` の防御範囲

**次の3点に限る。** deviceTokenの形式強制、登録総数の上限、招待コード誤りの回数計測とレート制限である。

サーバー側でのトークン発行は契約変更になり、既存メンバー7件の移行が必要になるため採らない。

形式強制はUUID v4を要求する。アプリは `crypto.randomUUID()` を使うので新規登録に影響はない。ただし既存メンバーが非UUIDのトークンを持つ場合、表示名更新のための再登録が拒否される。**着手時にまず本番KVの既存トークン形式を確認し、非UUIDが1件でもあれば形式強制のみ見送って残り2点を実施する。**

### J-104 バトル再接続時の得点

**`ParticipantState` をdeviceToken単位でルームの生存期間中メモリに保持し、再接続時に復元する。** 永続ストレージは使わない（22の3.2節の設計を維持する）。

あわせて `currentAnswers` をdeviceTokenで一意化し、再接続後の再回答による二重加点を防ぐ。

### J-105 不可逆操作の確認

**ConfirmDialogを次の4箇所へ広げ、残る `window.confirm` 2箇所も置換する。** ボス役記録の撤回、ゴーストリザルトの破棄、バックアップのインポート、BYOKキーの削除である。

インポートはファイル選択後に、対象ストアと件数を提示してから実行の可否を問う。件数の提示がないと、古いファイルの誤選択を実行前に気づけない。

### J-106 誤タップ救済の対象拡大

### J-107 `title` 属性のみの説明

## 4. 実行基盤

### 4.1 ブランチとPRの単位

ブランチは `task/T-xxx-説明` 形式でdevから切る。`feature/` は使わない（ブランチポリシーによりpushできない）。

PRはdevへ向け、ドラフトで作成する。mainへはフェーズ境界でまとめて出す。

1タスク1PRを原則とする。ただし同一ファイルの小さな修正が複数タスクにまたがる場合は、フェーズ内でまとめて1PRにしてよい。まとめる場合はPR本文にタスクIDを列挙する。

`docs/STATUS.md` の更新は実装と同じPRに含める。

### 4.2 単独PRにするタスク

共有面を変えるため、他の変更と混ぜない。

| ID | 理由 |
|---|---|
| T-179 | RaidBossDOのインターフェース追加。cron日次化（T-180）の前提 |
| T-182 | shared-schemaのメッセージ契約変更。app・apiの両方に波及する |
| T-234 | CLIコマンド追加とCIワークフロー変更。失敗すると全PRが赤くなる |
| T-256 | STATUS.mdの大規模移動。他PRとのコンフリクトが避けられない |

T-256は他タスクがSTATUS.mdを更新するため、**フェーズ9の最後に単独で実施する**。着手前に進行中のPRが無い状態を作る。

### 4.3 検証コマンドと完了条件

ルートで実行する。

```
npm test
npm run lint
npm run build
npm run format:check
```

4つすべてがexit 0であることを各タスクの最低条件とする。`docs/` のMarkdownは `.prettierignore` により整形対象外なので、文書のみのタスクでも `format:check` は通る。

APIのみを変更した場合も `npm test` をルートで実行する（app側の型が壊れていないかを見る）。

不具合修正のタスクは、**修正前に落ちる回帰テストを先に書く**。テストが修正前に通ってしまう場合は、原因の理解が誤っているか再現条件が違う。その場合は修正へ進まず、29の該当所見に立ち返る。

### 4.4 破ってはいけない不変条件

- `attempts` は追記のみ。削除APIを作らない。Dexieフックの遮断を外さない
- 音声再生・キャッシュ・通知・AI呼び出しは `packages/app/src/platform/` のインターフェース経由。UI・エンジンから `Audio` / `AudioContext` / `caches` を直接呼ばない
- 色は `packages/app/src/styles/tokens.css` のトークン経由で参照する
- 個人紐づきで共有APIへ送るのは、ダメージ換算値と表示名のみ。`questionStats` はdeviceTokenと結合できない匿名統計に保つ（ゴーストの例外はJ-102の記載範囲に限る）
- オフラインが正常系。解答とSRS更新はIndexedDBへ即時保存し、共有APIの全損でソロ学習が壊れないこと
- 問題パックは `license` と `origin` を必須とする。市販教材の流用を取り込まない
- 設計変更を伴う場合は該当する `docs/` を同じPRで更新する。docsに無い技術判断は `docs/adr/` に記録する

### 4.6 縮退の禁止

運用負荷・実行コスト・環境制約を理由に、テストやスコープを勝手に縮めてはならない。

「ユニットテストで担保される」を理由に手動確認を省く判断は越権とする。手動確認は自動テストで網羅できないシナリオを補完する目的で計画している。

縮退が必要と判断した場合は、実施せずに発起人へ判断を仰ぐ。判断を仰ぐ際は、困難だと感じる案を選択肢から意図的に外さない。

完了報告を書く前に「本来やるべきだったが省略した項目」を再点検する。

### T-179 の実装方針

`generateWeeklyBoss` の現在の順序は、①前週サマリ書込、②EMA更新、③HP算出、④当週ボス初期化である。④に冪等ガードがあるが①②は毎回走る。

冒頭に生成権の主張を挟み、取得できなければ即returnする。DOは単一スレッドなので、SQLiteの主キー制約による1行INSERTが原子的な主張になる。

例外時は主張を解放する。解放しないと、ボスが存在しないまま週が生成済みに固定され、手動生成でも復旧できなくなる。

`POST /admin/raid/generate` の存在チェックは残してよいが、重複防止の責務は `generateWeeklyBoss` 側に移る。ハンドラは「作成したか」を主張の結果から返す。

### T-180 の注意

`wrangler.toml` の `crons` と `index.ts` の `CRON_WEEKLY_BOSS` は文字列一致で照合される。片方だけ変えると `scheduled()` が `default` 分岐に落ち、警告だけを残して何も実行しない。`index.test.ts:75` の `WEEKLY_CRON` も同じ値を持つので3箇所を同時に変える。

`wrangler.toml:60` のコメント「"1" = 月曜（標準cron表記。日=0〜土=6）」は誤りである。Cloudflareは「1=日曜〜7=土曜」と解釈する。日次化で曜日フィールドを使わなくなるが、誤った記述を残すと将来同じ事故が起きるので訂正する。

デプロイ後、翌日の発火で2回目が無操作になることを確認する。ボスHPが変化しないことが判定条件である。

### T-183 の実装方針

skip分岐で `packCache.has(packUrl)` を1回確認する。不在なら通常の同期経路へ落とす。これで手動削除とiOSの退避の両方が自己修復する。

`handleClearCache` は `packCache.clear()` に加えて同期状態を削除する。片方だけでも動くが、両方入れる。

`CacheStoragePackCache` のキャッシュ名を将来v2へ上げる場合の旧名掃除（Q-18）は本タスクに含めない。現時点で移行の予定がなく、投機的な実装になる。29のQ-18に記録が残っているので、上げる時点で対応する。
