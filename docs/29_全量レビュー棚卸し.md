# 29. 全量レビュー棚卸し（2026-08-04）

## 1. 結論

アプリ・共有API・コンテンツパイプライン・ドキュメントを8観点で点検し、所見112件を記録した。

最優先は週次ボスが生成されない障害の原因仮説である。Cloudflare Workers のcron式は曜日を「1=日曜」と解釈するため、`0 0 * * 1` は月曜ではなく日曜0:00 UTCに発火する。日曜はISO週の最終日なので、発火しても生成対象が終わりかけの週になり、翌週分のボスは作られない。この仮説はコードと公式ドキュメントの突き合わせによるもので、本番ログでの確定は済んでいない。

次に、共有APIの `Access-Control-Allow-Methods` に `DELETE` が無く、ゴースト記録の撤回がブラウザから実行できない。同意撤回の経路が本番で機能していない疑いが濃い。

イベントバトルのWebSocketメッセージは `type` しか検証しておらず、参加者が得点を任意の値で送れば集計と順位表が壊れる。

学習ロジックでは、カリキュラム移行判定に読解の解答が混入する欠陥と、「間違えた問題」の克服バッジが実質常に false になる欠陥を検出した。オフライン面では、キャッシュを手動削除するかiOSがストレージを退避した後、問題パックが二度と再同期されない経路がある。

ビルド・テスト・lintはいずれも成功している（テスト1747件全通過）。品質の穴は静的検査で捕まらない領域に集まっている。

### Q-1 の機構

Cloudflare Workers のCron Triggers は曜日フィールドを「1=日曜〜7=土曜」と解釈する。公式ドキュメントは "Days of the week go from 1 = Sunday to 7 = Saturday, which is different on some other cron systems (where 0 = Sunday and 6 = Saturday)" と明記している。

`wrangler.toml:60` のコメントは「"1" = 月曜（標準cron表記。日=0〜土=6）」と書いており、Cloudflareに対しては誤りである。したがって `crons = ["0 0 * * 1"]` は日曜0:00 UTCに発火する。

日曜はISO週の最終日である。`generateWeeklyBoss` は `isoWeekInfo(now)` で当週を求めて `bossId` を作るため、日曜に発火すると終わりかけの週のIDになる。その週のボスは既に存在するので、`stub.init` の冪等ガードが働いて何も起こらない。翌週分のボスは作られない。

この機構は観測された症状と整合する。2026-07-26（日）に発火した場合、対象は `boss-2026-W30` で、これは2026-07-22に手動生成済みだったためスキップされる。2026-08-02（日）に発火した場合、対象は未生成の `boss-2026-W31` なので生成が成立する。いずれの場合も、月曜以降にアプリが要求する当週のID（W31・W32）は存在せず404になる。

確定には本番の状態確認が要る。手順は付録A-1に置いた。

修正は `crons` をCloudflare表記の月曜（`0 0 * * 2` または `0 0 * * MON`）へ変更する。同時に `index.ts:33` の `CRON_WEEKLY_BOSS` も変更しなければならない。`scheduled()` は `controller.cron` の文字列一致で処理を出し分けるため、両者が食い違うと `default` 分岐に落ちて何も実行されず、ログには警告だけが残る。

### Q-2 の機構

`corsHeaders` が返す `Access-Control-Allow-Methods` は `GET,POST,OPTIONS` で、`DELETE` を含まない。

アプリの `deleteOwnGhostRecord` は `DELETE /ghosts/own` を呼ぶ。`Authorization` ヘッダを伴うDELETEは単純リクエストではないため必ずプリフライトされ、`Allow-Methods` に列挙されていないメソッドはブラウザがブロックする。

ゴースト記録の撤回は同意の取り消しに当たる操作で、プライバシー上の重みがある。実ブラウザでの再現は行っていないが、仕様上ブロックされる。

### Q-3 の機構

`setIdOf` の正規表現 `^(.+)-q\d+$` は、サブ設問ID規約 `<親>-q<n>` に一致する文字列すべてを拾う。この規約は audio_set（Part3/4）と text_passage（Part6/7）で共通である。

`evaluateSetAccuracy` は audio_set のセット正解率を評価する条件（03の3.6節）だが、`aggregateSets` は親の `format` を確認しないため、読解の解答も同じ集約に入る。結果としてP2→P3移行とL3→L4移行の判定が読解成績で汚染される。

同じ規約を扱う `engine/readingPace.ts:75-76` は親を引いて `format === 'text_passage'` を確認しており、対処されている。`curriculum.ts` だけが未対処である。

加えて、`evaluateAccuracy` が持つ `isCountableAttempt`（`vocab:` `shadow:` の除外）が `evaluateSetAccuracy` には無い。

### Q-4 の機構

`collectWrongAnswers` は誤答のdraftを作り、後続の正解attemptで `recovered` を立てる。ただし正解を反映するのは「既にdraftが存在する場合」だけである。

唯一の呼び出し元 `WrongAnswersScreen.tsx:61-64` は `orderBy('answeredAt').reverse()` で新しい順に渡す。「誤答したが後に正解した」ケースでは正解attemptが先に走査され、draftが無いためスキップされる。その後に誤答が現れてdraftが作られるが、`recovered` を立てる機会はもう来ない。

関数のdocコメントは「順序は問わない」と書いており、これは誤りである。既存テストは昇順のみを与えているため、この経路を検出できていない。

### Q-7 の機構

`handleNext` は設問・パッセージ切替時に `setStartedAt(now())` を呼ぶが、`setElapsedSec(0)` を呼ばない。

tick用のeffectは `elapsedSec >= PACE_GUIDE_SECONDS` で早期returnするため、一度60秒を超えると以降のすべての設問で「1分超」の表示に固着する。実際には数秒しか経っていない設問でも同じ表示になる。

60秒未満でも、切替直後の最大1秒間は前問の経過秒が新しい設問に表示される。

### Q-8 の機構

参加者が再接続すると `ParticipantState` が新規作成され、`totalPoints` と `answeredQuestionIndexes` がゼロに戻る。電車内の瞬断で得点が消える。

加えて、出題オープン中に切断して再接続し同一設問へ再回答すると、`currentAnswers` に同一 deviceToken のエントリが複数積まれ、`closeQuestion` で二重加点できる。

### Q-112 の機構

IndexedDBとCache Storageはオリジン単位で隔離される。GitHub Pagesのプロジェクトページはオリジンが `war-lab.github.io` 全体で共有されるため、同一組織の他リポジトリのPages（およびそこに入り込んだスクリプト）から、BYOKのAPIキーと `attempts` を含む学習データを読み取れる。

`docs/05` 5節は「静的サイトなのでXSSの面は狭い」としているが、クロスリポジトリの同一オリジン共有という論点は記載が無い。支出上限付きキーの推奨で影響は緩和されるが、根本的な対策はカスタムドメインの導入である（J-113）。

なお、エクスポートからのAPIキー除外（`backup.ts:59`）とインポート時の多層防御（同199-208）は正しく実装されている。

現在のメインチャンクは510KBでQ-17の2MiB上限には遠い。ただしコード分割を導入すると、`autoUpdate` による即時takeoverで旧チャンクが404になる経路が新たに生じるため、Q-94（Viteの500KB警告）と合わせて判断する必要がある。動的importは現状0件で、単一バンドルのため今の設定は安全である。

`no-restricted-globals` によるESLint境界は `window.caches` や `new window.Audio()`、`webkitAudioContext` を検出できず、`Notification` は制限対象外である。現時点で違反箇所は無いが、抑止力としては穴がある（`eslint.config.js:35-49`）。

### Q-11・Q-12 の機構

`syncPacks` は `packHashes[entry.id] === entry.hash` が成立すればそのパックをskipする。実体がキャッシュに存在するかは確認しない。

設定画面の `handleClearCache` は `packCache.clear()` を呼ぶが、`packSyncState`（packHashes）をリセットしない。したがって削除後の起動でも全パックが「同期済み」と判定されてskipされ、キャッシュは空のまま残る。上流のハッシュが変わるまでこの状態が続く。

オンラインではfetchフォールバックが働くため気づきにくい。オフラインに入った時点で、問題パックと音声がすべて消えた状態が顕在化する。

同期状態はIndexedDB、実体はCache Storageという別ストレージに置かれているため、iOSがCache Storageだけを退避した場合も同じ状態になる。`App.tsx:301` で `navigator.storage.persist()` を要求しているが、非インストール状態のブラウザタブでは拒否されうる。

skip分岐で `packCache.has(packUrl)` を1回確認すれば、手動削除と退避の両方が自己修復する。あわせてキャッシュ削除時に同期状態もリセットする。

### Q-13 の補足

miss時にfetchで代替しても、取得したレスポンスをキャッシュへ書き戻さないため次回も miss する。Q-11・Q-12と重なると、オンラインで使えている間はキャッシュが一切回復せず、オフラインに入った瞬間に破綻が現れる。

### Q-16 の補足

`decodeAudioData` はサンプルレートに応じたfloat32 PCMへ展開するため、Part3/4の30秒級音声は1件あたり数MBから10MB超になる。上限が件数50のみだと最悪ケースで数百MB規模になり、iOS Safariではタブの強制終了につながる。実サイズの実測は行っていない。

### Q-19 の機構

`isBattleClientMessage` は `type` が既知の文字列かどうかだけを判定する。ペイロードのフィールドは一切検証しない。

`join.displayName` は型も長さも検証されないまま全参加者へブロードキャストされる。`answer.points` は数値であることすら検証されないため、参加者が負数・極大値・NaN・文字列を送れば `totalPoints` と順位表が壊れる。`openQuestion` の `questionIndex` `questionId` も素通しである。

REST側（`raidValidation` `statsValidation` `ghostValidation` `register`）は上限を含めて堅実に検証しており、WS層だけが検証層を欠いている。

### Q-20 の機構

`generateWeeklyBoss` は①EMA更新、②HP算出、③ボスDO初期化の順に進む。③には冪等ガードがあるが、①のEMA更新は冪等でない。

「既存ならスキップ」の判定は `POST /admin/raid/generate` のハンドラ側にあり、`generateWeeklyBoss` の内部には無い。したがって次の2経路でEMAが二重に平滑化される。

第一に、同じ週に手動生成とcron発火の両方が走った場合である。第二に、admin側の存在チェックと生成が非アトミックなため、並行する2リクエストが両方「存在しない」を観測した場合である。

## 付録

### A-1 cron曜日仮説（Q-1）の確定手順

いずれも読み取り専用で、本番の状態を変更しない。Bearerには本番KVに登録済みの `deviceToken` を使う。

第一に、`GET /raid/summary` を叩く。2026-07-30時点でこれは `200 []`（空配列）だった。現在も空であれば日曜発火は起きていない。エントリが存在すれば、`writeRaidSummary` が走った＝cronが発火したことになる。`generateWeeklyBoss` は前週ボスのサマリを書くため、記録されているbossIdから発火時期が絞れる。

第二に、`boss-2026-W31` が存在するかを確認する。仮説どおり2026-08-02（日）に発火していれば、その時点で未生成だったW31が生成されているはずである。W31が存在してW32が手動生成であることは、日曜発火を強く支持する。

第三に、Workers Logs（Cloudflareダッシュボード → Workers → beb-raid-api → Logs）で発火時刻を直接見る。`週次ボス生成完了` が日曜0:00 UTCに記録されていれば確定する。`未知のcron式` の警告があれば、Q-1とは別にCloudflare側の式正規化を疑う。ローカルのwrangler OAuthトークンではObservability照会が403で拒否されるため、ダッシュボードかObservability権限付きのAPIトークンが要る。無料プランの保持期間があるため、直近の記録は早めに確認する。
