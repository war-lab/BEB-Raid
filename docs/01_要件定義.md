# 01. 要件定義

## 1. 背景と経緯

### 初版（昼休み主軸）からのピボット

初版は「社内昼休み45分のワイワイ学習」を主軸に設計したが、草案更新により主戦場を**通勤電車でのソロ学習（電車ポチポチ）**に転換した。理由:

- 学習時間の絶対量は通勤時間の方が確保しやすい（毎日・往復・一人で完結）
- 昼休みは全員の予定が揃う日が限られ、同期イベント依存の設計は継続の脆弱点になる
- スマホ・1タップ起動・スキマ時間消化が草案でマスト要件になった

昼休みのワイワイ要素は捨てず、**週次レイド（非同期）と昼の同期イベント**として再配置する。

### 最終目的（不変）

遊びで終わらず**スコアが実際に上がる**こと（例: 380 → 760）。

### 目的の優先順位（不変）

1. **継続すること** — スコアは学習時間の関数。続かないアプリは無価値。
2. **正しい配分で学習すること** — レベル帯によって「やるべきこと」が全く違う（03参照）。
3. **楽しさ・連帯** — 1と2を支える手段。手段が目的化して学習効率を壊さない。

## 3. 機能要件

詳細は [02_機能設計](02_機能設計.md)。

- **FR-1 電車ソロセッション**: 1タップで3分/7分/15分パック開始。オフライン動作。片手操作UI。
- **FR-2 リスニング特化**: Part2瞬発、ディクテーション、再生速度変更（0.7x–1.3x）、シャドーイング支援（スクリプト同期ハイライト）。音声はTTS生成mp3。
- **FR-3 語彙（金フレ型体験）**: TOEIC頻出度順・1語1フレーズ・スワイプ操作のSRS単語帳。※金のフレーズのリスト・フレーズは流用しない（R-1参照）。
- **FR-4 key単語システム**: 各問題が「この単語が分からないと解けない」key語彙を持つ。誤答→key単語がSRSに入り、同じkey単語を使う類題が優先出題される。
- **FR-5 レイドバトル（統一エンジン）**: 週次協力レイド（PvE・非同期）とゴーストレイド（上級者の解答記録がボス化する非対称PvP）。ダメージは常にハンディキャップ換算。
- **FR-6 昼イベント**: Kahoot型同期バトル（プロジェクター＋各自スマホ解答）。週イチ程度のお祭り枠。
- **FR-7 復習ループ**: あらゆるモードの誤答が復習デッキ（SRS）に自動蓄積される。全設計の背骨。
- **FR-8 継続装置**: ストリーク（Duolingo型）、成長ランク、スコア伸びグラフ、到達予測。
- **FR-9 AI解説**: 全問に事前生成解説（人手レビュー済み）。オンデマンドAI質問はBYOK（自分のAPIキー）で提供、将来プロキシ化。
- **FR-10 コンテンツパイプライン**: LLM生成→人手レビュー→TTS→パックビルドの量産ライン。

## 4. 非機能要件

| 項目 | 要件 |
|------|------|
| デバイス | **スマホファースト（マスト要件）**。PCブラウザは管理・昼イベントホスト画面のみ |
| 起動 | ホーム画面アイコンから3秒以内に学習開始可能な状態。ログイン操作なし（local-first） |
| オフライン | 電車（トンネル・地下）で完全動作。問題JSON＋音声を事前キャッシュ。レイドの共有状態のみオンライン時に同期 |
| ストレージ | 端末キャッシュ 100–200MB 目安（音声含む）。学習ログのエクスポート/インポート対応 |
| 公開範囲 | GitHub Pages（全世界公開）に置いて問題ないコンテンツのみ。**個人名・成績・社名をリポジトリに含めない** |
| 共有API | 無料枠内で運用（レイド共有状態と匿名問題統計のみ）。API未接続でもソロ機能は全て動作すること |
| 心理的安全性 | 絶対スコアの晒し上げをしない。ランキングは成長ベース、表示名は本人選択 |
| 将来性 | iOS/Androidネイティブ化（Capacitorラップ）に移行可能な技術選定を維持する（05参照） |

## 5. 制約・前提

- ホスティングは GitHub Pages（静的）を第一候補とする。サーバーサイド処理は持てない。
- 共有が必要な機能（レイド）は無料枠のエッジAPI（Cloudflare Workers等）に限定して持つ。
- 市販教材（音声・問題・単語リスト）はアプリに搭載しない。個人購入教材は各自がアプリ外で使う。
- TTS・LLMの利用コストは作問時（ビルド時）のみ発生する設計とし、ランタイムのAPI課金を原則ゼロにする。

## 6. リスクと対応方針

### R-1: 著作権（着手前に必ず確認・最重要）

対象が2つある:

1. **市販教材の音声・問題**: 複製してWeb配信（社内限定でも）することは私的複製の範囲外となる可能性が高い。→ **アプリには一切搭載しない**。コンテンツは自作（LLM生成＋人手レビュー）＋TTS音声＋再配布可能ライセンス素材のみ。
2. **金のフレーズの単語リスト・フレーズ**: 単語の選定・配列・フレーズは編集著作物として保護される可能性が高い。リストの転記・フレーズ流用はしない。→ 「金フレ型の体験」（頻出度順・1語1フレーズ・高速周回）を、**公開コーパス由来＋LLM推定の自前頻出度リストと新規生成フレーズ**で再現する。なお、市販の頻出度リスト自体も編集著作物になり得るため、頻出度データの出所も自前・公開データに限定する（LLM推定頻出度の精度は未検証であり、実測正答率で補正する。03参照）。

### R-2: 学習時間の絶対量

初版時点の懸念（昼45分のみ→年190時間で不足）は、電車主軸化で改善した。通勤往復40分＋昼一部＋就寝前SRS10分なら年300時間超が視野に入る。ただし380→760（+380点）は数百時間規模とされ（100点UPに200–300時間という経験則。個人差が大きく未検証の目安）、**1年での到達は保証できない**。到達予測はダッシュボードに正直に表示し、楽観表示で誤魔化さない。

### R-3: レベル差による場の崩壊

素点勝負にすると上級者が常勝し初級者が脱落する。→ ハンディキャップ換算（Elo式期待正答率ベース）を全モード共通ルールとする。レイドでは上級者を「ボス役」に配置し、**レベル差そのものをゲーム構造に変換する**（02・03参照）。

なお、ハンディ換算には意図的なレート下げ（サンドバッグ）でダメージを盛れる構造的な穴がある。仲間内運用では実害が小さいと判断し、当面は対策せず既知の穴として扱う（03の5.6参照）。

### R-4: ソロアプリの飽き

ソロ学習アプリは3週間で飽きるのが相場。→ ストリーク（軽い成立条件）＋週次レイドの連帯（「今週みんなで倒す」）＋昼イベントの3層で継続圧を作る。初版にあった「幹事不在で文化が途切れる」リスクは、非同期レイド主軸化により解消された。

### R-5: iOS のストレージ退避

Safari は一定期間未使用の Web サイトのローカルデータを削除することがある（ホーム画面追加済みPWAは対象外とされるが、挙動はOSバージョン依存で完全には保証されない）。→ ①ホーム画面追加を初回導線で強く推奨、②学習ログの自動バックアップ（共有API接続時）またはエクスポート機能、③将来のネイティブ化（Capacitor）で根本解消。

### R-6: LLM生成問題の品質

悪問は学習を阻害し信頼を落とす。→ 人手レビュー必須（04のパイプライン）。アプリ内に「この問題おかしい」報告ボタンを付け、報告された問題は出題停止して再レビュー。

### R-7: 共有APIの無料枠超過・消失

→ レイド共有状態は極小データ（ダメージログと表示名のみ）に絞る。API消失時もソロ機能は無傷で動く設計（グレースフルデグラデーション）を必須とする。

## 7. スコープ外（明示）

- スピーキング/ライティング対策（TOEIC S&W）
- シャドーイングの録音自動採点（音声認識スコアリング）。スクリプト同期支援まで。録音セルフチェックはv2検討
- PDF自動取込（LLM半自動変換＋人手確認で代替）
- 全社・絶対スコアランキング
- 初版で検討した「社内サーバー/自PCでのローカルサーバー運用」は廃止（共有APIがインターネット上にあればスマホは自前回線で届き、社内LAN疎通問題が消えるため）
